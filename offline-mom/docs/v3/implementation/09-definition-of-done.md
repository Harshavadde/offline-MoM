# V3 Definition of Done

Derived from `docs/v3/01-prd.md` §24 (Acceptance criteria) and §25 (Implementation milestones) only — no requirement below is added from outside the PRD.

**Last updated:** 2026-08-10, Milestone 5 finalized (all five milestones complete).

## A task is done when

- The specific file(s) PRD §25 (via [02-backlog.md](02-backlog.md)) names for that task exist and compile — or, where the repository's real structure genuinely differed from the PRD's literal file list, the real file that serves the same purpose exists, and the difference is logged in [03-decisions.md](03-decisions.md).
- The task's own test(s) exist and pass.
- `flutter analyze` is clean for the changed files (and, before a milestone-level commit, project-wide).
- No unrelated file was touched (verified via `git status`/`git diff --stat` review).
- The task's containing milestone has been committed (not merely implemented in the working tree).

## A milestone is done when

All of the following:

1. Every task in that milestone's backlog slice ([02-backlog.md](02-backlog.md)) is done.
2. That milestone's own PRD §25 "Acceptance criteria" line is verifiably true — checked against actual test/analyze output.
3. That milestone's own PRD §25 "Manual verification" item is either completed and recorded, or explicitly logged as outstanding.
4. The full `flutter test` suite passes with zero failures (not just the milestone's own new tests).
5. The milestone's changes are committed as their own commit(s), separate from any other milestone, and pushed to `origin/main`.

**Applied literally through this pass:** Milestones 0 through 5 each meet every point above — each has its own commit on `origin/main` (`dd4a03d`/`0e47848`, `d67528a`, `30bf491`, `2f92bba`, `7219ac5`, plus Milestone 5's own commit recorded in [07-git-strategy.md](07-git-strategy.md)), each milestone's acceptance criteria is verifiably true against current code, and each milestone's manual-verification item is explicitly logged as either completed or still outstanding rather than silently skipped (see [01-master-roadmap.md](01-master-roadmap.md)). All five are marked ✅ **COMPLETE** on that basis — where "complete" means the milestone's own scoped work is done and gated, not that every real-device/human-judgment verification has occurred (several explicitly have not — see below).

**V3 is technically beta-ready — this is a narrower claim than "production ready," and the two must not be conflated.** Every PRD §24 criterion that is verifiable through code review, unit/widget tests, or static analysis in this implementation environment is now met. Three categories of verification remain genuinely outstanding, disclosed rather than silently assumed complete:

1. **Real-device verification** — RAM-tier detection/sequencing under actual memory pressure (RV3-03, RV3-04, RV3-12), and the two new native-PDF-extraction ATS round-trip tests (RV3-13, RV3-05) are written and statically verified but have never executed on real hardware, since none is available in this environment.
2. **Human visual/product-quality validation** — no genuine human review of the 10 shipped templates against the Enhance CV reference bar has ever occurred; only AI-assisted spot-checks and five subsequent AI-assisted redesign passes (Visual-Quality, Reference-Driven, Product/structural, Product Visual-Audit, Product Composition-Audit) have been done (RV3-10).
3. **Widget-test breadth** — 9 of ~15 screens remain without dedicated widget tests, a disclosed, deliberately deprioritized gap, not a beta blocker (RV3-15).

No blocking defect was found during Milestone 5 that would prevent beta testing from proceeding. The above three items are the honest, load-bearing caveats on "beta-ready" — they are what separates it from "production ready," and beta testing itself (real users, real devices) is exactly what would close them.

**Post-Milestone-5 beta validation pass** (see [10-v3-progress.md](10-v3-progress.md)): ran the real tailoring pipeline end-to-end against 3 realistic personas and visually inspected all 10 rendered templates directly. Found **zero blockers**, two new non-blocking cosmetic/UX findings (RV3-17, RV3-18), and independently reconfirmed RV3-10's whitespace observation with realistic content. This strengthens, but does not change, the verdict above — the same three caveats (real-device, human-visual, widget-test breadth) remain the load-bearing gaps between beta-ready and production-ready.

**Five subsequent redesign passes** (Visual-Quality, Reference-Driven, Product/structural, Product Visual-Audit, Product Composition-Audit — see [10-v3-progress.md](10-v3-progress.md)): resolved RV3-17, embedded a real typeface, replaced the flattened-string entry-title rendering with a structured role/company/date/location model and a genuinely differentiated Balanced Two-Column archetype, added the catalog's first genuine color anchors and a working icon system, and — in the most recent (composition-audit) pass — added the catalog's first real information-hierarchy mechanism (recency-weighted Experience bullet density for long careers) plus a corrected two-column ratio, while explicitly declining to build a generalized page-allocation layer that this pass's own investigation found `package:pdf`'s actual capabilities don't safely support without new infrastructure. Each pass's own mandatory visual re-inspection found no regression; three of the five passes' own inspections each caught and fixed one real defect (including a bug in the composition-audit pass's own test persona) before declaring completion, rather than after. None of the five changes the verdict above — human visual review (RV3-10) remains the one gate no amount of further AI-assisted iteration can close on its own, and the composition-audit pass explicitly did not claim to have closed the deeper "composition engine" gap either.
