# V3 Architecture & Product Decisions

Every decision below is either explicitly stated in `docs/v3/01-prd.md` (cited by section) or a concrete implementation decision made during Milestones 0–4 and confirmed against the actual repository. Nothing here is invented or backdated — decisions with no PRD section reference are marked **Implementation-derived** and grouped by the milestone during which they were made.

**Last updated:** 2026-08-11, final product-build + physical-device beta validation phase (release APK, LiteRT-LM runtime scoping).

## Implementation-derived decisions (Milestone 3)

| # | Decision | Reason | Source | Status |

| D-M3-03 | Suggestion **generation** is triggered from the JD Analysis results screen (`resume_jd_analysis_screen.dart`), not the Editor screen, even though PRD §25's Milestone 3 modified-file list only names `resume_editor_screen.dart`/`resume_editor_providers.dart` | JD content is explicitly session-only and never persisted (PRD §14/FR3-05) — by the time a user is back on the Editor screen, the JD text and the already-computed match results no longer exist anywhere for a "Generate" action to use. The JD Analysis screen is the only place in the app where a JD and its match results are simultaneously live in memory. The Editor's own entry point (`_SuggestionsAction`) only ever *reviews* suggestions that already exist — it never generates new ones | Implementation-derived, Milestone 3 (repository reality differs from the PRD's literal file list; PRD's *intent* — an entry point into review from the Editor — is still fully satisfied) | Accepted |
| D-M3-04 | `SuggestionFabricationGuard` is **flag-only** — it never blocks generation, never blocks acceptance, never prevents a `SuggestedEdit` from being persisted or shown | Matches PRD §6 AC3-03 and §22.3 D-08 exactly as written ("flags... for extra user scrutiny, never auto-rejects"). The shipped `SuggestionFabricationGuard.check()` has never implemented rejection at any point — it returns a `FabricationCheckResult{isSafe, newNumbers, newProperNouns}` that callers only ever use for display, never for control flow. `GenerateResumeSuggestionsUseCase` does not call the guard at all (a persisted suggestion's flag is computed lazily, at review time, from already-stored `originalValue`/`suggestedValue` — functionally identical to computing it once at generation time and discarding nothing, since the check is a pure function of stored data). `AcceptSuggestedEditUseCase` does not call the guard either — a suggestion the user chooses to accept despite a shown warning is accepted exactly as chosen | PRD §6 (AC3-03), §22.3 (D-08) | Accepted — confirmed, not a deviation |
| D-M3-05 | `AcceptSuggestedEditUseCase` re-validates against the resume's *current, fully-resolved* field content (recompiled via the existing `ResumeCompilerService`, not a cached value) before applying, and rejects with `SuggestedEditNoLongerApplicableException` if it no longer matches `SuggestedEdit.originalValue` byte-for-byte | Acceptance is the last gate before anything reaches live content — it must never trust that generation-time state still holds. Without this check, accepting a suggestion generated against now-stale content (e.g. the user manually edited the same bullets afterward) would silently overwrite the user's newer edit with a stale AI rewrite | Implementation-derived, Milestone 3, following the general "revalidate before applying" instruction given for this milestone | Accepted |
| D-M3-06 | Suggestion generation is scoped to the `bullets` field on Experience/Project entries and the `details` field on Education entries only — Certification/Skill entries and profile-level fields are not suggestion targets in this milestone | `ResumeBlockRepository.setOverride`/`ResumeCompilerService` only ever resolve a per-resume override for `experience.bullets`, `education.details`, and `project.bullets` (confirmed by direct inspection of `resume_compiler_service.dart` — certification/skill refs never read `overrideJson`, and `Resume`/`ResumeEditorController.updateProfile()` have no mergeable "summary" field). Generating suggestions for a field with no real merge path would mean either inventing a new persistence mechanism (out of this milestone's scope) or generating suggestions Accept could never actually apply | Implementation-derived, Milestone 3 (repository reality bounds the PRD's more general "per-entry AI rewrite suggestions" language) | Accepted |
| D-M3-07 | A new `LlmEngine.generateFromPrompt(systemPrompt, userPrompt)` method was added rather than reusing an existing `LlmEngine` method | Every existing method (`answerQuestion`, `answerQuestionStream`, `answerGeneralKnowledgeStream`, `generateSummary`) bakes its own fixed system prompt into the engine implementation, tuned for a different purpose (`answerQuestion`'s system prompt literally says "using ONLY the meeting notes given to you," which would be actively misleading for a resume-suggestion prompt; `answerGeneralKnowledgeStream` explicitly *permits* the model to draw on outside knowledge, the opposite of AC3-01's fabrication ban).
