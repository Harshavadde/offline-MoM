# Responsible AI Statement

## Scope

OfflineMoMAI uses three on-device AI models, each independently downloadable/switchable/deletable via the AI Model Manager: whisper.cpp (six selectable tiers, `tiny` through `large-v2`) for speech-to-text, Qwen2.5-1.5B-Instruct (via llama.cpp) for meeting/document summarization, key-topic extraction, and Chat, and embeddinggemma-300M for the embedding search that powers Chat's retrieval. This statement covers how the project approaches their reliability, transparency, and oversight. (An earlier version of this app used two models and an "Ask AI" feature scoped to meetings only; Ask AI still exists but is no longer linked from any screen — see [`docs/architecture/ai-architecture.md`](../architecture/ai-architecture.md#the-legacy-ask-ai-feature-orphaned-not-removed) — and has been superseded by Chat, which spans meetings, documents, and the whole workspace.)

## Transparency about AI limitations

- The app never presents AI output as ground truth. The full transcript is always available alongside the AI-generated summary/MoM specifically so a user can verify the AI's interpretation against what was actually said.
- Action items are entered and checked off by the user, not AI-generated — see the "Why decisions and action items aren't AI-extracted" note in [`docs/architecture/ai-architecture.md`](../architecture/ai-architecture.md). An earlier version had the AI extract both action items and decisions; this was reversed after testing showed the small model's structured extraction was too often malformed or unreliable, particularly on longer or more complex meetings, for a feature meant to save time rather than require careful verification.
- Chat answers from the user's own meetings/documents when its retrieval engine finds a confident match, with citations back to the source; every message also carries an always-visible "AI-generated response — please verify important information" note. When nothing in the user's own content is a confident match, Chat still answers using the model's own general knowledge rather than a dead end, but that answer is clearly labeled as general knowledge (not sourced from the user's content) and never carries a citation. The legacy Ask AI feature (meetings-only, no general-knowledge fallback) is unchanged and still available at its own unlinked route.
- Transcription accuracy, especially for Indian languages less represented in Whisper's training data, is a known, disclosed limitation; the default model was upgraded from `base` to `small` specifically to improve this, and users can opt into "Always give me English text" or select their spoken language explicitly, but accuracy is not claimed to be perfect.
- See [`docs/architecture/ai-architecture.md`](../architecture/ai-architecture.md) for the specific, documented trade-off of using small models (whisper `small`, Qwen2.5-1.5B) rather than larger ones, made deliberately for on-device feasibility, at a known cost to output quality.

## Human oversight

Every AI output in this app is generated on request and requires no further automated action — nothing the AI produces triggers an automatic external effect (no auto-sent emails, no auto-scheduled calendar invites, no auto-shared summaries, no automatically-trusted translation used to make a decision on the user's behalf). The human user is always the one who decides whether to act on, export, share, or speak based on any AI-generated content.

## Failure handling, including bounded latency

Every AI-backed feature (transcription, summarization, Chat) has explicit failure handling: if a model call fails or its output is unusable, the relevant flow surfaces a clear, plain-language error (never a raw exception or stack trace — every user-visible error passes through a shared translation utility) rather than silently fabricating a plausible-looking but wrong result, and the UI shows a dedicated failure state (`AiPipelineFallback` for meetings/documents, a dedicated empty state in Chat if no chat model is installed yet) instead of presenting failure as success. This extends to *timing out*, not just outright failing: because summarization and Chat share one underlying model that processes requests one at a time, a stuck generation call was found in testing to be able to block every AI feature in the app indefinitely (see [`docs/architecture/ai-architecture.md`](../architecture/ai-architecture.md#reliability-timeouts-and-cancellation)); the same was separately found true of a stuck Whisper transcription call. Both are now bounded by explicit timeouts, alongside the one-time model download, so an AI failure always surfaces to the user in bounded time rather than as an indefinite wait that looks identical to the app being broken.

## Reliability testing performed

Use-case-level tests (`test/use_cases/generate_meeting_summary_use_case_test.dart`, `transcribe_meeting_use_case_test.dart`) verify the app's handling of AI success, failure, and timeout paths. What could **not** be verified in this project's build environment is real-world output quality/reliability on actual meeting audio and real conversations, since no Android device or emulator was available during initial development (see [`docs/guides/installation-guide.md`](../guides/installation-guide.md)). Real-device testing performed later in the project did surface two genuine reliability defects — an indefinite generation hang and an unbounded model-download hang — both since fixed; this is disclosed as evidence that on-device validation matters and surfaces things unit tests alone do not, not as a claim that all such issues are now found.

## Data used by the AI models

No meeting content, document content, or Chat/Ask AI question is used to train, fine-tune, or otherwise improve any model — the models are fixed, pre-trained artifacts downloaded once and run purely for inference. Nothing generated or processed by this app is sent anywhere that could feed back into model training.
