# V2 Technical Risk Register

Every risk below is tracked against a specific mitigation and a fallback — a mitigation reduces the chance or severity of the risk; a fallback is what happens if the mitigation isn't enough. Owners are named by role (per the multi-hat review that shaped this document set), not by individual, since team assignment happens at implementation time.

| R-21 | `Future.whenComplete(callback)` awaits whatever `callback` *returns*, if that return value is itself a `Future` - a real, silent footgun anywhere a cleanup callback's return value isn't deliberately discarded (e.g. an arrow-function callback that happens to end in a `Map.remove(key)` call, whose return type is the removed *value*, not `void`) | Confirmed - already happened once, in this exact codebase | High if it recurs - the failure mode is a hung `Future` that never resolves, indistinguishable at first glance from a generic slow test/generic hang; it can pass every earlier `await` in the same function genuinely, making the actual defect (the cleanup callback's return value) far from the symptom (a 30-second per-test timeout in a completely different-looking test file) | None automated (no lint currently catches "arrow-function `whenComplete`/`then`/`catchError` callback whose expression happens to evaluate to a `Future`") - awareness and code-review discipline only | Prefer a block-bodied callback (`.whenComplete() { ...; }`) for any `whenComplete`/`then`/`catchError` cleanup callback whose only purpose is a side effect, never an arrow function (`=> expr`) unless `expr`'s type is visibly `void` - a block body's implicit `void` return can never accidentally hand back a `Future`. | R-23 | A test's own synchronization was timing-fragile, not the production code it tested: `chat_controller_test.dart`'s "cancel() while the request is already running" test waited for `WorkspaceChatUseCase`'s retrieval-then-enqueue steps to reach `LlmEngine.answerQuestionStream` by draining a **fixed** count (20) of `Future.delayed(Duration.zero)` ticks, then immediately asserted on a token emitted right after - if the real sqlite-ffi round-trips retrieval depends on (persisting the user message, `BruteForceVectorStore.similaritySearch`, resolving citation sources) took more real event-loop turns than that fixed budget, the token was emitted before `answerQuestionStream` had actually been called (`onToken` still unregistered) and silently dropped, so the test failed even though the production code under test was correct. Notably, a fixed tick count *of any size* wasn't a reliable fix either: the number of event-loop turns this needed turned out to be process-lifetime-dependent, not just machine-dependent - the test passed reliably every time run alone (any tick budget from 20 up would have looked "sufficient" in isolation), but failed deterministically once run as part of the full suite, hundreds of tests deep in the same long-lived Dart VM process, even against a generous 500-tick budget | Confirmed - reproduced deterministically both in Phase 3B's own environment and, via a temporary `git worktree` checkout, against the pre-Phase-3A baseline commit `514f47f`, proving the underlying fragility predates Phase 3A/3B entirely and is not a regression either phase introduced | Medium - a false-failure in CI/local verification is a real cost (it blocks a legitimate release gate on a bug that isn't there), though it never affected the shipping app itself, only the test's own reliability | Replaced the fixed-tick `_flush()` at that call site with `_pumpUntil(condition, {timeout: Duration(seconds: 10)})`, which polls a real wall-clock deadline (2ms real delays, not `Duration.zero`) against a new `_ControllableLlmEngine.hasPendingCall` getter (and, after emitting the token, `state.streamingText == 'Partial '`) instead of a tick count of any size - a wall-clock bound stays correct regardless of how many event-loop hops the wait actually needs, which a tick count fundamentally cannot guarantee. Verified stable across repeated isolated runs and three full-suite runs after the fix, including the specific full-suite context that reproduced the original failure | If a similar fixed-tick-count wait is found elsewhere and proves fragile the same way, apply the same wall-clock-polling pattern rather than raising the fixed count, since this pass demonstrated that even a 25x-larger fixed count (500 vs. 20) still wasn't sufficient in the full-suite context | QA Lead | Resolved (Phase 3B) in `test/features/chat/chat_controller_test.dart`'s "already running" test. **Two more instances surfaced during Phase 5A's own full-suite verification run** (unrelated to that phase's own Student Toolkit changes - caught only because a routine final `flutter test` pass happened to hit them): (1) `test/use_cases/workspace_chat_use_case_test.dart`'s "cancelling a still-queued request..." test had its own fixed-tick `_flush({times: 20})` waiting for `requestId` to be captured - fixed with the same `_pumpUntil(() => requestId != null)` wall-clock-polling pattern, stable across repeated isolated runs after. (2) `chat_controller_test.dart`'s *other* cancellation test, "cancel() while the request is still queued behind another one", turned out to be a **different and more serious bug once its own fixed-tick wait was first swapped for a naive `_pumpUntil(() => isSending)`**: `isSending` flips true synchronously before `WorkspaceChatUseCase.call` has even started retrieval, well before the request actually reaches the queue and `ChatController._activeRequestId` gets set - so `notifier.cancel()` was racing ahead of `_activeRequestId` being set, silently skipping the `queue.cancel(id)` call entirely (`if (id != null)` guard just no-opped), leaving the still-pending request to sit behind the test's own blocking foreground request forever and deadlocking `await sendFuture`. Naively swapping a fixed-tick wait for `_pumpUntil` on the wrong condition made this **worse, not better** - it went from "occasionally fails a fast assertion" to "hangs for the full 30-second test timeout, 4 times out of 5 in isolation" once the race more reliably tipped the wrong way. Fixed by polling the queue's own `statusStream` (`pendingForeground >= 1`) instead of `isSending` - the correct proxy for "the request has actually been enqueued," matching what the original fixed-tick wait was actually (if unreliably) waiting for. Verified stable across 6+ repeated isolated runs and multiple full-suite runs after the fix. **Lesson for R-23's own general guidance**: swapping a fixed-tick wait for `_pumpUntil` is only a safe mechanical fix when the polled condition is actually the right proxy for "the async work this test depends on has happened" - polling the wrong-but-plausible-looking condition can turn a rare false-failure into a frequent real hang.
