# V2 Master Implementation Roadmap

Implements `docs/v2/07-feature-roadmap.md`'s four phases as concrete, git-tagged milestones. Every milestone ends with a working, installable app and a defined set of manual/automated acceptance checks — none of them are "half-built" checkpoints. See [03-decisions.md](03-decisions.md) for the decisions this ordering depends on, [05-dependency-graph.md](05-dependency-graph.md) for why this order is safe, and [07-git-strategy.md](07-git-strategy.md) for the tagging scheme referenced below (`v2.0.0-alpha.N` etc.).

## How to read this document

Each milestone states: **Goal**, **What ships** (functionality a real user or reviewer can exercise), **Depends on**, **Acceptance check** (how you know it's genuinely done, not just coded), **Git milestone** (tag + merge target). Milestones within a phase are listed in required order unless explicitly marked parallel.

## Phase 0 — Foundation Repair

No new user-facing module. Fixes real gaps in the shipped V1 product and builds infrastructure every later phase depends on. Corresponds to `docs/v2/07-feature-roadmap.md` Phase 0.

### M0.1 — Search parity (summaries + notes become searchable) + FTS5 for existing content
**Goal:** Close the gap where summaries and notes exist but were never searchable, and move off `LIKE`-scan search entirely for existing content types.
**What ships:** Migration v4 (FTS5 tables + sync triggers for `meetings`/`transcripts`/`summaries`/`action_items`/`notes`, per ADR-009). `SearchMeetingsUseCase` reads from FTS5 instead of the four-repository `LIKE` fan-out. No UI change required beyond search now actually returning summary/note matches.
**Depends on:** Nothing new — this is a self-contained improvement to existing, shipped functionality.
**Acceptance check:** A search query matching only a summary's text or a note's content returns the right meeting. Existing search test coverage (title/transcript/action-item matches) still passes unmodified. Query latency does not regress on a database seeded with a realistic transcript-heavy dataset.
**Git milestone:** `v2.0.0-alpha.1`, merged to `main`.

### M0.2 — Explicit LLM request queue
**Goal:** Close the gap between what `docs/v2/11-ai-architecture.md` originally assumed about `llamadart`'s concurrency and what the library actually does (a second concurrent call fails immediately rather than queuing).
**What ships:** `LlmRequestQueue` per ADR-008 (FIFO, foreground-pauses-background-start behavior). Existing call sites (`GenerateMeetingSummaryUseCase`, `AskAboutMeetingsUseCase`) route through it instead of calling `LlmEngine` directly. No user-visible feature change — this is a correctness fix for a bug that hasn't yet been observed in production only because concurrent AI calls have been rare so far.
**Depends on:** Nothing new.
**Acceptance check:** A test that deliberately fires two concurrent LLM calls (one simulating background summarization, one simulating a foreground Ask AI question) completes both successfully in sequence rather than one throwing an uncaught exception — this is the specific regression this milestone exists to prevent, and should be asserted directly, not just assumed fixed.
**Git milestone:** `v2.0.0-alpha.2`, merged to `main`.

### M0.3 — Schema/pipeline hygiene: `decisions` table decision closed, "audio missing" status added
**Goal:** Close two small, disclosed V1 gaps before building on top of the schema further.
**What ships:** `decisions` table's fate formally closed per ADR-012 (no code change — kept as-is, documented as final). `Meeting.status` gains an `audioMissing` state (V1's disclosed risk R5) for the orphaned-row scenario where a meeting's audio file is lost/corrupted after the row was created.
**Depends on:** Nothing new.
**Acceptance check:** A meeting whose audio file is missing at pipeline-start time (simulated in a test) transitions to `audioMissing` with a clear message instead of failing with a generic `error`.
**Git milestone:** `v2.0.0-alpha.3`, merged to `main`.

### M0.4 — V1 documentation sync (non-code)
**Goal:** V1's `docs/` currently describes a Conversation Translator that no longer exists and a Whisper default (`base`) that's no longer accurate. This is documentation work, not Flutter code, and is listed here because Phase 0 is the right time to do it — before V2 work adds more content that would need the same treatment twice.
**What ships:** Updates to the affected V1 files (README, architecture docs) — not part of this implementation-planning document set's own scope to execute, but tracked here as a Phase 0 backlog item (see [02-backlog.md](02-backlog.md), Epic: Foundation Repair).
**Depends on:** Nothing.
**Acceptance check:** No remaining reference to the Conversation Translator as a live feature anywhere in `docs/`; Whisper default correctly stated as `small`.
**Git milestone:** Included in `v2.0.0-alpha.3`'s commit (documentation-only, no separate tag needed).

**Phase 0 exit criteria:** `flutter analyze` and `flutter test` both clean; search demonstrably covers summaries/notes; the concurrency regression test from M0.2 passes; V1 docs no longer describe removed/changed features. Tag: `v2.0.0-alpha.3`.

## Phase 1 — Workspace Infrastructure

The real technical bet. Nothing here is user-facing on its own except where explicitly noted; the goal is a validated, working foundation before UI investment. Corresponds to `docs/v2/07-feature-roadmap.md` Phase 1.

### M1.0 — Embedding & vector-storage feasibility spike (gates everything after it) ✅ Done
**Goal:** Resolve ADR-003 and ADR-004 with evidence, not assumption, before committing further engineering time.
**What ships:** A throwaway/prototype-quality (not production-hardened) proof that (a) a chunk of text can be turned into a vector entirely on-device through the chosen approach, and (b) that vector can be stored and similarity-searched against a small synthetic corpus, end to end. Also validates ADR-011's chunk-size/K starting parameters against real token counts, not estimates.
**Depends on:** Phase 0 complete (uses the LLM request queue's engine-access pattern as the integration point to spike against).
**Acceptance check:** A written spike report (checked into `docs/v2/implementation/spikes/m1-0-embedding-spike.md` or equivalent) stating definitively: which embedding approach works (ADR-003 option 1 or 2), which vector storage approach works (ADR-004 option 1 or 2), and confirmed or corrected chunk-size/K numbers. **This milestone does not end until that report exists and its conclusions are reflected as amendments to ADR-003/004/011 if they differ from the pending default.**
**What actually happened:** Resolved by direct source inspection of `llamadart` 0.8.17 (no on-device execution was available in this development environment - disclosed explicitly in the report). ADR-003: option 1 confirmed feasible (`LlamaEngine.embed`/`embedBatch`, the same package/native path the chat LLM already uses). ADR-004: option 1 (`sqlite-vec`) confirmed **infeasible** for this app specifically (requires `package:sqlite3`, not `package:sqflite`, which the entire database layer is built on) - option 2 (brute-force Dart cosine similarity) is the implementation. ADR-011: chunk-size calibrated via a documented characters-per-token estimate (not a real on-device tokenizer measurement) - remains flagged `Pending Validation`. Given the clean "yes" on ADR-003, M1.2's full pipeline was implemented in the same pass rather than left as a throwaway prototype (see M1.2 below), matching this project's Phase 1A precedent of moving straight from a resolved spike into production code within one milestone. Full report: `docs/v2/implementation/spikes/m1-0-embedding-spike.md`.
**Git milestone:** Not yet committed/tagged as of this documentation update - per this milestone's explicit instructions, implementation stopped short of any git action; recommended tag `phase-1b` (see the milestone's final report).

### M1.1 — Document import + text extraction (no chat/retrieval yet) ✅ Done
**Goal:** A user can import a PDF/DOCX/TXT/Markdown file and see its extracted text and an AI summary — the full pipeline up to but not including retrieval/chat.
**What ships:** `Document` model/repository/migration v5 (per ADR-009's corrected sequence). `DocumentImportController` (mirrors `ImportController`). Per-format `DocumentTextExtractionService` implementations, license-audited per ADR-016 before adoption. `Document.status` state machine (`created → extracting → ready`/`error`, `indexing` withheld until M1.2). Document summary generation, reusing the existing LLM engine/queue/timeout machinery and the shared `summaries` table (ADR-005). Also shipped (beyond this section's original scope, per the Phase 1A implementation prompt that superseded it): rename/delete, the real Documents UI (Home/Import/Details/Rename/Delete, `AiPipelineFallback` generalized for reuse), and documents joining the existing FTS5 search (`ContentSearchRepository`/`SearchMeetingsUseCase` generalized rather than duplicated) — folding in the search-integration slice of what M2.2 originally scoped as a separate migration v7, since v6 already touched `content_fts` for the CHECK-constraint rebuild (see ADR-018).
**Depends on:** M0.2 (LLM queue), M0.3 (schema hygiene precedent). **Does not depend on M1.0** — text extraction and summarization don't need embeddings; this milestone is intentionally sequenced to start in parallel with the spike where calendar time allows (see [05-dependency-graph.md](05-dependency-graph.md)).
**Acceptance check:** Import a real-world PDF, DOCX, TXT, and Markdown file each; each reaches `ready` with correct extracted text and a summary. A password-protected or corrupted PDF reaches `error` with a specific message, not a crash. A scanned/image-only PDF reaches `error` with the ADR-015 message, not silent garbage output.
**Git milestone:** Tagged `phase-1a` (not `v2.0.0-alpha.5` — this document set's illustrative tag scheme was not followed in practice; Phase 0 was tagged `phase-0`, establishing the actual convention), merged to `main`.

### M1.2 — Chunking, embedding, vector storage (`knowledge_chunks` populated, no UI change) ✅ Done
**Goal:** Every `ready` meeting and document gets automatically chunked and embedded in the background, closing the loop M1.0 validated.
**What ships:** `knowledge_chunks` table, migration v6. `ChunkingService`, `EmbeddingEngine` (concrete implementation per M1.0's validated approach), `VectorStore` (concrete implementation per M1.0's validated approach). `Document.status` gains the `indexing` sub-stage. Meetings gain the same background indexing step retroactively (existing `ready` meetings get indexed on next app launch or via a one-time backfill task).
**Depends on:** M1.0 (validated approach), M1.1 (documents exist to index).
**Acceptance check:** After importing a document or completing a meeting, `knowledge_chunks` rows exist for it within a bounded time, without user action. A similarity query against a known-relevant chunk returns it in the top results of a hand-verified test corpus. Chunk/K token counts from ADR-011 are re-validated against this real implementation, not just the M1.0 prototype.
**What actually shipped (Phase 1B):** `knowledge_chunks` table via migration **v7**, not v6 (v6 was already spent in Phase 1A - see ADR-019). `ChunkingService`/`DefaultChunkingService`, `EmbeddingEngine`/`LlamaDartEmbeddingEngine`, `VectorStore`/`BruteForceVectorStore`, `KnowledgeChunkRepository`/`SqfliteKnowledgeChunkRepository`, `RetrievalEngine`/`DefaultRetrievalEngine` (all content-type-agnostic, ADR-020). `Document.status.indexing` is now actually used (was reserved-but-unused since Phase 1A) - `DocumentIndexer` wired into `ProcessNewDocumentUseCase`/`RetryDocumentProcessingUseCase`, so a newly-imported document is chunked, embedded, and stored automatically. **Not shipped this pass:** meeting indexing (`MeetingIndexer` + `MeetingStatus.indexing`) - deliberately deferred per ADR-020, disclosed as a gap below rather than silently left undone. Chunk/K calibration is a documented characters-per-token estimate, not an on-device tokenizer measurement (no device available to this implementation environment - see the spike report) - ADR-011 stays `Pending Validation`.
**What actually shipped (Phase 1C, closing this milestone):** Migration **v8** (ADR-021) adds `content_type`/`source_id` to `knowledge_chunks`, so a meeting's several independently-changing prose sources (transcript, summary, each note) can be re-indexed without clobbering siblings' chunks. `MeetingIndexer` (ADR-022) now indexes every `ready` meeting's transcript and summary automatically, mirroring `DocumentIndexer`; `MeetingStatus.indexing` is wired through `ProcessNewMeetingUseCase`/`RetryMeetingProcessingUseCase` and every exhaustive `switch` over `MeetingStatus`. Meeting notes are indexed individually at add/edit/delete time via `NotesController` (not part of the pipeline, since they're mutated interactively). `RetrievalEngine`/`VectorStore` gain a `KnowledgeChunkFilter` parameter (ADR-023) supporting workspace, meeting-only, document-only, mixed, and content-type-filtered retrieval. `RetryMeetingProcessingUseCase` gained the same existing-summary guard `RetryDocumentProcessingUseCase` already had (ADR-024), so an indexing-only retry never re-generates a duplicate summary. Benchmarked at 100/500/1000/3000 meetings and a mixed 1500-meeting + 1500-document workspace (`test/performance/meeting_indexing_benchmark_test.dart`). Chunk/K calibration remains a documented estimate, not an on-device tokenizer measurement - ADR-011 still `Pending Validation`. M1.2 is now fully closed for both meetings and documents.
**Git milestone:** Phase 1B tagged `phase-1b`, merged to `main`. Phase 1C not yet committed/tagged - recommended tag `phase-1c` (see this milestone's final report).

### M1.3 — Retrieval-backed workspace chat (generalizes Ask AI) ✅ Done
**Goal:** Replace keyword-overlap Ask AI with real retrieval-backed Q&A across meetings and documents, per ADR-010.
**What ships:** `WorkspaceChatUseCase`, the new chat prompt contract (per `docs/v2/11-ai-architecture.md`), `chat_sessions`/`chat_messages` tables (migration v8, moved up from its illustrative v6 position per ADR-009's renumbering), source citation in answers (parsing the model's "Sources:" convention). `AskAboutMeetingsUseCase` retired **only once this is validated working** (ADR-010's explicit no-regression-window requirement).
**Depends on:** M1.2 (retrieval infra populated and validated).
**Acceptance check:** A question answerable only by combining a meeting and a document returns a correct, source-cited answer. A question with no relevant content returns the honest "couldn't find anything" fallback, not a hallucinated guess. The old meeting-only Ask AI's existing test suite is ported to the new implementation and still passes before the old code path is deleted.
**What actually shipped (Phase 2A):** `WorkspaceChatUseCase` implemented for real, retrieval-backed via `RetrievalEngine` (never bypassed) - never a parsed "Sources:" line as originally sketched here; see ADR-026 for why citations are instead derived directly from the `KnowledgeChunk`s actually retrieved (stronger "no hallucinated citations" guarantee). `chat_sessions`/`chat_messages` ship in migration **v9**, not v8 (v8 was already spent in Phase 1C on `knowledge_chunks` - ADR-025, the same kind of renumbering ADR-019/ADR-021 already established as normal). Progressive token streaming via a new `LlmEngine.answerQuestionStream` (ADR-026), routed through the existing `LlmRequestQueue` unchanged. One chat screen with an in-chat scope selector (ADR-013), reachable from Home and from "Chat about this" actions on meeting/document details. `AskAboutMeetingsUseCase`/the existing Ask AI screen are **kept running unchanged**, exactly as ADR-010's no-regression-window rule requires - not yet retired, per this milestone's explicit instructions.
**Git milestone:** Not yet committed/tagged - recommended tag `phase-2a` (see this milestone's final report).

### M1.4 — Document-scoped chat ✅ Done
**Goal:** A user can chat with one specific document, per FR-28.
**What ships:** The `document` scope of the chat UI (per ADR-013's single-screen-with-scope-selector design) becomes usable, backed by the same `WorkspaceChatUseCase` filtered to one `document_id`.
**Depends on:** M1.3.
**Acceptance check:** A question about content only present in one specific document, asked in that document's scope, is answered correctly and does not leak content from unrelated documents/meetings into the answer.
**What actually shipped (Phase 2A):** Landed in the same pass as M1.3 - `ChatScope.document` narrows retrieval via `KnowledgeChunkFilter.forDocument`, selected from the in-chat scope selector (a document picker, not a separate screen). Additionally, and beyond this section's original scope: `ChatScope.meeting` (not part of `docs/v2/12-database-design.md`'s original three-value `scope` enum - added per ADR-025) absorbs what `AskAboutMeetingsUseCase` does today, per ADR-010, though the old implementation is kept running in parallel rather than retired this pass.
**Git milestone:** Not yet committed/tagged - recommended tag `phase-2a` alongside M1.3 (see this milestone's final report; both landed in the same pass).

**Phase 1 exit criteria:** A user can import a document, get a summary, and ask questions that draw on it individually or alongside their meetings, with citations. Met, pending `AskAboutMeetingsUseCase`'s actual retirement (ADR-010's no-regression-window rule - deliberately not done yet, see the Phase 2A report). Tag: `v2.0.0-alpha.8` in this document's illustrative scheme; actual tag `phase-2a`.

**Depends on:** M1.1, M1.3/M2.1 (the screens being navigated to must exist).

## Phase 3 — Scale, Quality, and Monetization

Corresponds to `docs/v2/07-feature-roadmap.md` Phase 3. Gates general availability, not feature completeness.

### Phase 3A — Production hardening ✅ Done
**Goal:** Not a named milestone in this document's original table - a preparatory engineering-hardening pass run ahead of M3.1's real-device benchmarking, on the reasoning that measuring battery/thermal/latency against a model-lifecycle/retrieval/indexing implementation that still has real, fixable inefficiencies (models never unloaded, a duplicate-load race, a full corpus re-fetch on every retrieval call, no duplicate-indexing guard, a resource-leaking embedding-timeout path) would produce numbers that don't reflect what the app is actually capable of. "The app already works. Now improve stability, memory usage, model lifecycle, cancellation, indexing performance and runtime reliability" (this milestone's own framing) - no new end-user features.
**What shipped:** A centralized `ModelLifecycleManager` (`lib/services/ai/model_lifecycle_manager.dart`) - load-on-demand (unchanged, each engine's own existing lazy `_ensureLoaded`), but now with real unload, a fixed duplicate-load race (an in-flight `Future` is cached and shared, not just the eventual result), reference-counted idle cleanup (5 minutes, `AppConstants.modelIdleUnloadTimeout`), and per-model-kind status reporting, for all three model-backed engines (`LlamaDartLlmEngine`/`LlamaDartEmbeddingEngine`/`WhisperSpeechToTextEngine`) via an additive, optional constructor parameter - zero interface changes, zero fake-test-double changes. `BruteForceVectorStore` gained an in-memory chunk cache (invalidated on every mutation path, including one it doesn't own itself - `IndexingService`'s direct repository delete, via a new `VectorStore.invalidateCache()`) and a bounded top-k selection replacing a full score-and-sort of every candidate - `cosineSimilarity` itself deliberately untouched (ADR-004/the retrieval algorithm are frozen, per this milestone's own "NOT allowed" list). `DefaultIndexingService` gained a duplicate-indexing guard (concurrent calls for the same source coalesce into one result). `LlamaDartEmbeddingEngine.embed`/`embedBatch` now call `cancelGeneration()` on timeout, closing a resource leak `LlamaDartLlmEngine` had already fixed for chat generation but the embedding path never had. A developer-only `AppLogger` (`dart:developer.log`, never analytics/telemetry/network) replaced every scattered `print()` pipeline-failure call. Full detail, including a real deadlock bug caught and fixed during this milestone's own test-writing (a `Future.whenComplete` callback that inadvertently returned a `Future`, making the guard above hang every call, not just concurrent ones), in ADR-029 (docs/v2/implementation/03-decisions.md) and R-21 (docs/v2/implementation/04-risk-register.md).
**Not started this pass:** Real on-device battery/thermal/latency measurement - still M3.1's job, unchanged; this pass only removed the specific inefficiencies that would have skewed those numbers before they're even collected. OCR, accessibility, premium/billing, Play Store publishing - all explicitly out of scope per this milestone's own instructions.
**Git milestone:** Tagged `phase-3a` (bundled with Phase 3B's commit - Phase 3A itself was, per its own instructions, left uncommitted at the time; see Phase 3B's final report for the actual commit/tag).

### Phase 3B — Production-grade performance pass ✅ Done
**Goal:** Not a named milestone in this document's original table - continues Phase 3A's "make the app production-grade" framing with a broader, UI/database/resource-management-focused review ("faster, lighter, smoother and more memory efficient... review the ENTIRE application"), specifically naming app startup, memory, model management, database, search, chat, documents, meetings, RAG, UI rebuilds, background work, logging, and error handling as areas to review. No new end-user features.
**What shipped:** `ChatScreen` no longer rebuilds its whole widget tree once per streamed token - only the message list does, via `Consumer`/`.select()`-scoped regions for the AppBar, scope selector, error banner, and input bar. `ChatHistoryScreen` now builds its conversation list lazily (`ListView.builder`) instead of eagerly constructing every conversation up front. `DocumentRepository.getAll()` no longer fetches each document's full `extracted_text` column on every list load - a column no list view renders, and one that can be an entire document's body. Six dialog-presenting methods across four screens now explicitly dispose their local `TextEditingController`s. Full detail, including what was reviewed and found already adequate (app startup, `HistoryScreen`/`DocumentsScreen`'s existing lazy lists, `AppLogger`'s existing debug gate, `SplashScreen`'s intentional delay), in ADR-030 (docs/v2/implementation/03-decisions.md).
**Not started this pass:** Real on-device measurement of any of the above - still M3.1's job; this pass only removed specific, code-level inefficiencies found by review, honestly disclosed as unmeasured on real hardware rather than accompanied by fabricated numbers. OCR, accessibility, premium/billing, Play Store publishing - all explicitly out of scope, unaffected.
**Git milestone:** Tagged `phase-3b` (see this milestone's final report for the commit hash - this commit also includes Phase 2B and Phase 3A's work, none of which had been committed yet per those milestones' own "do not commit" instructions).

### Phase 4A — Production UX/accessibility pass ✅ Done
**Goal:** Not a named milestone in this document's original table - a UX/accessibility-focused pass run ahead of M3.2's real-device TalkBack audit, mirroring Phase 3A/3B's own "prepare before the real-device milestone runs" precedent. "Review EVERY screen... TalkBack friendliness, Semantics widgets, accessible labels... confirmation dialogs, delete dialogs... production Play Store launch" (this milestone's own framing) - explicitly not premium features, OCR, Billing, an AI model marketplace, or Play Store publishing itself.
**What shipped:** A shared `showDestructiveConfirmDialog()` (`lib/shared/widgets/confirm_dialog.dart`) consolidating five duplicated delete-confirmation `AlertDialog`s and adding error-colored destructive-button styling none of them had; a missing confirmation dialog added to note deletion (the one delete path in the app with none); `Semantics`/tooltip accessible labels added to every icon-only control a full-codebase inventory found unlabeled, plus two touch targets bumped to Android's recommended 48dp; a real, computed WCAG AA contrast failure fixed in `AppTheme.heroGradient` (re-verified across all 12 selectable accent colors); TalkBack speaker labels and a live region added to Chat's message bubbles and streaming indicator; two snackbars that leaked raw exception text replaced with friendly copy. Full detail in ADR-031 (docs/v2/implementation/03-decisions.md).
**Not started this pass:** The real TalkBack-navigation-order device audit and device-measured touch-target/contrast verification M3.2's own acceptance check requires - still gated on a physical Android device this implementation environment doesn't have. Premium/OCR/Billing/marketplace/Play Store publishing - all explicitly out of scope per this milestone's own instructions, unaffected.
**Git milestone:** Tagged `phase-4a` (see this milestone's final report for the commit hash).

### Phase 4B — Production-readiness audit ✅ Done
**Goal:** Not a named milestone in this document's original table - "imagine the application is shipping to thousands of users next week... everything that could create instability, inconsistency, poor UX, release issues, logging problems, recovery problems, lifecycle bugs, configuration mistakes... should now be cleaned up" (this milestone's own framing). ### Phase 5A — Student Toolkit: Image Tools ✅ Done
**Goal:** Not a named milestone in `docs/v2`'s original table - a genuinely new end-user-facing surface (unlike Phase 3A/3B/4A/4B, all hardening/audit passes over existing features), scoped down from an originally four-section "Student Toolkit" (Scanner, Image Tools, PDF Tools, Recent Files) pitched at a CamScanner/Adobe-Scan/SmallPDF caliber bar. Presented to the product owner as an explicit `AskUserQuestion` choice rather than unilaterally descoped; **"Image Tools only, fully polished" was selected** over "everything" or "Image Tools + Scanner." Scanner and PDF Tools are deferred, not cancelled.
**What shipped:** Image Compression (preset mode - 8 presets for Passport/Scholarship/Government Exam/College Admission/Job Application/Visa/Email Attachment/Custom, each resolving to a concrete target-size + max-dimension spec; advanced mode - target KB, quality slider, optional resolution cap, JPG/PNG output) and Image Resize (percentage/width/height modes, aspect-ratio lock, JPG/PNG/WebP output - WebP conversion folded in here rather than a separate screen, since `package:image`'s WebP encoder is lossless-only and so incompatible with the compression tool's target-size search). Both tools share an in-memory-only pipeline (pick → configure → process → preview all stay as `Uint8List`, nothing touches disk until Save/Share) and a real, tested target-size JPEG binary-search-plus-analytical-downscale algorithm. A `toolkit_files` table (migration v11) backs a real Recent Files list (grouped Today/This Week/Older, rename/favorite/delete, reusing `KnowledgeSourceCard`). Home screen gained a dedicated Student Toolkit entry card (separate from the Knowledge Source pillar grid, since toolkit outputs aren't Knowledge Sources) linking to `StudentToolkitScreen`, which links to Compress/Resize/Recent Files. Full detail in ADR-033 (docs/v2/implementation/03-decisions.md).
**A real bug found (and fixed, in-scope) by this phase's own test-writing:** a widget test for the Recent Files rename dialog reproduced a genuine "TextEditingController used after being disposed" crash - fixed in that one screen; the same pattern exists in six other dialogs app-wide (introduced by ADR-030/Phase 3B) and is flagged as a follow-up (R-30, docs/v2/implementation/04-risk-register.md), not fixed here, since touching those five other files is outside "Image Tools only" scope.
**Not started this pass:** Scanner (camera/multi-page scan, crop, perspective correction, PDF generation), PDF Tools (compress/merge/split/rearrange/extract), and Recent Files' scope beyond Image Tools' own outputs - all explicitly deferred, not built as placeholders. Premium/Billing/OCR/cloud sync - out of scope, unaffected, matching every prior phase's exclusions.
**Git milestone:** Not tagged - this phase's own instructions say do not commit/tag; see its final report for the recommended tag once approved.

### Phase 5B — Student Toolkit: Scanner + PDF Tools ✅ Done
**Goal:** Not a named milestone in `docs/v2`'s original table - the two remaining Student Toolkit sections Phase 5A deferred (not cancelled), completing the Product Vision's "complete Offline Productivity Workspace" at the same Adobe Scan/CamScanner/SmallPDF caliber bar, under an explicit "do not refactor the already-reviewed-as-future-proof architecture" constraint.
**What shipped:** Scanner - camera capture (per-shot, reusing `image_picker`) and multi-select gallery import, a reorderable multi-page session (delete/undo-delete/reorder/rotate), a four-corner perspective-correction/crop page editor (real projective-transform math, not a stub), PDF generation, and the full save/share/duplicate/delete/rename set via the existing Recent Files repository. PDF Tools - Compress (5 named presets + Custom, fixed DPI/quality tiers), Merge (PDFs and images, reorderable queue), Split (every-N-pages or tap-to-mark-breakpoints, multiple output files), and Organize (one tool covering both "Extract Pages" and "Reorder Pages" from the product brief, since they're the same underlying transform). All four PDF Tools and Scanner's "Generate PDF" step share one foundation, `PdfPageRenderingService`, built entirely on `pdf`/`printing` - both already-present, permissively-licensed dependencies; a real AGPL-3.0-licensed alternative (`pdf_manipulator`) was researched and explicitly rejected. Full detail in ADR-034 (docs/v2/implementation/03-decisions.md).
**A real technical question resolved before writing any code, not assumed:** Phase 5A's own scope-negotiation flagged "no license-safe native PDF manipulation library exists" as the reason Scanner/PDF Tools were deferred. This phase researched the actual pub.dev landscape, found the `pdf`/`printing` rasterize-and-rebuild path already available with zero new dependencies, and confirmed it before any implementation began - mirroring this project's own ADR-016/R-09 "license-audit before adoption" discipline.
**Not started this pass:** OCR, AI-based document understanding, cloud sync/storage, ads, analytics, premium/licensing/billing, backend - all explicitly out of scope per this phase's own instructions, unaffected. True text-preserving PDF editing (the rasterize-and-rebuild strategy flattens text to images, a disclosed tradeoff - R-33, docs/v2/implementation/04-risk-register.md).
**Git milestone:** Not tagged - this phase's own instructions say do not commit/tag; see its final report for the recommended tag once approved.
