# V2 Architecture Decision Log

This is the single source of truth for every architectural decision governing V2 implementation. `docs/v2/*.md` (frozen product/architecture specification) remains the primary reference for *what* is being built; this log exists because a small number of things were left open in that specification — by design, per its own README, under "explicitly a decision for the product owner, not resolved by this document set" — and cannot stay open once implementation starts. Every decision below either (a) formally accepts a choice `docs/v2` already made, so it's traceable in one place, or (b) resolves something `docs/v2` explicitly deferred. **No decision below changes a data model, a functional requirement, or a module boundary that `docs/v2` stated as settled.** Where a decision corrects an internal inconsistency between two `docs/v2` files, that is called out explicitly as a sequencing/consistency fix, not a redesign.

Status values: `Accepted` (ratified, ready to implement), `Accepted — Pending Validation` (ratified as the default plan, but contingent on a specific upcoming spike/test), `Superseded` (replaced by a later ADR, kept for history).

---

### ADR-001 — Reuse existing Clean Architecture / Riverpod / single composition root
**Reason:** `docs/v2/10-system-architecture.md` mandates this; it already survived one real backend swap (`flutter_llama` → `llamadart`) at the cost of one provider re-point.
**Alternatives considered:** None seriously — re-architecting a working, proven layering to build new features on top of it would be pure risk with no offsetting benefit.
**Tradeoffs:** None material; this is the cheapest possible choice.
**Status:** Accepted. **Date:** 2026-07-27.

### ADR-002 — Feature-first module boundaries for Documents and Chat
**Reason:** `docs/v2/10-system-architecture.md`'s proposed folder layout (`lib/features/documents/`, `lib/features/chat/`) mirrors the existing `meetings/`, `ask/`, `search/` convention exactly.
**Alternatives considered:** A single monolithic "workspace" feature folder. Rejected — would violate the existing "one feature, one concern" convention for no benefit.
**Tradeoffs:** None material.
**Status:** Accepted. **Date:** 2026-07-27.

### ADR-003 — Embedding model approach: `llama.cpp`-based first, separate runtime as fallback
**Reason:** `docs/v2/11-ai-architecture.md` names this the largest unvalidated assumption in the whole plan and specifies a feasibility spike before any Document/Chat UI work begins.
**Alternatives considered:** (a) Commit to a separate ONNX/TFLite embedding runtime up front, skipping the spike — rejected, since it pays the higher integration cost (new native dependency, new ProGuard rule, new download path) even if the cheaper option would have worked. (b) Use a cloud embedding API — rejected outright, violates NFR-17 (no new network edges).
**Tradeoffs:** The spike (see Milestone M1.0 in [01-master-roadmap.md](01-master-roadmap.md)) costs real calendar time before any user-visible Document/Chat progress is possible. Accepted as the cheaper failure mode compared to committing to the wrong integration and discovering it late, which is exactly what happened with `flutter_llama` in V1.
**Resolution (M1.0 spike, 2026-07-29):** Option 1 confirmed feasible by direct inspection of `llamadart` 0.8.17's source - `LlamaEngine.embed()`/`embedBatch()` exist, work against a normal (non-special-mode) loaded context, and route through the same worker-isolate infrastructure the existing chat engine already uses. Implemented as `LlamaDartEmbeddingEngine` (`lib/services/ai/llamadart_embedding_engine.dart`), a second `LlamaEngine` instance loaded with `embeddinggemma-300M` rather than the chat model. Full evidence trail, including what was and wasn't validated on a real device (this spike ran in a desktop dev environment with no on-device execution available), in [../implementation/spikes/m1-0-embedding-spike.md](spikes/m1-0-embedding-spike.md).
**Status:** Accepted. **Date:** 2026-07-29 (resolution date; originally logged 2026-07-27).

### ADR-004 — Vector storage: `sqlite-vec` extension first, brute-force Dart cosine similarity as fallback
**Reason:** `docs/v2/14-rag-architecture.md`'s stated preference — keeps the project on SQLite-only storage (no second database engine), matching the existing FTS5 decision's own reasoning.
**Alternatives considered:** A dedicated vector database/ANN index (e.g., an HNSW library) — rejected as over-engineering relative to the corpus sizes this product is scoped for (NFR-16: hundreds to low thousands of chunks, not millions).
**Tradeoffs:** Brute-force fallback has real, unbenchmarked latency risk on low-end devices (flagged in [04-risk-register.md](04-risk-register.md)); accepted because at this scale it is a legitimate engineering choice, not a compromise, per `docs/v2/14`'s own reasoning.
**Resolution (M1.0 spike, 2026-07-29):** Option 1 (`sqlite-vec`) is **not usable** - it requires `package:sqlite3`'s direct FFI bindings (confirmed via `llamadart`'s own example, which depends on `sqlite3`/`sqlite_vector`), a completely different Flutter database package from `package:sqflite`, which this app's entire database layer is built on. Adopting it would mean replacing the app's whole database access layer, far outside this milestone's scope. Option 2 (brute-force Dart cosine similarity) is the implementation - `BruteForceVectorStore` (`lib/services/retrieval/vector_store.dart`), benchmarked at 100/500/1000/3000-document synthetic corpora in `test/performance/indexing_benchmark_test.dart` (see the spike report for the numbers and their caveats).
**Status:** Accepted. **Date:** 2026-07-29 (resolution date; originally logged 2026-07-27).

### ADR-005 — Polymorphic content association via two nullable FKs + CHECK constraint
**Reason:** `docs/v2/12-database-design.md` specifies this pattern for both `summaries.document_id`/`meeting_id` and `knowledge_chunks`. Keeps real foreign keys and real cascade deletes rather than an unenforced `(content_type, content_id)` pair.
**Alternatives considered:** A fully separate `document_summaries` table (avoids conditional reads on `summaries`, at the cost of a near-duplicate repository and duplicated query logic). Rejected in favor of the shared-table approach specified in `docs/v2/12`, since the duplication cost was judged higher than the conditional-read cost.
**Tradeoffs:** Every future query against `summaries` or `knowledge_chunks` must account for which FK is populated. Accepted as the smaller of two real costs, not a free choice.
**Status:** Accepted. **Date:** 2026-07-27.

### ADR-006 — Chat history persisted locally by default
**Reason:** `docs/v2/17-privacy.md` distinguishes chat (the user's own questions/answers about their own content) from the old Conversation Translator's deliberate in-memory-only design (someone else's spoken words). Persisting locally, deletable, never transmitted, is the more useful default.
**Alternatives considered:** In-memory-only chat, matching the Translator pattern exactly. Rejected — would make chat feel disposable in a way meetings/documents don't, undermining the "workspace" framing.
**Tradeoffs:** More data at rest for a device thief/unlocked-phone scenario to potentially see (see [16-security.md](../16-security.md)'s disclosed at-rest-encryption gap, unchanged by this decision). Accepted as consistent with how every other content type in the app already behaves.
**Status:** Accepted. **Date:** 2026-07-27.

### ADR-007 — Monetization: one-time Play Billing purchase (Option B), not subscription
**Reason:** `docs/v2/18-subscription-model.md`'s recommendation; preserves the "no accounts, no backend, ever" constraint without nuance.
**Alternatives considered:** Paid-app-only (Option A, no freemium) — kept as a documented fallback if a fair free/Pro split proves hard to define. Subscription via Play Billing (Option C) — explicitly rejected per `docs/v2/18`'s own reasoning: technically backend-free but undermines the "no recurring cost" differentiation this product is built around.
**Tradeoffs:** Weaker long-term revenue durability than a subscription model would offer (flagged as a business risk in [04-risk-register.md](04-risk-register.md)); accepted because it's the only option that doesn't quietly walk back a constraint the product's own positioning depends on.
**Status:** Accepted. **Date:** 2026-07-27.

### ADR-008 — LLM request queue: FIFO baseline, foreground requests pause (not just queue behind) background jobs
**Reason:** `docs/v2/11-ai-architecture.md` explicitly left "should foreground preempt background" as an open question "not resolved here." Implementation cannot proceed with an undefined queue-priority behavior — a user's first chat interaction getting silently stuck behind an unattended background summarization job is a first-impression risk severe enough to require a default now rather than being discovered during QA.
**Alternatives considered:** Plain FIFO with no distinction between foreground/background requests (the literal baseline `docs/v2/11` described) — rejected as the sole behavior because it does not protect the user-facing chat experience from being blocked by invisible background work. A full priority queue with preemption of an *in-flight* generation — rejected as unnecessary complexity: the existing engine can't be safely interrupted mid-token-stream without going through the same `cancelGeneration()` path already used for timeouts, and doing that routinely (rather than only on genuine stalls) risks wasting completed background work for a marginal responsiveness gain.
**Decision, precisely:** The queue is FIFO. Before *starting* a queued background job (meeting/document summarization), the queue checks whether a foreground request (chat) is pending or in flight; if so, the background job waits until the foreground queue is empty. A background job already *in flight* when a foreground request arrives is not interrupted — it runs to completion or its existing 45-second stall timeout, whichever comes first — avoiding the complexity and waste of mid-generation preemption while still preventing background work from ever being *queued ahead of* a user actively waiting.
**Tradeoffs:** A foreground chat request can still wait up to ~45 seconds behind an already-in-flight background job in the worst case. Accepted as a bounded, known worst case (identical to today's single-stall-timeout bound) rather than an unbounded one.
**Status:** Accepted (resolves an explicitly open question in `docs/v2/11-ai-architecture.md`; does not alter its architecture). **Date:** 2026-07-27.

### ADR-009 — Migration sequencing correction: FTS5-for-existing-content ships before Documents/Chunks/Chat tables
**Reason:** **This is a genuine inconsistency between two frozen documents, not a redesign.** `docs/v2/07-feature-roadmap.md` places the search-parity fix (summaries/notes become searchable) in Phase 0, before Documents exist. `docs/v2/12-database-design.md`'s illustrative migration order places all FTS5 work last (v7), after `documents` (v4), `knowledge_chunks` (v5), and `chat_sessions`/`chat_messages` (v6) — which would make Phase 0's search fix impossible to ship on schedule. The table *designs* in `docs/v2/12` are unchanged by this ADR; only the *order* migrations are applied in is corrected.
**Resolved migration sequence for implementation:**
- **v4** — FTS5 virtual table(s) + sync triggers for existing content only (`meetings`, `transcripts`, `summaries`, `action_items`, `notes`). Ships in Phase 0.
- **v5** — `documents` table + `summaries.document_id` (nullable) + `meeting_id` becomes nullable + CHECK constraint. Ships in Phase 1.
- **v6** — `knowledge_chunks` table + indexes. Ships in Phase 1.
- **v7** — FTS5 extended to include `documents`. Ships in Phase 1/2.
- **v8** — `chat_sessions` + `chat_messages` tables + indexes. Ships in Phase 1/2.
**Alternatives considered:** Leave `docs/v2/12`'s literal v4–v7 order and delay the Phase 0 search fix until Phase 1 instead. Rejected — it would mean Phase 0 doesn't actually ship what `docs/v2/07` says it ships, silently breaking the phase plan's own "each phase produces a working, testable application" requirement.
**Tradeoffs:** None material — this is a pure ordering fix.
**Status:** Accepted. **Date:** 2026-07-27.

### ADR-010 — Ask AI's fate: meeting-scoped Q&A is absorbed into the generalized Chat module
**Reason:** **Resolves a real conflict between two frozen documents.** `docs/v2/03-prd.md`'s module table states "Offline AI Chat (generalizes existing Ask AI)" as settled. `docs/v2/10-system-architecture.md` leaves whether `ask_about_meetings_use_case.dart` is retired or kept as an explicit "implementation decision for Phase 1, not resolved here." Implementation needs one answer.
**Decision:** The existing `ask/` feature's meeting-only Q&A becomes a special case of the new Chat module — a chat session scoped to one meeting, using the same retrieval-backed `WorkspaceChatUseCase` filtered to a single `meeting_id` rather than a parallel, separately-maintained code path. `AskAboutMeetingsUseCase`'s keyword-overlap implementation is retired once the retrieval-backed replacement is validated (Milestone M1.3), not before — the existing feature keeps working on the existing implementation until its replacement is proven, avoiding a period with no working Ask AI at all.
**Alternatives considered:** Keep `AskAboutMeetingsUseCase` permanently as a separate, simpler, meeting-only implementation alongside the new general retrieval system. Rejected — two independently-maintained answer-generation code paths for what is conceptually one capability (answer a question from relevant content) is exactly the kind of unnecessary duplication `docs/v1`'s own architecture principles argue against.
**Tradeoffs:** Meeting-only Q&A briefly depends on retrieval infrastructure landing (Milestone M1.2) before it can be upgraded, rather than being independently improvable. Accepted — the existing implementation is not removed until the replacement is ready, so there is no functional regression window.
**Status:** Accepted. **Date:** 2026-07-27.

### ADR-011 — RAG context budget: chunk size and K calibrated to fit the 2048-token window
**Reason:** **This is the one item in this log that qualifies as "a critical bug that makes implementation impossible" as written.** `docs/v2/14-rag-architecture.md` proposes chunks of 300–500 tokens with K=4–6 retrieved chunks — at the high end, 3,000 tokens of chunk content alone against a 2048-token *total* context that must also hold the system prompt, the question, and the response budget. As specified, this cannot fit.
**Decision:** Starting parameters for implementation: chunk size ~200–250 tokens, K=3. This budgets roughly 600–750 tokens for retrieved content, leaving headroom for system prompt (~150–250 tokens depending on the chat prompt contract), question, and a meaningful response budget (the existing `answerQuestion` pattern already reserves `maxTokens: 300` for the reply). These are **starting values to be validated empirically during Milestone M1.2/M1.3**, not final tuned constants — real chunk/question/answer token counts on real content should adjust them, but they must never be chosen without checking the arithmetic against the model's actual context size again.
**Alternatives considered:** Ship the original 300–500/K=4–6 parameters and let it fail/truncate unpredictably in production. Rejected outright — this is not a product decision to make, it's a hard numeric constraint. Increase the model's context size instead of shrinking chunks/K — deferred to Phase 3's configurable-larger-model work; not assumed available for the Phase 1 default model.
**Tradeoffs:** Smaller K means less cross-source synthesis per answer than `docs/v2/14`'s original framing implied — a real quality reduction from what was originally described, disclosed here rather than discovered by users.
**Partial resolution (M1.0/M1.2, 2026-07-29):** `DefaultChunkingService` (`lib/services/retrieval/chunking_service.dart`) implements a 900-character (paragraph/sentence-boundary-aware) chunk budget, derived from this ADR's 200-250 token target via the commonly-cited ~4-characters-per-token average for English prose - a documented estimate, not a measurement, since no on-device tokenizer execution was available to this spike (see [../implementation/spikes/m1-0-embedding-spike.md](spikes/m1-0-embedding-spike.md)). K stays at 3 (`RetrievalEngine`'s default), the conservative end of the original 4-6 range. **Still Pending Validation**: re-run this calibration against `LlamaEngine.tokenize()`'s real output once on-device execution is possible, before M1.3 locks in a chat prompt budget against it.
**Status:** Accepted — Pending Validation (empirical tuning in M1.3, char-per-token estimate not yet measured). **Date:** 2026-07-27.

### ADR-012 — `decisions` table: remains permanent schema-compatibility dead weight, not removed or resurrected
**Reason:** `docs/v2/07-feature-roadmap.md` Phase 0 lists this as a decision to make, not a default to inherit silently again. **Status:** Accepted. **Date:** 2026-07-27.

### ADR-013 — Chat UI: one screen with a scope selector, not three separate routes
**Reason:** Implementation-level UI consolidation. `docs/v2/10-system-architecture.md` specifies a `chat/` module with `presentation/{screens,providers}` generically — it does not mandate three separate routes for document-scoped, workspace-scoped, and general chat, and `docs/v2/08-functional-requirements.md`'s FR-28/29/31 describe three *capabilities*, not three *screens*. **This does not change any functional requirement, data model, or module boundary** — `ChatSession.scope` (`general`/`workspace`/`document`, per `docs/v2/12-database-design.md`) already models exactly this as data, not as separate routes.
**Decision:** One chat screen. A scope selector (default "All" = workspace-scoped) lets the user narrow to a specific document or meeting. Reduces route count, provider count, and empty/error-state surface area to build and test, without removing any capability.
**Alternatives considered:** Three separate routes/screens as originally sketched during the pre-freeze design review. Rejected as unnecessary navigation complexity for a distinction most users won't naturally think in terms of.
**Tradeoffs:** A single screen's provider carries slightly more conditional logic than three simple ones would. Accepted — less total surface area to build, test, and maintain.
**Status:** Accepted. **Date:** 2026-07-27.

### ADR-014 — Navigation shell: Documents and Chat added via a secondary nav layer, not by expanding the primary 4-tab bar
**Reason:** `docs/v2` does not specify how `AppShell`'s existing four-destination bottom nav (Home/History/Search/Settings) accommodates two new top-level modules. V1 already has a real, user-reported history of nav-surface crowding (the "Record Meeting" shown three times bug). Left unresolved, this risks repeating that mistake at a larger scale.
**Decision:** Documents and Chat are reached from Home (as prominent entry points, similar to how Record/Import already work today) and from a new items in the Settings-adjacent or a slide-out surface, rather than adding a fifth/sixth item to the persistent bottom bar. Exact visual treatment is a UX/UI task (see [02-backlog.md](02-backlog.md), Epic: Navigation & UX Integration), not fixed here — this ADR only commits to *not* expanding the primary tab bar past four items.
**Alternatives considered:** Add Documents and Chat as two more persistent bottom-nav tabs (six total). Rejected — matches the exact anti-pattern already fixed once in V1 (too many competing entry points for the same or adjacent actions).
**Tradeoffs:** Documents/Chat are one tap less discoverable than a persistent tab would make them. Accepted as the safer default given V1's own precedent.
**Status:** Accepted. **Date:** 2026-07-27.

### ADR-015 — OCR: out of scope for V2; documents without an extractable text layer surface a clear error, not silent failure
**Reason:** Not addressed anywhere in `docs/v2`. Scanned/image-based PDFs (common in legal/professional documents — exactly the personas this product targets) have no text layer for the planned extraction libraries to find.
**Decision:** V2 does not add OCR. `DocumentTextExtractionService` (per `docs/v2/10-system-architecture.md`) detects when extraction yields empty/near-empty text and sets the document to `error` with an explicit, honest message ("No readable text found in this file — scanned/image-only PDFs aren't supported yet") rather than silently producing an empty or garbage summary.
**Alternatives considered:** Add on-device OCR now (a real, heavier addition — another native dependency, another battery/performance cost, another model). Rejected for V2 on cost/scope grounds; recorded as a strong Phase-3-or-later candidate in [../20-future-roadmap.md](../20-future-roadmap.md)'s spirit (this ADR does not edit that frozen file, just notes the connection).
**Tradeoffs:** A real, disclosed limitation for exactly the professional/legal persona segment this product is positioned toward. Accepted as an honest, visible gap rather than a silent one.
**Status:** Accepted. **Date:** 2026-07-27.

### ADR-016 — Document-parsing library selection requires a license audit before adoption
**Reason:** Not addressed anywhere in `docs/v2`. Several popular open-source PDF/DOCX parsing libraries carry copyleft licenses (GPL/AGPL) that can impose obligations incompatible with a closed-source commercial app.
**Decision:** No PDF/DOCX parsing dependency is adopted without an explicit license check (permissive license required: MIT/BSD/Apache-2.0-class) as a gating step in Milestone M1.1, logged as part of that milestone's completion evidence.
**Alternatives considered:** Defer the check until legal review before launch. Rejected — discovering a licensing blocker after the dependency is already load-bearing in the codebase is far more expensive to unwind than checking first.
**Tradeoffs:** None material — this is a cheap, one-time check.
**Status:** Accepted. **Date:** 2026-07-27.

### ADR-017 — Embedding-model download is deferrable, not a mandatory onboarding gate
**Reason:** Not addressed anywhere in `docs/v2`. The existing onboarding flow already mandates a two-model download before the app is usable at all; a real, prior user complaint in this project was about first-run download friction. Adding a third mandatory model (if the M1.0 spike requires one) worsens exactly that problem.
**Decision:** If an embedding model is required (ADR-003), its download is **not** added to the mandatory onboarding gate. A user can use Meetings (and, once shipped, basic Search) immediately after the existing two-model onboarding download. The embedding model download is offered the first time the user attempts to import a document or use workspace/general chat, using the same download-progress UX pattern already shipped for the existing models.
**Alternatives considered:** Add it to the mandatory onboarding gate for consistency. Rejected — trades a small consistency benefit for a real, disproportionate first-run conversion cost.
**Tradeoffs:** A user's first document-import or chat attempt may require an additional wait they weren't warned about during onboarding. Mitigated by the same clear progress/explanation UX already used elsewhere, surfaced at the moment it's actually needed instead of upfront.
**Status:** Accepted. **Date:** 2026-07-27.

### ADR-018 — Migration v6 rebuilds `content_fts` instead of `ALTER TABLE ADD COLUMN`
**Reason:** Not addressed anywhere in `docs/v2` or in this log prior to Phase 1A implementation — the original v6 migration (written during Phase 1A) added `content_fts.document_id` via `ALTER TABLE content_fts ADD COLUMN document_id UNINDEXED`, which passed code review but failed at runtime on every test that opens a fresh database: SQLite FTS5 virtual tables do not support `ALTER TABLE ... ADD COLUMN` at all (raises "virtual tables may not be altered"), unlike ordinary tables. This was caught by `flutter test`, not `flutter analyze` (a schema-level runtime error, not a static one), and broke effectively the entire suite (every test that touches the database) until fixed.
**Decision:** Migration v6 drops `content_fts` and recreates it as a `CREATE VIRTUAL TABLE ... USING fts5(...)` with `document_id` present in the column list from the start, then re-runs all five of migration v4's original backfill `INSERT ... SELECT` statements (meetings/transcripts/summaries/action_items/notes) plus two new ones (documents/document_text) — dropping the table discards every row it held, so the backfill must restore all of it, not just the new content types.
**Alternatives considered:** None — this is not a design choice but a correction of a factual error about FTS5's capabilities; there is no working alternative that keeps the `ALTER TABLE` approach.
**Tradeoffs:** None material for a fresh install (this is `onCreate`'s v6 step). For a real upgrade from an installed v5 database, the rebuild is a few extra `INSERT ... SELECT` passes over data that was already being backfilled anyway — negligible at this product's scale (NFR-16).
**Related fix, same migration:** A second, independent bug in the same migration was caught by the new document-search test coverage this milestone added: `documents_fts_ad` (the AFTER DELETE trigger on `documents`) only deleted the `content_type = 'document'` (title) row for a deleted document, leaving its `content_type = 'document_text'` (extracted-text) row permanently orphaned in the index — a deleted document's body text remained searchable forever. Fixed by widening that one trigger's `DELETE` to `content_type IN ('document', 'document_text')`, since both content types share the same `source_id` (the document's own id).
**Status:** Accepted. **Date:** 2026-07-28.

### ADR-020 — Meeting indexing deferred; retrieval infrastructure built content-type-agnostic to allow it later at low cost
**Reason:** `docs/v2/01-master-roadmap.md`'s M1.2 acceptance check calls for both meetings and documents to be automatically indexed. The Phase 1B implementation prompt's explicit component list, however, named `DocumentIndexer` specifically (not a meeting equivalent), and wiring meeting indexing into the pipeline would additionally require adding `MeetingStatus.indexing` and updating every exhaustive `switch` over `MeetingStatus` (`meeting_list_tile.dart`, `meeting_details_screen.dart`) - a wider blast radius than this milestone's stated scope.
**Decision:** `KnowledgeChunk`, `IndexingService`, `ChunkingService`, `EmbeddingEngine`, and `VectorStore` are all content-type-agnostic by construction (driven by `ContentType` plus exactly one of `meetingId`/`documentId`, never a documents-only assumption baked into their contracts). Only `DocumentIndexer` (the document-side orchestration wrapper) was built and wired into `ProcessNewDocumentUseCase`/`RetryDocumentProcessingUseCase` this milestone. A `MeetingIndexer` mirroring it, plus `MeetingStatus.indexing`, is deferred to a follow-up pass, not blocked on any further infrastructure work.
**Alternatives considered:** Wire meeting indexing now, matching the roadmap's full M1.2 scope literally. Rejected for this pass specifically because it was not in the prompt's explicit "Implement" list and touches a wider surface (`MeetingStatus`'s call sites) than a scope this document set can silently expand without being asked.
**Tradeoffs:** M1.2 is not fully closed by this milestone as originally scoped in `docs/v2/implementation/01-master-roadmap.md` - existing `ready` meetings, and newly-transcribed ones, are not yet indexed or retrievable. Disclosed in [10-v2-progress.md](10-v2-progress.md) and [11-gap-analysis.md](11-gap-analysis.md) rather than silently left unaddressed.
**Status:** Accepted. **Date:** 2026-07-29.

### ADR-021 — `knowledge_chunks` gains `content_type` + `source_id` (migration v8), scoped by source rather than owner alone
**Reason:** ADR-020 deferred meeting indexing but built `IndexingService`/`KnowledgeChunk` content-type-agnostic in anticipation of it. Wiring up actual meeting indexing this milestone exposed a real schema gap that anticipation didn't cover: a document has exactly one indexable prose source (its extracted text), so Phase 1B's `deleteForMeeting`/`deleteForDocument` (owner-scoped delete-before-reinsert) was safe. A meeting has *several* independently-changing prose sources sharing one `meeting_id` — its transcript, its summary, and each of its notes. An owner-scoped delete-before-reinsert would wipe every sibling source's chunks each time just one of them (e.g. one edited note) was re-indexed, directly violating the Phase 1C requirement that "the retrieval index must automatically stay consistent... no orphan embeddings, no duplicate chunks, no manual repair required." This was caught during design, before `MeetingIndexer` was written against the old schema, by direct analogy to a real Phase 1A bug (ADR-018's `documents_fts_ad` trigger only ever clearing one of `documents`' two `content_fts` content types and permanently orphaning the other).
**Decision:** Migration v8 (`lib/database/migrations/v8.dart`) rebuilds `knowledge_chunks` (SQLite cannot `ALTER TABLE ADD COLUMN` a `NOT NULL` column with a per-row-computed default — same create-copy-drop-rename pattern as ADR-018/summaries) adding `content_type TEXT NOT NULL` and `source_id INTEGER NOT NULL`. Every pre-existing (Phase 1B, documents-only) row backfills as `content_type = 'document', source_id = document_id` — not a guess, the only value Phase 1B's code ever wrote. `KnowledgeChunkRepository.deleteForSource(ContentType, int sourceId)` replaces `deleteForMeeting`/`deleteForDocument`; `IndexingService.indexContent` now requires `sourceId` and deletes-before-reinserts scoped to `(content_type, source_id)`, never the owning `meeting_id`/`document_id` alone. `meeting_id`/`document_id` are kept unchanged for `getForMeeting`/`getForDocument` and `ON DELETE CASCADE` when the owner itself is deleted.
**Alternatives considered:** A separate `note_chunks`/`transcript_chunks` table per content type. Rejected — reintroduces exactly the "shape of the data is identical, don't parallel-table it" problem ADR-005 already resolved once for `summaries`; `content_fts.content_type`/`source_id` already proves the single-table-plus-discriminator shape works for this exact scoping need. Keeping the owner-scoped delete and instead having each call site pre-fetch and re-insert sibling sources' chunks. Rejected — pushes correctness onto every caller instead of the schema, the same class of mistake ADR-018's trigger bug already demonstrated is easy to get wrong.
**Tradeoffs:** A second schema migration touching this table within two milestones (v7 then v8). Accepted — the alternative (shipping the owner-scoped design into a real meeting-indexing rollout) risks silent data loss (orphaned/wrongly-deleted chunks) in production, which no amount of test coverage after the fact fully closes off; catching it at the schema-design stage is strictly cheaper.
**Status:** Accepted. **Date:** 2026-07-29.

### ADR-022 — `MeetingIndexer` added alongside `DocumentIndexer`; `IndexingService` stays the one shared generic layer
**Reason:** Phase 1C's explicit instruction: "If `DocumentIndexer` has become generic enough, rename it appropriately. If not, create a higher-level orchestration service that both Meeting and Document indexing reuse. Avoid duplicate pipelines." `DocumentIndexer` orchestrates exactly one content source (a document's whole extracted text) through the shared `IndexingService`; a meeting has two pipeline-produced sources to orchestrate (transcript, summary) plus a third, interactively-mutated one (notes) that doesn't fit the "index once when the pipeline finishes" shape at all.
**Decision:** `IndexingService` (already content-type-agnostic per ADR-020) remains the single shared chunk→embed→store implementation both sides call. A new `MeetingIndexer` (`lib/features/meetings/meeting_indexer.dart`) is added, mirroring `DocumentIndexer`'s exact shape (flip owner to `indexing`, index each source, flip to `ready`/`error`) but calling `IndexingService.indexContent` twice — once for the transcript, once for the summary, each under its own `(ContentType, sourceId)` — rather than once for a single blob. `DocumentIndexer` is left as-is, not renamed: renaming it to something owner-agnostic would be cosmetic only, since it still legitimately only ever handles one content source per call, unlike `MeetingIndexer`. Notes are deliberately indexed outside both indexers, individually at mutation time, by `NotesController` calling `IndexingService` directly — they're not produced once by a pipeline stage, they're added/edited/deleted interactively for the life of the meeting.
**Alternatives considered:** A single `ContentIndexer` class parameterized to handle both documents and meetings' multi-source orchestration. Rejected — the two owners' indexable-source *shapes* genuinely differ (one source vs. two-plus-interactive-notes), so a unified orchestrator would need owner-type branching internally, which is exactly the duplication-by-a-different-name this instruction warns against; two thin, shape-appropriate orchestrators sharing one real implementation layer (`IndexingService`) is the actual point of no-duplication here. Folding meeting indexing into `GenerateMeetingSummaryUseCase` directly. Rejected — mirrors `DocumentIndexer`'s own established reasoning for staying a separate pipeline step: keeps the already-shipped, already-tested summary-generation contract untouched.
**Tradeoffs:** Two indexer classes instead of one, with near-identical status-flipping boilerplate. Accepted — the boilerplate is the cheap part; the actual indexing logic (chunk/embed/store) has exactly one implementation (`IndexingService`), which is what "avoid duplicate pipelines" is actually protecting against.
**Status:** Accepted. **Date:** 2026-07-29.

### ADR-023 — `KnowledgeChunkFilter` value object, not a family of retrieval methods, for scoped search
**Reason:** Phase 1C's RETRIEVAL requirement: `RetrievalEngine` must support workspace, meeting-only, document-only, mixed, top-K, metadata-filtered, and content-type-filtered retrieval - seven retrieval "shapes" through one contract, not seven near-duplicate methods (`retrieveMeetingsOnly`, `retrieveDocumentsOnly`, ...).
**Decision:** A new `KnowledgeChunkFilter` value object (`lib/services/retrieval/knowledge_chunk_filter.dart`) carries `contentTypes`/`ownerType`/`meetingId`/`documentId` and exposes a single `matches(KnowledgeChunk)` predicate. `VectorStore.similaritySearch` and `RetrievalEngine.retrieve` both gain an optional `filter` parameter defaulting to `KnowledgeChunkFilter.workspace` (matches everything - today's behavior is unchanged when the parameter is omitted). `BruteForceVectorStore` applies it as an in-memory predicate before cosine-scoring candidates, consistent with ADR-004's brute-force approach; a future `sqlite-vec`-backed store could translate the same filter object into a `WHERE` clause instead, without `RetrievalEngine`'s or its callers' contracts changing.
**Alternatives considered:** Separate typed methods per retrieval shape on `RetrievalEngine`. Rejected - doesn't compose (a caller wanting "meeting-only AND content-type=summary" would need a method per combination, an exponential blow-up as filter dimensions are added) and every existing call site would need updating regardless of which shape it uses. A raw SQL/`WHERE`-clause string parameter. Rejected - couples every caller to `BruteForceVectorStore`'s specific storage engine, defeating the whole point of `VectorStore` being an interface (ADR-004).
**Tradeoffs:** None material - purely additive; every existing `retrieve()`/`similaritySearch()` call site compiles unchanged since `filter` has a default.
**Status:** Accepted. **Date:** 2026-07-29.

### ADR-024 — `RetryMeetingProcessingUseCase` checks for an existing summary before regenerating it (mirrors the Phase 1B `RetryDocumentProcessingUseCase` fix)
**Reason:** Phase 1C's KEEP EVERYTHING SYNCHRONIZED requirement lists "Summary regenerated" as a change the retrieval index must stay consistent with, and requires retries to never produce duplicate/orphaned data. `RetryMeetingProcessingUseCase` (pre-existing, pre-Phase-1C) called `GenerateMeetingSummaryUseCase` unconditionally on every retry with a transcript present, regardless of whether a summary already existed. Once indexing became a third pipeline stage, a meeting that failed at *indexing* (transcript and summary both already persisted) would, on retry, regenerate a second summary row before indexing ran again — the exact duplicate-row/orphaned-data failure mode this milestone's synchronization requirement explicitly rules out. This mirrors a bug already found and fixed on the document side in Phase 1B (`RetryDocumentProcessingUseCase`, same root cause).
**Decision:** `RetryMeetingProcessingUseCase` now takes `SummaryRepository` and checks `getForMeeting(meetingId) == null` before calling `GenerateMeetingSummaryUseCase`; if a summary already exists, that stage is skipped and only `MeetingIndexer` runs. Applies the identical fix shape already proven for `RetryDocumentProcessingUseCase`.
**Alternatives considered:** Add an existing-summary guard inside `GenerateMeetingSummaryUseCase` itself. Rejected - same reasoning as the Phase 1B fix: `GenerateMeetingSummaryUseCase`'s own contract (always generate a fresh summary when called) is correct and used elsewhere (e.g. `ProcessNewMeetingUseCase`'s first-time path) exactly as-is; the guard belongs at the retry call site, which is the only caller for which "already exists" is a valid reason to skip.
**Tradeoffs:** None material.
**Status:** Accepted. **Date:** 2026-07-29.

### ADR-025 — `chat_sessions`/`chat_messages` ship in migration v9, not v8; `ChatScope` gains a fourth value (`meeting`) beyond `docs/v2/12-database-design.md`'s original three
**Reason:** ADR-009's illustrative sequence numbered chat's tables as v8, but Phase 1C's ADR-021 already spent v8 on `knowledge_chunks.content_type`/`source_id` - the same "the illustrative number is already gone by the time this milestone actually starts" situation ADR-019 resolved for `knowledge_chunks` itself. Separately, Phase 2A's own instructions require three selectable scopes - "Entire Workspace, One Meeting, One Document" - but `docs/v2/12-database-design.md`'s `chat_sessions.scope` only ever specified `general | workspace | document`. Meeting-scoped chat was previously served by the separate `AskAboutMeetingsUseCase` (ADR-010), not by a `ChatScope` value, since at the time `docs/v2` was frozen the generalized Chat module wasn't expected to need meeting-level granularity of its own - ADR-010 only committed to *absorbing* Ask AI's capability into Chat "as a special case," without specifying the scope value it would use to do so. Implementing ADR-010's absorption now surfaces that the scope enum itself needs a fourth value to represent it.

Rejected - directly contradicts ADR-010's already-accepted decision that meeting-only Q&A becomes "a chat session scoped to one meeting" inside the generalized module, not a permanently separate capability. A `content_type`/`content_id` polymorphic pair instead of three nullable columns. Rejected for the same reason ADR-005 already rejected it for `summaries`/`knowledge_chunks`: loses real foreign keys and real cascade deletes.
**Tradeoffs:** `chat_sessions`' CHECK constraint is one clause longer than `docs/v2/12`'s original two-column design implied. Accepted - trivial cost for schema-enforced correctness.

### ADR-026 — Chat streaming via an `onToken` callback through the existing `LlmRequestQueue`, not a `Stream<String>` return type; citations are derived from the chunks actually retrieved, not parsed from the model's own text
**Reason:** Phase 2A requires streamed (or at least progressive) responses and requires citations with "no hallucinated citations." Two implementation questions `docs/v2/11-ai-architecture.md` left at spec-level rather than code-level: how streaming interacts with the single-flight `LlmRequestQueue` (ADR-008), and how literally to take that document's "a trailing 'Sources:' line the UI can extract" suggestion.
**Decision (streaming):** `LlmEngine` gains `Future<String> answerQuestionStream(String context, String question, {void Function(String token)? onToken})`: still a `Future<String>` returning the complete answer (so `LlmRequestQueue.enqueue<T>`'s existing `Future<T> Function() run` contract needs no changes at all), but invoking `onToken` synchronously for each token/delta as `llamadart`'s own `engine.create(...)` stream produces them, before the method's future resolves. `LlmRequestQueue`'s single-flight guarantee (ADR-008) is preserved exactly as-is: the queue still awaits the whole `run()` call before considering the engine free, so this is real token-by-token UI streaming layered on top of the existing one-request-at-a-time discipline, not a second concurrent-generation path. `WorkspaceChatUseCase.call` forwards its own `onToken` parameter straight through, and separately exposes the `LlmQueueRequest`'s assigned id via an `onRequestQueued(int id)` callback (fired synchronously, before the request's `run()` executes) so a caller (`ChatController`) can capture the id for [ADR-027](#adr-027)'s cancellation path without a second round-trip through the queue.
**Decision (citations):** Citations shown to the user are built directly from the actual `KnowledgeChunk`s `RetrievalEngine.retrieve` returned and that were actually included in the prompt's context - resolved to a human label (`"<Meeting title> — Transcript"`, `"<Meeting title> — Summary"`, `"<Meeting title> — Notes"`, or `"<Document title>"`) via `MeetingRepository`/`DocumentRepository`, deduplicated, and persisted onto the assistant `ChatMessage.sourcesJson` at answer time. The model is *not* asked to produce a parseable "Sources:" line, and no citation is ever derived from parsing the model's free-text output.
**Alternatives considered (streaming):** A `Stream<String>` return type on `LlmEngine`/threaded through the queue as a new request shape. Rejected - `LlmRequestQueue`'s entire contract (`Future<T> Function() run`, "exactly one request in flight," a `Future<T> result` on the handle) is built around request/response, not long-lived streams; introducing a second submission shape purely for chat would duplicate the queue's own bookkeeping (pending/running/cancel state) for no benefit, since the callback approach achieves the same UI-visible streaming behavior without touching the queue's contract at all. **Alternatives considered (citations):** Following `docs/v2/11-ai-architecture.md`'s literal "Sources:" line suggestion, parsed out of the model's response. Rejected - a small on-device model asked to self-report which sources it used can misreport, omit, or invent one (the model has no ground-truth access to what was actually retrieved, only to text a prompt handed it), which is precisely the "no hallucinated citations" failure mode this milestone explicitly rules out. Deriving citations from the actual retrieved set instead makes a hallucinated citation structurally impossible: a chip can only ever reference a chunk that was genuinely retrieved and genuinely included in the prompt.
**Tradeoffs:** A citation chip can be shown even if the model's answer didn't actually end up using that particular chunk (recall bias: every retrieved chunk that fit in context is credited, not just the ones the model's answer demonstrably drew from). Accepted - the alternative (trusting the model's self-report) has a strictly worse failure mode (fabrication) for a feature whose explicit requirement is "no hallucinated citations," and over-crediting a genuinely-retrieved, genuinely-in-context source is a materially smaller honesty gap than inventing one that was never retrieved at all.
**Status:** Accepted. **Date:** 2026-07-30.

### ADR-027 — Chat cancellation: queue-level cancel for a not-yet-started request, UI-level "abandon" (not true mid-generation preemption) for one already running
**Reason:** Phase 2A requires "Cancellation" as a supported UX state. ADR-008 already established, deliberately, that a request already in flight against the shared `llama.cpp` engine cannot be interrupted through `LlmRequestQueue` - only a still-queued (not yet started) request can be cancelled; an in-flight one runs to completion or its own 45-second stall timeout, whichever comes first. A chat Cancel button needs to do *something* useful in both cases, not just the queued case.
**Decision:** `ChatController` calls `LlmRequestQueue.cancel(requestId)` (captured via ADR-026's `onRequestQueued` callback) when the user taps Cancel. If the request was still queued, this succeeds outright and the turn ends with `LlmQueueCancelledException` surfaced as a normal "cancelled" state, exactly like any other queue cancellation. If the request had already started running (the far more likely case in practice, since a chat request is `isForeground: true` and therefore usually starts almost immediately per ADR-008's priority rule), `cancel()` returns `false` - `ChatController` treats this as a **UI-level abandon**: it sets a local `_abandoned` flag and immediately returns to an idle state, then `WorkspaceChatUseCase.call`'s own `isAbandoned` callback parameter (checked once the LLM call actually resolves, whatever it resolves with) reads that same flag - when true, the use case discards the answer itself (returns `null`, never calls `_persist`, never touches `session.updatedAt`), so an abandoned answer is never written to `chat_messages` at all, not merely hidden in the UI. The actual native generation keeps running in the background exactly as ADR-008 already specifies, until it finishes (its result is simply discarded, by the use case, once it arrives) or hits the existing 45-second stall timeout. This is not a new capability bolted onto the engine - it is the same "the engine must always be freed for the next caller, eventually" guarantee ADR-008 already makes, viewed from the chat UI's perspective rather than the queue's.
**Alternatives considered:** Add true mid-generation preemption (a new `LlmEngine.cancelGeneration()`-triggering path reachable from the queue). Rejected for the same reason ADR-008 already rejected it: the existing `cancelGeneration()` mechanism exists specifically for the stall-timeout case, and routing routine user-initiated cancellation through it as well risks wasting engine cycles on a generation that was seconds from finishing, for a marginal responsiveness gain over simply hiding it - real added complexity for no capability `docs/v2` actually requires. Block the Cancel button entirely once generation has started. Rejected - directly contradicts this milestone's explicit "Cancellation" requirement; a user should never be stuck staring at a spinner with no way back to idle.
**Tradeoffs:** A "cancelled" chat turn does not truly stop consuming the shared engine's cycles until the underlying generation naturally finishes or times out - the engine is not available for the *next* request any sooner than it otherwise would have been. Accepted - identical, already-accepted tradeoff to ADR-008's own; this ADR does not make it worse, it only extends the same accepted behavior to a new caller (chat) instead of introducing a new one.
**Status:** Accepted. **Date:** 2026-07-30.

### ADR-028 — Phase 2B Knowledge Source abstraction: one shared `KnowledgeSourceCard` widget, content-type exposure added to the existing FTS5 repository (no new migration), `SearchMeetingsUseCase` renamed to `SearchWorkspaceUseCase`, `chat_sessions.is_pinned` in migration v10
**Reason:** Phase 2B's six numbered requirements repeatedly point at the same underlying gap: `MeetingListTile`/`DocumentListTile` are near-duplicate widgets (the latter's own doc comment already said so), `ContentSearchRepository` already indexes per-content-type match info (`content_fts.content_type`) but discarded it before this pass, `SearchMeetingsUseCase` already searches both meetings and documents despite its name (its own doc comment called this rename "planned"), and "pin conversation" is the one genuinely new Workspace Chat capability requested (rename/delete/recent/resume already shipped in Phase 2A) - none of the rest ("no new AI capability") needed schema changes.

All six "Knowledge Source card" display fields (AI Summary available, Indexed status, Processing status, Last updated, Size, Searchable indicator) are derived from fields `Meeting`/`Document` already have (`status == ready` implies summary-available and searchable simultaneously, since this app's pipeline order guarantees summary-then-index-then-ready; `updatedAt`; `fileSizeBytes`/`durationSeconds`) - zero new queries, zero new database fields.
**Decision (search content-type exposure):** `ContentSearchRepository.search()`'s query changes from `SELECT DISTINCT meeting_id, document_id` to also select `content_type`, populating two new `ContentSearchResults` fields (`meetingContentTypes`/`documentContentTypes`, `Map<int, Set<String>>`) - additive, so every existing caller/test reading only `.meetingIds`/`.documentIds` is unaffected. No migration: `content_fts.content_type` has existed since migration v4 (ADR-009) and was already being written by every insert trigger, just never selected back out.
**Decision (search use case rename):** `SearchMeetingsUseCase` → `SearchWorkspaceUseCase` (`lib/features/search/search_workspace_use_case.dart`), `searchMeetingsUseCaseProvider` → `searchWorkspaceUseCaseProvider`. Same public shape (`Future<SearchResults> call(String)`), `SearchResults` gains the same additive content-type maps. `SearchScreen` rebuilt: results grouped into Documents/Meetings sections; the old meeting-source-only filter chips (All/Favorites/Recorded/Imported - a `HistoryScreen`-only concept that had leaked into Search) are replaced with a genuine Workspace filter (All/Meetings/Documents/Notes), where Notes is a cross-cutting content-type filter (`meetingContentTypes[id]?.contains('note')`), not an owner-type partition like Meetings/Documents are.
**Decision (pin conversation):** Migration **v10** (`lib/database/migrations/v10.dart`) adds `chat_sessions.is_pinned INTEGER NOT NULL DEFAULT 0`. `ChatSession` gains `isPinned` (`@Default(false)`), read/written through the existing `toMap`/`fromMap`/`update()` path with no repository interface changes. `chatSessionListProvider` re-sorts pinned-first on top of the repository's existing most-recently-updated-first query (a presentation-layer sort, not a second query or a repository-level `ORDER BY is_pinned` - keeps `SqfliteChatSessionRepository.getAll()`'s contract identical to every other repository's). `ChatHistoryScreen` groups sessions under "Pinned"/"Recent" headers with a pin/unpin `PopupMenuItem` alongside the existing rename/delete ones. `ChatScreen`'s empty state also gained scope-aware quick-action chips (canned questions like "Summarize this meeting") that call the same `ChatController.sendMessage` a typed question would - no new AI capability, per this milestone's explicit constraint.

Rejected - the data already existed; adding a second representation of the same fact would be pure duplication. Keeping `SearchMeetingsUseCase`'s name unchanged (avoiding the rename's mechanical blast radius across `app_providers.dart`/`search_providers.dart`/its test file). Rejected - the rename was already anticipated by that class's own doc comment and gap-analysis §3, is purely mechanical (three call sites, one test file, all updated in this pass), and Phase 2B's requirement #6 ("Knowledge Source abstraction... avoid feature-specific logic where a shared abstraction exists") argues directly against leaving a workspace-wide use case named after only one of the things it searches. Sorting pinned conversations via `ORDER BY is_pinned DESC, updated_at DESC` in the repository's own query instead of a presentation-layer sort. Rejected as unnecessary complexity for a `getAll()` result set that's already small (every conversation a single-device user has ever had) and already fully loaded into memory by the caller.

**Status:** Accepted. **Date:** 2026-07-31.

### ADR-029 — Phase 3A production hardening: a centralized `ModelLifecycleManager` (attach/beginUse/endUse, not a typed engine dependency), an additive `VectorStore.invalidateCache()`/in-memory chunk cache, a bounded top-k selection replacing full-sort, a per-(contentType, sourceId) duplicate-indexing guard, and a fixed embedding-timeout resource leak
**Reason:** Phase 3A's own framing is explicit: "The app already works. Now improve stability, memory usage, model lifecycle, cancellation, indexing performance and runtime reliability... No new end-user features." Reading the existing AI-engine/retrieval/indexing code against that bar surfaced five concrete, fixable gaps, none of which needed a redesign: (1) `LlamaDartLlmEngine`/`LlamaDartEmbeddingEngine` each load their `LlamaEngine` once and never unload it - a model stays native-resident for the app's entire lifetime once first used, even if idle for hours. (2) Both engines' `_ensureLoaded()` had a duplicate-load race: two callers arriving before the first load finished each saw `_engine == null` and started an independent `loadModelSource` call. (3) `BruteForceVectorStore.similaritySearch` re-fetched and BLOB-decoded every row from `knowledge_chunks` on every single call - every chat message, every search - even when nothing had changed since the last call, and scored+fully-sorted every candidate even though only the top `k` (typically 3, ADR-011) were ever read. (4) Two concurrent `IndexingService.indexContent` calls for the exact same `(contentType, sourceId)` (e.g. a double-tapped Retry) could both run their delete-then-insert sequence concurrently, since the delete happens synchronously up front but the insert only after real async chunking/embedding work - leaving duplicate chunk rows for one source. (5) `LlamaDartEmbeddingEngine.embed`/`embedBatch` wrapped the native call in `.timeout(_stallTimeout)` but, unlike `LlamaDartLlmEngine._collect`'s already-correct pattern, never called `engine.cancelGeneration()` on timeout - a stalled embed call kept running in the native worker with no way to reclaim it.
**Decision (ModelLifecycleManager):** A new `lib/services/ai/model_lifecycle_manager.dart` centralizes unload/idle-cleanup/reference-counting/status-reporting for all three model-backed engines (`ModelKind.llm`/`embedding`/`speechToText`). Deliberately **not** a typed dependency on `LlmEngine`/`EmbeddingEngine`/`SpeechToTextEngine` or any concrete engine class - an engine that wants to be managed calls `manager.attach(kind, unload: ..., statusOf: ...)` once at construction (plain closures, not an interface), then wraps every public method body in `manager.beginUse(kind)`/`manager.endUse(kind)` (a `try/finally` pair). This keeps every existing fake test double (`FakeLlmEngine`, `FakeEmbeddingEngine`, `FakeSpeechToTextEngine` - `test/test_helpers/fake_ai_engines.dart`) and the `LlmEngine`/`EmbeddingEngine`/`SpeechToTextEngine` interface contracts themselves completely untouched; only the three real, `llamadart`/`whisper_flutter_new`-backed implementations opt in, via a new **optional, nullable** constructor parameter (`ModelLifecycleManager? lifecycleManager`) that defaults to `null` (fully backward-compatible: any existing call site or test that constructs these engines without the new parameter behaves exactly as before). Reference counting is what `beginUse`/`endUse` provide "for free": the idle-unload timer only starts once the ref count returns to zero, so a model already serving a request - however long that request takes - is never unloaded out from under it. `WhisperSpeechToTextEngine` attaches too (for consistent status reporting across all three engines, per this milestone's explicit "reporting model status" requirement) but with a no-op `unload` - `whisper_flutter_new`'s `Whisper.transcribe` already spawns a fresh `Isolate.run(...)` per call that loads the native model, transcribes, and tears the isolate (and every native resource it holds) down when the call completes, so there is nothing persistent this class could unload even if it wanted to; Whisper already had the "never resident longer than actively needed" property Phase 3A asks for, before this milestone touched it.
**Decision (idle timeout + wiring):** `AppConstants.modelIdleUnloadTimeout` = 5 minutes (new constant, `lib/core/constants/app_constants.dart`) - long enough that reading a just-generated summary or thinking about a follow-up chat question doesn't trigger a reload on the very next action, short enough that an idle-in-background app doesn't keep a combined ~1.4GB (LLM + embedding model) resident indefinitely. One `modelLifecycleManagerProvider` (`lib/providers/app_providers.dart`, disposed via `ref.onDispose(manager.dispose)`, same convention as `llmRequestQueueProvider`) is watched by `speechToTextEngineProvider`/`llmEngineProvider`/`embeddingEngineProvider` and passed into each engine's constructor - one shared manager instance for the app's lifetime, not one per engine.
**Decision (duplicate-load race fix):** Both `LlamaDartLlmEngine`/`LlamaDartEmbeddingEngine`'s `_ensureLoaded()` now cache the **in-flight `Future<LlamaEngine>` itself** (a new `_loading` field), not just the eventual `_engine` result - a second caller arriving before the first load finishes awaits that same in-flight future instead of starting a second `loadModelSource` call. `unload()` (new public method on both classes) calls `LlamaEngine.unloadModel()` (confirmed reusable - `llamadart` 0.8.17's own `loadModel` doc comment: `'Model is already loaded. Call unloadModel() first.'` implies a fresh `loadModelSource` works again afterward) and clears `_engine`, so the next call transparently reloads exactly like the very first call ever made.
**Decision (retrieval cache):** `VectorStore` gains one new method, `void invalidateCache()` (additive - `BruteForceVectorStore` is the only implementation in this codebase, so no other implementer needs updating). `BruteForceVectorStore` now keeps an in-memory `List<KnowledgeChunk>? _cache` of every chunk (embeddings already BLOB-decoded); `add`/`addAll` clear it themselves (they perform the mutation), and `IndexingService`'s two call sites that delete `knowledge_chunks` rows **directly** via `KnowledgeChunkRepository.deleteForSource` (bypassing the store, since that delete has always lived at the repository layer, not the store's `add`/`addAll` pair) now also call `_vectorStore.invalidateCache()` right after - the one mutation path the store has no other way to observe. A cache miss (`null`) is both the initial state and the state right after any invalidation, so a stale read is structurally impossible: every mutation path either clears the cache itself or is required to call `invalidateCache()`.
**Decision (bounded top-k):** `BruteForceVectorStore.similaritySearch`'s candidate scoring no longer allocates one `MapEntry` per candidate and fully sorts all of them before taking the first `k` - a new `_topK` helper keeps a bounded buffer of at most `k` entries (ascending by score), only touched when a new candidate's score beats the current worst kept one: O(candidates × k) with a small, fixed allocation instead of O(candidates) allocation + O(candidates log candidates) sort. `cosineSimilarity` itself is **unchanged** - its own doc comment already explains why it deliberately computes the full formula rather than assuming pre-normalized inputs reduce to a bare dot product, and that reasoning is exactly the kind of "changing the retrieval algorithm" this milestone's rules forbid touching.
**Decision (duplicate-indexing guard):** `DefaultIndexingService` gains an in-flight map (`Map<String, Future<void>> _inFlight`, keyed by `'$contentType:$sourceId'`). A second `indexContent` call for a key already in flight awaits and returns the **same** `Future` the first call already started, rather than beginning a second delete-then-insert sequence - the source ends up indexed exactly once, not duplicated and not silently skipped (the caller still gets a real result once indexing genuinely completes). A call for a *different* key, or the same key once the prior call has already finished, is unaffected - proven by the existing `indexing_service_concurrency_test.dart` suite (different-source concurrent cases) continuing to pass unchanged, plus two new same-source tests added this pass.
**Decision (embedding-timeout leak fix):** `LlamaDartEmbeddingEngine.embed`/`embedBatch` now call `engine.cancelGeneration()` in their `on TimeoutException` handler before rethrowing `LlmTimeoutException` - the exact fix `LlamaDartLlmEngine._collect`/`_collectStreaming` already had, now applied to the embedding engine for the first time (it was the one AI-engine call path in this codebase without it).
**Decision (logging):** A new `AppLogger` (`lib/core/logging/app_logger.dart`) wraps `dart:developer.log()` - developer-only, never analytics/telemetry/a network call (consistent with `docs/v2/17-privacy.md`'s zero-transmission commitment). Replaces every scattered `print()`/`// ignore: avoid_print` pipeline-failure log call across `MeetingIndexer`, `DocumentIndexer`, `TranscribeMeetingUseCase`, `GenerateMeetingSummaryUseCase`, `SummarizeDocumentUseCase`, `ExtractDocumentTextUseCase`, and `NotesController` with a consistent, named, leveled (`info`/`warning`/`error`) call.
**Alternatives considered:** Making `beginUse`/`endUse` typed methods on `LlmEngine`/`EmbeddingEngine`/`SpeechToTextEngine` themselves (a cleaner-looking call site). Rejected - would force every existing fake test double to implement lifecycle methods it has no use for, breaking `FakeLlmEngine`/`FakeEmbeddingEngine`/`FakeSpeechToTextEngine` and every test that constructs them, for a milestone whose own rules require preserving backward compatibility; the callback-registration (`attach`) pattern achieves the identical runtime behavior with zero interface changes. Routing `IndexingService`'s delete-for-source calls through a new `VectorStore.removeForSource` method instead of keeping the direct repository call plus a separate `invalidateCache()` signal. Rejected - `DefaultIndexingService`'s constructor already requires `KnowledgeChunkRepository` (used by 13+ existing test files and `app_providers.dart`); routing delete through the store instead would leave that field genuinely unused, triggering the analyzer's `unused_field` diagnostic (this project's "0 issues" bar) unless the constructor signature itself changed, which would ripple through every one of those call sites for a purely internal refactor with no externally-visible benefit. Real `sqlite-vec`/a genuinely different retrieval algorithm/reduced-precision (float32) embeddings for a smaller cache footprint. All explicitly out of scope per this milestone's own "NOT allowed" list (ADR-004 stays the standing decision on vector storage) and not attempted.
**Tradeoffs:** `ModelLifecycleManager`'s idle-unload behavior means a model that was unloaded after 5 idle minutes pays a full reload (and, if the on-device file cache evicted it, a re-download-skip-but-re-load) cost on the next call after a long pause - accepted as the entire point of the milestone (memory freed when genuinely idle, reloaded transparently when needed again), same "one-time cost, then cached" shape the existing model-download convention already has. The duplicate-indexing guard coalesces a second concurrent call into the first one's result rather than queuing it to run again afterward with potentially newer content - in the narrow window where two calls for the same source arrive concurrently with genuinely different text (not the same-content-retry case this guard is actually aimed at), the second caller's specific text isn't separately re-indexed; accepted as a materially smaller risk than the duplicate-chunk-rows bug being fixed, and a caller that edits content again after this narrow window (e.g. `NotesController.edit` on a subsequent, non-concurrent call) still re-indexes normally. None of the real `llamadart`/`whisper_flutter_new`-backed engine changes (unload, race-fix, cancelGeneration-on-timeout) can be unit-tested in this implementation environment - no on-device execution is available (the same standing limitation ADR-003's spike and R-18/R-19 already disclose); `ModelLifecycleManager` itself is fully unit-tested in isolation (pure Dart, no native dependency) since its logic is what's actually novel here, and the engine-side changes are small, targeted, code-reviewable diffs mirroring an already-proven pattern (`LlamaDartLlmEngine._collect`'s existing `cancelGeneration()`-on-timeout call) rather than new untested logic.
**A real bug caught and fixed during this milestone's own test-writing, not before (see R-21, docs/v2/implementation/04-risk-register.md):** the duplicate-indexing guard's first version deadlocked every single `indexContent` call, not just concurrent ones - `.whenComplete(() => _inFlight.remove(key))`'s arrow-function callback returned `Map.remove`'s result, which for a `Map<String, Future<void>>` is the removed *value itself* (the very `Future<void>` `whenComplete` was attached to); `Future.whenComplete` awaits whatever its callback returns if that return value is itself a `Future`, so the future was made to wait on itself. Every prior `await` inside `_indexContent` completed normally (confirmed via targeted diagnostic instrumentation: chunking, embedding, and the final `VectorStore.addAll` all genuinely finished) - only the outermost `Future` `indexContent()` itself returns never resolved, which is why this surfaced as three unrelated-looking test files (`chat_controller_test.dart`, `notes_controller_test.dart`, `indexing_service_concurrency_test.dart`) all timing out at exactly the default 30-second per-test limit rather than as an obvious compile-time or logic error. Fixed by switching to a block-bodied callback (`.whenComplete() { _inFlight.remove(key); }`), whose implicit `void` return can't be mistaken for something to await. A new, tightly-timed (5-second explicit `Timeout`) regression test was added specifically to catch a reintroduction of this exact bug class fast, rather than relying on the generic 30-second default to eventually flag it as "some test somewhere hung."
**Status:** Accepted. **Date:** 2026-08-03.

### ADR-030 — Phase 3B production-readiness pass: scoped `Consumer`/`.select()` rebuilds in `ChatScreen`, a lazily-built `ChatHistoryScreen`, `DocumentRepository.getAll()` excluding `extracted_text`, and explicit disposal for every dialog-local `TextEditingController`
**Reason:** Phase 3B's own framing: "make the application production-grade on real Android devices... faster, lighter, smoother and more memory efficient... review the ENTIRE application." A systematic pass across the app-startup/memory/database/chat/UI/background-work areas that milestone names surfaced four concrete, fixable, measurable-by-code-review (not by a real device, which this environment doesn't have) issues; everywhere else reviewed either already matched the target bar (model lifecycle - ADR-029; retrieval caching/top-k - ADR-029; `HistoryScreen`/`DocumentsScreen` already used `ListView.separated`; `main.dart`/`SplashScreen` startup path was already minimal) or is explicitly out of this environment's reach (real-device battery/thermal/memory measurement - M3.1's job, [08-quality-gates.md](08-quality-gates.md) §6-7).
**Decision (ChatScreen rebuild scoping):** `ChatScreen`'s `build()` no longer calls `ref.watch(chatControllerProvider)` for the whole `ChatState` - previously, every streamed token (`ChatState.streamingText` changing potentially many times per answer) rebuilt the entire screen: `AppBar` (title, both `IconButton`s), the scope selector, and the input bar, none of which depend on `streamingText`. Each independently-varying region is now its own `Consumer` scoped via `chatControllerProvider.select(...)` to only the fields it actually reads (AppBar title → `session?.title`; new-chat button → `hasActiveSession`; scope selector → `hasActiveSession` gate, full state only while pre-session, when nothing is ever streaming anyway; error banner → `error`; input bar → a `(isSending, canStartTurn)` record). Only `_ConversationBody`'s own `Consumer` still watches the full state - the one region that legitimately needs to redraw every token. The scroll-to-bottom side effect moved from an inline `build()`-time comparison (which required watching full state at the top level to run at all) to `ref.listen<ChatState>`, which doesn't itself cause a rebuild.
**Decision (ChatHistoryScreen lazy list):** Replaced a plain `ListView(children: [...for loops over pinned/recent...])` - which built every conversation's `Card`/`ListTile`/`PopupMenuButton` up front regardless of scroll position - with `ListView.builder` over a flattened list of header/session rows (a small `_Row` sealed union). Matches NFR-16's "hundreds to low thousands" corpus-scale expectation; a user's chat history has no natural upper bound the way a single meeting's action items do.
**Decision (DocumentRepository.getAll() column trimming):** `getAll()` now selects every `documents` column except `extracted_text` - the only two callers (`documentListProvider`/`DocumentsScreen`, `chatEligibleDocumentsProvider`/the in-chat document picker) render list tiles (title/status/size/updated), never the extracted text, but the previous query fetched it anyway, and a document's full extracted text can be the entire body of a PDF/DOCX - real, unbounded-per-row I/O paid on every single list load for data never used. `getById`/`getByIds` (the only paths that ever need the real text - document detail view, search results) are unchanged. `Document.fromMap` already treats a missing map key the same as a genuinely-null column, so this doesn't change the model's shape, only what `getAll()` specifically populates.
**Decision (controller disposal):** Six dialog-presenting methods (`HomeScreen._editDisplayName`, `DocumentDetailsScreen._renameDocument`, `ChatHistoryScreen._rename`, `MeetingDetailsScreen`'s rename/add-action-item/add-or-edit-note dialogs) each created a `TextEditingController` local to the method and never called `.dispose()` on it - not a growing leak (each becomes normal garbage once the method returns and nothing references it), but not the resource-cleanup convention Flutter's own `ChangeNotifier`-derived controllers are documented to expect either. Each now wraps its `showDialog` call in `try/finally`, reading any `controller.text` the caller still needs before the `finally` block disposes it.
**Decision (reviewed, no change needed):** App startup (`main.dart`) already only does what's required to render the first frame (Hive box open, database open, both genuinely blocking since settings/routing depend on them) - no AI model loads eagerly (confirmed lazy since ADR-029). `SplashScreen`'s fixed 900ms delay is an intentional branding pause, not a performance defect - left untouched, since removing deliberate UX timing without being asked would exceed this milestone's "not about adding new features" framing in the opposite direction (removing an existing, working, intentional behavior). `AppLogger`'s existing `info`-only `kDebugMode` gate (ADR-029) was re-examined against this milestone's "production builds should never spam logs" requirement and found already sufficient: `warning`/`error` (the rare, failure-path calls, never a hot loop) stay always-on so a developer attaching DevTools to a release build can still see them, and `dart:developer.log()` itself is a documented no-op sink without an attached observatory/DevTools session in release mode - not equivalent to `print()`'s unconditional stdout write, so "always-on but only rare failure paths call it" does not constitute log spam.
**Alternatives considered:** Splitting `ChatScreen` into many more granular `Consumer`s than the six regions actually implemented (e.g. a separate `Consumer` per `AppBar` action). Rejected as over-engineering relative to the actual rebuild-frequency problem (only `streamingText`/`messages` change at token-frequency; every other field changes at most once per user action) - six regions already isolate every field that changes at a different cadence from every other. A `CustomScrollView`/`SliverList` instead of `ListView.builder` for `ChatHistoryScreen`. Rejected - `ListView.builder` already provides the lazy-building property this change needed; a `Sliver`-based rewrite would add real complexity (custom `SliverPersistentHeader`s for the section labels) for no additional benefit at this list's shape (two flat, unnested sections). Removing `SplashScreen`'s delay or gating `AppLogger.warning`/`error` behind `kDebugMode` too. Rejected per the "reviewed, no change needed" decision above - both were deliberate, already-reasoned prior choices, not oversights this pass discovered.
**Tradeoffs:** `ChatScreen`'s six `Consumer` regions are more verbose than a single `ref.watch` call was - accepted as the standard, unavoidable cost of scoped rebuilds in Riverpod (there is no way to get independent rebuild regions from one `build()` method without splitting it). `DocumentRepository.getAll()` and `getById`/`getByIds` now have a subtly different contract (one excludes `extractedText`, the others don't) where they didn't before - accepted since it's documented in both the method's own doc comment and this ADR, and no existing call site was affected (verified: only two callers, neither reads `extractedText` from a `getAll()` result, confirmed by grep and by the existing/unchanged `document_repository_test.dart` suite still passing).
**Real-device readiness (explicit, honest statement per this milestone's own instruction not to fabricate benchmarks):** None of the changes in this ADR have been measured on real hardware - this implementation environment has no physical Android device, matching every prior phase's identical disclosed limitation (R-04/R-18/R-19). What's verified here is code-level: the rebuild-scoping change is proven by existing widget tests continuing to pass unchanged (same rendered output, fewer widget-tree reconciliations - Flutter's own profiler, not available here, would be needed to quantify "fewer" precisely); the lazy-list change is proven by a new test asserting only a bounded subset of 200 seeded rows are actually built (`chat_history_screen_test.dart`); the column-trimming change is proven by a new repository test asserting `getAll()` omits the field while `getById`/`getByIds` don't. Whether any of this is perceptible on a real low-end/mid-range/flagship device - the milestone's own explicit question - is not answered by this pass and requires M3.1's real-device benchmarking, unchanged from ADR-029's identical disclosure.
**Status:** Accepted. **Date:** 2026-08-05.

### ADR-031 — Phase 4A production UX/accessibility pass: a shared destructive-confirm dialog, a missing note-delete confirmation, TalkBack labels for icon-only controls, a WCAG-AA contrast fix to `AppTheme.heroGradient`, and TalkBack speaker/live-region labels in Chat
**Reason:** Phase 4A's own framing: "review EVERY screen... TalkBack friendliness, Semantics widgets, accessible labels... loading states, empty states, error states, confirmation dialogs, delete dialogs" for production Play Store readiness. `docs/v2` never addressed accessibility at all before this pass (the exact gap M3.2, [01-master-roadmap.md](01-master-roadmap.md), exists to close) - a full-codebase inventory (every screen, every `IconButton`, every `showDialog`/`showSnackBar` call site) was run first (not sampled) to ground this pass in what actually exists, per the same discipline every prior phase's ADR has followed, rather than guessing at likely problem spots.
**Decision (shared destructive-confirm dialog):** A new `showDestructiveConfirmDialog()` (`lib/shared/widgets/confirm_dialog.dart`) replaces five near-identical, independently-written `AlertDialog`s (meeting delete, document delete, chat conversation delete, `KnowledgeSourceCard`'s swipe-to-delete, and the new note delete below) that each built their own `TextButton('Cancel')` + `FilledButton('Delete')` pair. Two problems in one fix: duplicated widget code (the mandatory "No duplicated widgets" rule) and a real visual-consistency gap the inventory surfaced - every "Delete" button used the theme's default (primary-colored) `FilledButton` styling, visually indistinguishable from a routine "Save" button. The shared helper styles the destructive action with `ColorScheme.error`/`onError` - a pairing Material 3's `ColorScheme.fromSeed` derives specifically to meet WCAG AA against each other, so this is a contrast improvement as well as a visual one, not just a color swap.
**Decision (note-delete confirmation, a real gap, not just inconsistency):** The inventory found `MeetingDetailsScreen`'s note deletion (`_NotesTab`) had **no confirmation dialog at all** - the only delete path in the entire app that didn't - a real accidental-data-loss risk given every other destructive action (meeting, document, chat conversation, and even the swipe-to-delete `KnowledgeSourceCard` pattern) confirms first. Fixed using the same shared helper.
**Decision (TalkBack labels for icon-only controls):** The inventory found zero uses of `Semantics`/`semanticLabel`/`Tooltip` anywhere in `lib/` before this pass - `IconButton(tooltip: ...)` (which doubles as its accessible label) was the only convention in place, and three `IconButton`s were missing even that (search's clear button, the recording title-save button, the meeting audio play/pause toggle - now labeled, the last dynamically per playing/paused state). Five custom icon-only tappables (`RecordingScreen`'s `_RoundIconButton` used for pause/resume/stop/mark, `AppShell`'s FAB-style record shortcut, `AppearanceScreen`'s accent-color swatches, `HomeScreen`'s avatar/edit-display-name button) had no accessible name of any kind - a screen-reader user would hear only "button" or nothing distinguishing them. Each now carries an explicit `Semantics(button: true, label: ...)`; the accent-color swatches read from a new `AccentColors.names` map (color hex → human name, e.g. "Purple") rather than duplicating a name list next to the widget. `AppShell`'s bottom-nav tabs gained `Semantics(selected: isSelected)` so TalkBack announces which tab is currently active, not just its name. Two color swatches were also bumped from 44dp to 48dp (Android's recommended minimum touch target); the home-screen avatar button from 40dp to 48dp likewise.
**Decision (WCAG AA contrast - `AppTheme.heroGradient`, a real, computed failure, not a suspicion):** The inventory flagged the dark theme's manually-overridden surface colors (ADR-009's original ... no, not applicable here - the surfaces themselves, per `app_theme.dart`'s own existing doc comment) as worth re-checking, plus the `heroGradient` used behind three hero elements (Home's Record card, its glowing record shortcut, the onboarding mic icon) as a non-flat background white text/icons sit on. Computed WCAG relative-luminance contrast ratios (implemented directly against the actual `ColorScheme`/gradient values, via a throwaway Dart script, not a browser tool) found: every `onSurface`/`onSurfaceVariant`-against-surface pairing already passes AA comfortably (9.85:1-16.31:1, since only the surfaces were darkened, never the text colors, which can only improve contrast) - no change needed there. But `heroGradient`'s original lighter two-thirds (`primary` lightened 12%, and `primary` itself) measured only **1.58:1 and 1.70:1** against the solid-white text/icons placed directly over them - a severe, confirmed WCAG AA failure (need 4.5:1), not a marginal one; only the gradient's darkest stop (6.99:1) passed. Root cause: Material 3's dark-scheme `primary` is, by design, a light pastel accent tone (meant to sit *on* a dark surface, not serve as a background *for* white text) - lightening it further made this worse, and even the unlightened `primary` alone still failed (1.70:1). Fixed by darkening all three gradient stops (`Color.lerp(primary, Colors.black, [0.60, 0.68, 0.78])` in place of the original `[lightened 12%, primary, darkened 55%]`) - re-verified via `test/core/theme/app_theme_test.dart` against **every one of the app's 12 selectable accent colors** (not just the default), for both solid white and the dimmer `Colors.white70` subtitle color, all 24 cases passing comfortably (5.15:1-16.9:1 range). Still a visible diagonal gradient, just shifted into a tonal range this app's actual text content can sit on safely everywhere along it, not just at its darkest end.
**Decision (Chat: speaker labels and a streaming live region):** Two Chat-specific TalkBack gaps the inventory's "Citation UX"/"Streaming UX" review areas surfaced: (1) `_MessageBubble` conveyed who sent a message (user vs. assistant) only via bubble alignment/background color - both invisible to a screen reader, which reads widgets in tree order with no sense of "this one is right-aligned." Fixed with one `Semantics(label: '$speaker said: ...')` per bubble (folding in source-citation names too), with `ExcludeSemantics` on the visual subtree beneath it so the underlying `SelectableText`/citation `Chip`s aren't announced a second time, redundantly. (2) `_StreamingBubble` updated its visible text token-by-token with no announcement at all - TalkBack only speaks a node when it first appears or is told content changed. Fixed with `Semantics(liveRegion: true, label: ...)`, so an in-progress answer (or the "Assistant is thinking" state before the first token arrives) is actually announced as it changes, not silently rendered.
**Decision (fixed two raw-exception snackbars):** `BackupScreen`/`ExportScreen` interpolated a caught exception's `toString()` directly into a user-facing `SnackBar` (e.g. "Could not create backup: SocketException: ..."), inconsistent with every other error message in the app's established friendly-copy convention. Replaced with plain, actionable sentences; the underlying exception is simply discarded (`catch (_)`) rather than logged, matching this codebase's existing "developer-only logging, never surfaced to end users" posture (ADR-029) for a path this shallow (a snackbar has no stack-trace-worthy failure mode here).
**Decision (reviewed, no change needed):** `SearchScreen`'s no-results state already distinguishes "Search your workspace" (pre-query) from "No matches... in this filter" (query with zero results, filter-aware) - already meets this pass's "no-result experience" objective without changes. `EmptyState`/`AiPipelineFallback` (the app's existing shared loading/empty/error-state widgets, used consistently by every screen already) were reviewed and found to already satisfy this pass's "consistent loading/empty/error state" objective - no parallel widget was introduced.
**Alternatives considered:** Clamping `MediaQuery.textScaler` app-wide to prevent large system font sizes from affecting layout. Rejected - this would *reduce* accessibility (a low-vision user's chosen text size being silently overridden is the opposite of what an accessibility pass should do); the inventory found no case of a `Text`/ellipsis combo sitting inside a fixed-height container that would clip under scaling, so no defensive clamp was warranted. Adding a text shadow to the hero-gradient white text as a cheaper alternative to redesigning the gradient's stops. Rejected - WCAG's contrast formula doesn't recognize shadows as a mitigation, and a computed pass/fail number is a stronger, testable guarantee than a visual approximation. A full real-device TalkBack navigation-order audit of every screen. Not performed - no physical Android device or TalkBack is available in this implementation environment (the same standing limitation as every prior phase, R-04/R-18/R-19); code-level `Semantics` correctness was verified via `flutter test`'s semantics-tree APIs (`find.bySemanticsLabel`) instead, honestly disclosed as the ceiling of what this pass could verify, not represented as equivalent to a real TalkBack pass.
**Tradeoffs:** `ExcludeSemantics` on `_MessageBubble`/`_StreamingBubble`'s visual subtree means a screen-reader user can no longer navigate to an individual source citation `Chip` as its own focusable node - accepted, since those chips were never interactive (no `onPressed`) and their names are now folded into the outer bubble's one label, so no information is lost, only per-chip navigation granularity. The five accent-color swatches gained an `AccentColors.names` map that must be kept in sync with `AccentColors.presets`/`extended` by hand (a new small duplication risk, flagged as R-24 below) - accepted over hard-coding names inline at the one call site, since a shared, colocated map is easier to keep in sync than a second copy.
**Real-device readiness (explicit, honest statement per this milestone's own instruction not to fabricate results):** No physical Android device or TalkBack session was available in this implementation environment - the same standing limitation disclosed in every prior phase (R-04/R-18/R-19). What's verified here is code-level and computed: every `Semantics` label is asserted via `flutter test`'s `find.bySemanticsLabel`; every contrast claim is a WCAG relative-luminance ratio computed directly from this app's actual `ColorScheme`/gradient values (not eyeballed, not a device screenshot), re-run across all 12 accent colors. Whether TalkBack's actual navigation *order* through each screen reads sensibly, and whether the touch-target/contrast fixes are perceptible as improvements on a real device, remains M3.1/M3.2's open, unanswered question - this pass narrows what's left to check there, it doesn't close M3.2 outright.
**Status:** Accepted. **Date:** 2026-08-08.

### ADR-032 — Phase 4B production-readiness audit: `autoDispose` on every per-id detail provider, `VectorStore.invalidateCache()` on meeting/document delete, a leaked backup-export temp file fixed, two `assert`s converted to always-enforced exceptions, three duplicated format helpers consolidated, `allowBackup="false"` + an explicit network security config, and a confirmed (not speculative) release-build blocker
**Reason:** Phase 4B's own framing: "imagine the application is shipping to thousands of users next week... everything that could create instability, inconsistency, poor UX, release issues, logging problems, recovery problems, lifecycle bugs, configuration mistakes... should now be cleaned up." Four parallel, read-only research passes (release-mode cleanliness; Android release configuration; lifecycle/dispose correctness; navigation and storage/cascade-delete correctness) were run first to ground this pass in what actually exists, matching every prior phase's discipline - two of the four research agents hit a transient session-limit error mid-run and were re-launched from scratch rather than acted on partially. **New this phase, and different from every prior one**: a real Android SDK toolchain (`ANDROID_HOME`) is present in this implementation environment for the first time, so `flutter build apk --release` was actually attempted - twice, including one attempt preceded by a full `flutter clean` + `flutter pub get` to rule out stale build artifacts - rather than the "no device/toolchain available" disclaimer every prior phase (Phase 3A/3B/4A) had to fall back on for anything build- or device-adjacent.
**Decision (provider memory-growth, `autoDispose`):** Eight `FutureProvider.family` providers across six files (`meetingByIdProvider`, `transcriptForMeetingProvider`, `documentByIdProvider`, `recordingMarksForMeetingProvider`, `notesForMeetingProvider`, `summaryForMeetingProvider`/`actionItemsForMeetingProvider`/`decisionsForMeetingProvider`/`summaryForDocumentProvider`, `meetingReportDataProvider`) cached one entry per unique id visited *for the app process's entire lifetime*, with nothing ever evicting it - the only prior `autoDispose` usage in the whole composition root was `audioPlayerServiceProvider`. Given NFR-16's own "hundreds to low thousands of meetings/documents accumulated over the app's lifetime" scale target, a long session visiting many different detail screens would accumulate unbounded provider-cache memory. All eight now use `FutureProvider.autoDispose.family` - safe because the only consumer of each is the one detail screen that `ref.watch`es it for exactly as long as it's on screen, the same lifetime `autoDispose` already assumes; confirmed via grep that no test constructs any of them directly (only exercised indirectly through screen widget tests, which already match the watched-while-visible pattern).
**Decision (dead code removed, not just flagged):** `chatMessagesForSessionProvider` (`lib/features/chat/presentation/providers/chat_providers.dart`) had zero references anywhere in `lib/` or `test/` - `ChatController` reads messages via `chatMessageRepositoryProvider` directly (`openSession`, line ~184), never through this provider. Confirmed genuinely dead (not reflection/string-routed) and deleted outright, rather than given an `autoDispose` it would never benefit from since nothing watches it.
**Decision (stale retrieval cache after delete, `VectorStore.invalidateCache()`):** `DeleteMeetingUseCase`/`DeleteDocumentUseCase` deleted `knowledge_chunks` rows only via the database's own `ON DELETE CASCADE` (never through `IndexingService`/`VectorStore` directly), which is correct for the *rows* but left `BruteForceVectorStore`'s in-memory `_cache` (ADR-029) unaware the deletion happened - a deleted meeting's or document's content could keep surfacing in workspace chat/search answers for the rest of the app session, until some unrelated `indexContent` call happened to invalidate the cache first. Both use cases now take a `VectorStore` dependency and call `invalidateCache()` immediately after their repository delete succeeds (mirrors `NotesController.delete`'s existing `removeIndexForSource` call, the one deletion path that was already covered). Verified with a spy `VectorStore` test double per use case (real corpus/retrieval setup wasn't needed - only the call itself needed proving) rather than a full retrieval-level regression test, since `DeleteMeetingUseCase`/`DeleteDocumentUseCase` don't own retrieval logic themselves.
**Decision (leaked backup-export temp file):** `BackupScreen._exportBackup()` copied the live database to `getTemporaryDirectory()` before sharing it, and never deleted that copy - `StorageScreen`'s "Clear temporary cache" only ever targeted leftover `.wav` transcode files, never these, so every backup export permanently leaked a full database copy into temp storage with no UI path to remove it. Fixed at the source (the copy is deleted in a `finally` block once `share()` completes, success or failure) and given a safety net (`clearTempTranscodeCache` - kept its name, since renaming would ripple through its one call site and doc comments for no functional benefit - now also matches `offline_mom_backup_*.db`) for the one case the source-level fix can't cover: the app process being killed between writing the copy and that `finally` block running.
**Decision (two `assert`s converted to always-enforced exceptions):** `KnowledgeChunk`'s constructor and `DefaultIndexingService.indexContent`'s entry both validated "exactly one of meetingId/documentId must be set" via `assert(...)` - stripped entirely by `flutter build --release`, meaning a bug that violated this invariant would build silently in release and corrupt a chunk's owner reference, not fail loudly, since `flutter test` (where `assert` *is* enabled) would never catch the release-only difference. Both converted to a real `if (...) throw ArgumentError(...)` - `KnowledgeChunk`'s constructor lost its `const` modifier to allow a body (confirmed via grep: nothing anywhere ever constructed one with `const` regardless, so this costs nothing). The other `assert`s the research pass found (`KnowledgeSourceCard`'s constructor contract, `text_markdown_parser.dart`'s hardcoded-enum check, `LlmQueueRequest.maxAttempts`, `WorkspaceChatUseCase`'s two session/question invariants) were left as `assert` - each is either only ever constructed with values this codebase's own call sites already guarantee are valid (not user input), or (for the `WorkspaceChatUseCase` blank-question case specifically) confirmed already re-validated at the actual call boundary (`ChatController.sendMessage`) before reaching it, making the assert genuinely redundant documentation rather than the only guard.
**Decision (three duplicated format helpers consolidated, one left alone):** `storage_screen.dart`'s `_formatBytes`, `document_details_screen.dart`'s `_formatBytes` (a 3-tier variant lacking `formatFileSize`'s GB tier - functionally identical for any realistic document size), and `meeting_details_screen.dart`'s `_formatDuration(int)` were byte-for-byte or functionally-identical reimplementations of `lib/shared/utils/format_utils.dart`'s existing `formatFileSize`/`formatDurationSeconds` (Phase 2B) - all three deleted, call sites repointed at the shared functions. `recording_screen.dart`'s `_formatElapsed(Duration)` (same mm:ss algorithm, but threaded through 3 sites as a `String Function(Duration)` callback parameter, not called directly) and `meeting_details_screen.dart`'s second `_formatDuration(Duration)` (audio-playback-position display, deliberately no hour-rollover) were reviewed and left alone - genuinely distinct calling conventions/purposes, not the same kind of drop-in duplication as the other three, and changing a threaded callback's signature was judged more invasive than this pass's "duplicated helper methods" finding actually warranted.
**Decision (release configuration hardening, `AndroidManifest.xml`):** `android:allowBackup` was unset (defaults to `true`), meaning Android's own Auto Backup/`adb backup` would fold this app's local sqlite database - meeting transcripts, chat history - into OS-level backup infrastructure this app's entire pitch (NFR-17, docs/v2/17-privacy.md: content never leaves the device) never claims to offer or need, since Backup/Restore already has its own explicit, user-initiated path (Settings > Backup). Set to `false`. A new `network_security_config.xml` (`cleartextTrafficPermitted="false"`) was added and referenced from the manifest - `targetSdk 36` already blocks cleartext HTTP by Android's own default (API 28+) so this changes no runtime behavior today, but pins that behavior explicitly rather than leaving it true only by omission/default, matching the existing `INTERNET`-permission comment's own discipline of stating the network posture outright rather than leaving it implicit.
**Decision (confirmed, not fixed - a real release-build blocker outside this phase's safe scope):** `flutter build apk --release` fails to compile, twice, including after a full `flutter clean` + `flutter pub get`: `GeneratedPluginRegistrant.java` references `dev.flutter.plugins.integration_test.IntegrationTestPlugin`, a class that doesn't exist on the release Java compile classpath. Root-caused (not just observed): `.flutter-plugins-dependencies` correctly marks `integration_test` `dev_dependency: true` (confirmed by direct inspection), and Gradle correctly excludes its AAR from the release compile classpath *because of* that flag - but the Flutter-tool-generated `GeneratedPluginRegistrant.java` (this Flutter SDK version, 3.44.8 stable) emits an unconditional reference to its plugin class regardless of build variant, wrapped only in a runtime `try/catch` that cannot rescue a compile-time "package does not exist" error. This is a genuine Flutter SDK/tooling version mismatch, not an app misconfiguration (`integration_test` is correctly placed under `dev_dependencies` in `pubspec.yaml`, and a real `integration_test/app_test.dart` exists and is presumably still wanted) - not something a safe, minimal, verifiable fix exists for within this phase's explicit "do not change architecture / do not rewrite existing code" scope, and an AGP/Flutter-SDK version bump (the build's own separate warning: AGP 8.9.2 is below Flutter's recommended 8.11.1+) is exactly the kind of unbounded, multi-cycle (~13 minutes per attempt), hard-to-fully-validate experiment this phase's conservative-scope instruction argues against attempting speculatively. Documented as R-26 (docs/v2/implementation/04-risk-register.md) instead - this is the single most significant finding of this phase, and the first confirmed (not merely disclosed-as-unmeasurable) Play Store blocker any phase of this project has found, precisely because this is the first phase with a real Android toolchain available to attempt the build at all.
**Alternatives considered (release-build blocker):** Removing `integration_test` from `pubspec.yaml` entirely. Rejected - a real `integration_test/app_test.dart` exists, so removing the dependency would silently delete working test infrastructure as a side effect of an unrelated release-build fix, a bigger and more consequential decision than this audit is positioned to make unilaterally. Upgrading AGP per Flutter's own warning. Rejected for this pass specifically - plausible fix, but unverified, multi-cycle, and a genuine Gradle/toolchain change beyond "audit and report" scope; flagged in the risk register as the team's most likely next step, not attempted here.
**Real-device readiness (explicit, honest statement per this milestone's own instruction not to fabricate results):** No physical Android device is available in this implementation environment, unchanged from every prior phase (R-04/R-18/R-19). What changed this phase: a real Android SDK/Gradle/NDK toolchain *is* available, so `flutter build apk --release` was genuinely attempted rather than assumed - and it genuinely fails, at the Java-compile step, before Gradle ever reaches R8/minification/resource-shrinking. This means `08-quality-gates.md`'s ProGuard/minify-compatibility question for `share_plus`/`path_provider`/`printing` (flagged by the release-configuration research pass as lacking explicit `-keep` rules) remains **unverified in either direction** - not confirmed working, not confirmed broken - since the build never got far enough to exercise R8 at all. Once R-26 is resolved, re-running a release build is also the first real opportunity to check that.
**Status:** Accepted. **Date:** 2026-08-10.

### ADR-033 — Phase 5A Student Toolkit: Image Tools only (Scanner/PDF Tools deferred), an in-memory-only compress/resize pipeline with no temp files, target-size JPEG compression via analytically-computed downscale retries, WebP excluded from compression (lossless-only in `package:image`) but offered for resize/conversion, `toolkit_files` in migration v11 with no FTS5 entry, and `KnowledgeSourceCard` reused for Recent Files rows
**Reason:** The Student Toolkit was originally scoped across four sections (Scanner, Image Tools, PDF Tools, Recent Files) at a CamScanner/Adobe-Scan/SmallPDF caliber bar ("polished enough that many students install OfflineMoMAI ONLY because of this module"), explicitly "no placeholders, no TODOs, no mock implementations, everything production quality." Given that bar, attempting all four sections in one pass risked either a multi-week scope no single milestone in this project's history has attempted, or a shallow implementation of everything that would violate the "no placeholders" instruction outright. Presented to the product owner as an explicit choice (`AskUserQuestion`, not a unilateral descope) between "Image Tools only, fully polished," "Image Tools + Scanner," or "everything" - **Image Tools only was selected**. Scanner and PDF Tools are deferred to a later phase, not cancelled; Recent Files ships, but scoped to Image Tools' own outputs only (its schema and UI generalize cleanly to more tool types later without a rewrite).
**Decision (in-memory-only pipeline, no temp files):** The entire pick → configure → compress/resize → preview flow keeps the image as `Uint8List` bytes in the Riverpod controller's state; nothing touches disk until the user explicitly taps Save (writes once, directly to `<appDocs>/toolkit/` via `newToolkitOutputPath`) or Share (`XFile.fromData(bytes, ...)`, no intermediate file at all - confirmed `cross_file`'s `XFile.fromData` exists by reading the bundled package source before relying on it). This is a deliberate reaction to Phase 4B's own finding (ADR-032): `BackupScreen`'s leaked temp-file bug existed specifically because a temp copy was written to disk and cleanup depended on a `finally` block actually running. The toolkit avoids that entire class of bug by never creating a temp file the pipeline itself is responsible for cleaning up - the only file it ever writes is the one the user asked to keep.
**Decision (target-size JPEG compression, analytically-computed downscale):** `compressImage` (`lib/services/toolkit/image_compression_service.dart`) binary-searches JPEG quality between a floor (10) and ceiling (95) for the highest quality that still fits a target byte size; if even the quality floor doesn't fit, it downscales and retries. The downscale ratio per retry is computed analytically - `ratio = (sqrt(targetSizeBytes / atFloorEncodedSize) * 0.9).clamp(0.2, 0.9)`, reasoning that JPEG size at fixed quality scales roughly with pixel count - rather than a fixed percentage per step. **This replaced a fixed-15%-per-retry version that failed to converge within its retry budget** for a large source (2000×1500) against a small target (15KB): six retries at 0.85× linear only reaches ~14% of the original pixel count, insufficient for a >100:1 size reduction; caught by `test/services/toolkit/image_compression_service_test.dart`'s own downscale-convergence test before this ever reached the UI layer, not discovered later. `ImageCompressionResult.reachedTarget` is honestly `false` (never silently misreported) when even the analytical downscale search can't hit the target within its retry budget - the UI surfaces this as a visible warning, not a silent best-effort substitution.
**Decision (WebP excluded from compression, offered for resize/conversion):** `package:image` 4.9.1's `WebPEncoder` (confirmed by reading its source directly, not assumed) only emits the lossless VP8L container - no quality parameter exists to trade off size against fidelity, which is incompatible with a target-size *or* explicit-quality compression tool by definition. `ImageOutputFormat` (compression) therefore offers only `jpg`/`png`; `ImageResizeOutputFormat` (resize) is a strict superset adding `webp`, since resize has no target-size search for WebP's losslessness to conflict with - this is also deliberately where "Image Conversion" lives (an output-format choice on the resize tool), rather than a fourth near-duplicate screen the original spec's four-tool list implied.
**Decision (`toolkit_files` schema, migration v11, no FTS5 entry):** `ToolkitFile` (plain class, not `@freezed`, mirroring `Note`/`KnowledgeChunk`'s existing precedent) backs Recent Files. No foreign keys (a toolkit output isn't owned by any meeting/document) and deliberately **no FTS5/searchable-content entry** - toolkit outputs (a compressed passport photo, a resized diagram) aren't part of the workspace's searchable knowledge the way a meeting transcript or document extract is, so extending `ContentSearchRepository`/`ContentType` to cover them would be scope creep against what Workspace Search is actually for. `AppConstants.sqliteDbVersion` bumped 10→11; `test/test_helpers/test_database.dart` updated in the same commit as `AppDatabase.open()` (per R-20's standing discipline about this exact file needing to stay in lockstep).
**Decision (`KnowledgeSourceCard` reused for Recent Files rows, not a new widget):** `ToolkitFile` isn't a Knowledge Source (see above), but its list-row shape - icon/title/updated-label/status-chip/size-label/swipe-to-delete-with-confirmation/optional trailing icons - is identical to what `KnowledgeSourceCard` (Phase 2B, ADR-028) already provides. Reused as-is (favorite/rename/share icons passed via its existing `trailing` slot; reduction-percent shown via `statusLabel`/`statusColor`), with its doc comment broadened from "Knowledge Source" specifically to a general reusable list-row shape - building a near-identical second widget here would itself have violated the project's own "no duplicated widgets" rule.
**Decision (Home screen entry point, separate from the Knowledge Source pillar grid):** The Student Toolkit gets its own full-width card on `HomeScreen` (`_StudentToolkitCard`), placed below the four-pillar Knowledge Source grid rather than as a fifth tile inside it - consistent with the schema decision above that toolkit outputs are not Knowledge Sources, this keeps that grid's own stated meaning ("every Knowledge Source pillar") intact rather than diluting it with an unrelated fifth entry. Only Compress Image and Resize Image are exposed anywhere in the UI (Home card → `StudentToolkitScreen`'s two tool cards) - Scan Document and Compress PDF, named in the original four-section spec, are deliberately absent from every menu/quick-action surface, not shown-but-disabled, per the project's own standing "no placeholders for unbuilt features" rule.
**Decision (a real bug found and fixed by this phase's own widget-test-writing, not by inspection):** Writing a widget test for the Recent Files rename dialog (`toolkit_recent_files_screen_test.dart`) reproduced a genuine "TextEditingController used after being disposed" crash: the dialog's controller was disposed in a `finally` block immediately after `showDialog`'s returned Future resolved (at `Navigator.pop()` time), which is *before* the dialog's own exit-transition animation finishes one more rebuild of the still-mounted `TextField`. Fixed in this screen by switching to `TextFormField(initialValue: ..., onChanged: ...)`, which owns no controller and so has no dispose-timing window to race at all. **This exact `TextEditingController` + `showDialog` + `finally`-dispose pattern is the one ADR-030 (Phase 3B) deliberately introduced across six other dialog-presenting methods app-wide** (`HomeScreen._editDisplayName`, `DocumentDetailsScreen._renameDocument`, `ChatHistoryScreen._rename`, three `MeetingDetailsScreen` dialogs) - none of which had a widget test actually driving their full open→type→save→close flow before this phase, which is almost certainly why the same latent bug was never caught there. Fixing those six call sites is out of this phase's "Image Tools only" scope; flagged as a follow-up task rather than fixed here, since it touches five files this milestone did not otherwise need to open.
**Alternatives considered:** Building all four Student Toolkit sections at reduced depth to hit the original spec's literal scope. Rejected by the product owner's own `AskUserQuestion` answer - "Image Tools only, fully polished" was chosen specifically over "everything," so building a shallower version of Scanner/PDF Tools anyway would directly contradict that decision. A dedicated `ImageConversionScreen` as originally implied by the four-tool-name spec. Rejected - resize already has no target-size constraint fighting WebP's losslessness, so folding conversion into resize's output-format choice avoids a near-duplicate pick→configure→result screen for what is, underneath, the same pipeline shape. Disposing the rename dialog's controller via a delayed/post-frame callback instead of switching to `TextFormField`. Rejected - a `TextFormField` with no controller at all removes the entire class of dispose-timing bug outright, rather than tuning a delay against an animation duration that could change.
**Tradeoffs:** Users hitting an unreachably small compression target get an honest "couldn't fully reach it" result rather than either a silent quality cliff or a refusal - accepted as the more trustworthy behavior for a tool whose whole pitch is "fits under this exam portal's KB limit," even though it means the UI must handle and clearly surface a not-quite-succeeded state rather than a simple binary success/failure. Recent Files' schema has no FTS5 entry, so a toolkit output can never surface in Workspace Search - accepted as correct given what these outputs are, but means a user who forgets which tool produced a file has only the Recent Files screen itself (grouped by recency, not full-text-searchable) to find it, not the app's general search.
**Status:** Accepted. **Date:** 2026-08-12.

### ADR-034 — Phase 5B Scanner + PDF Tools: rasterize-and-rebuild as the PDF-manipulation strategy (no new native/licensed dependency), a shared `PdfPageRenderingService` foundation, pure-Dart 4-point perspective correction, one "Organize" tool covering both Extract and Reorder, fixed-tier (not target-byte) PDF compression presets, and a `toolkit/tmp/` temp-file discipline for multi-page work
**Reason:** The long-term Product Vision named Scanner and PDF Tools as the two remaining Student Toolkit sections, at the same Adobe Scan/Microsoft Lens/CamScanner/SmallPDF/iLovePDF quality bar Phase 5A was held to, with an explicit "do not refactor the existing architecture" constraint (already reviewed and confirmed future-proof for exactly this addition, ahead of this phase). The one open technical question Phase 5A's own scope-negotiation flagged - "PDF manipulation has no true native library available without a licensed dependency" - had to be resolved before writing any PDF Tools code, mirroring this project's own ADR-016/R-09 discipline (license-audit before adopting a new dependency), not assumed away.
**Decision (PDF manipulation strategy - rasterize and rebuild, no new dependency):** Researched two real candidate libraries for merge/split/extract/compress of an *existing* PDF: `pdf_manipulator` (AGPL-3.0 via itext7, plus a Rust native engine) and `pdf_combiner` (MIT, but only covers merge/image-to-PDF, not split/extract/reorder/compress). Neither was adopted. Instead: `pdf` (`^3.11.3`) and `printing` (`^5.14.3`) - both MIT/Apache-2.0, both **already dependencies** of this app for meeting PDF export - are sufficient for the entire PDF Tools surface. `printing`'s `Printing.raster()` rasterizes an existing PDF's pages to raw RGBA bitmaps via the platform's own native renderer (Android `PdfRenderer`, iOS/macOS PDFKit); `pdf`'s widget layer (`pw.Document`/`pw.Image`) rebuilds a new PDF from those (now JPEG-recompressed) page images. Every PDF Tool - Compress, Merge, Split, Organize - is built on this one primitive. **Zero new dependencies were added for PDF manipulation.**
**Decision (shared `PdfPageRenderingService` foundation):** A single service (`lib/services/toolkit/pdf_page_rendering_service.dart`) wraps `Printing.raster()`, streaming one rasterized-and-JPEG-encoded page at a time to a toolkit temp file rather than holding a whole document in memory - the app's own performance requirement to avoid loading huge documents into memory. `Printing.raster()` calls into native code via a platform channel, which only works on the root isolate (unlike `ImageCompressionService.compressImage`, this cannot run inside `compute()`); only the pure-Dart JPEG-encode step per page is offloaded to `compute()`. `PdfCompressionService`/`PdfMergeService`/`PdfSplitService`/`PdfOrganizeService` all depend on this one interface, not on `Printing` directly - kept `PdfPageRenderingService` swappable and, critically, fake-able in tests (`FakePdfPageRenderingService`, shipped alongside the interface per this project's established fakes-live-with-the-interface convention), since `Printing.raster`'s platform channel has no implementation under `flutter test`.
**Decision (page-selection order vs. rasterization order):** `rasterizePages(pageIndices: ...)` always sorts/deduplicates the requested indices and rasterizes ascending, regardless of the order requested, and tags each yielded page with its true source `pageIndex` - it does *not* trust the underlying native rasterizer to preserve an arbitrary requested order (undocumented behavior, unsafe to assume). Callers needing a specific final order (Organize's reordering, Split's grouping) resequence the *already-rasterized* pages themselves, keyed by `pageIndex` - pure, reliable Dart list logic, decoupled from any native-rasterizer ordering assumption.
**Decision (pure-Dart 4-point perspective correction, no OpenCV/native dependency):** `applyPerspectiveCorrection` (`lib/services/toolkit/scan_image_processing_service.dart`) implements the classic unit-square-to-quadrilateral closed-form projective transform (Heckbert 1989), applied in the inverse direction (destination unit square → source quad) so every output pixel maps back to exactly one source sample via bilinear interpolation, with no resampling holes - standard, well-understood computer graphics math, not a novel or unverified algorithm. Verified by unit tests against synthetic quadrant-colored images, including a genuinely skewed (non-axis-aligned) quad, before any UI was built on top of it - mirroring Phase 5A's own "verify the risky algorithm before building UI on it" discipline for the compression target-size search. Rectangular "Crop Page" and full "Perspective Correction" share one tool (`ScanPageEditorScreen`'s four draggable corner handles) rather than two screens, since dragging all four corners into an axis-aligned rectangle *is* a plain crop - a strict subset of what the general transform already does.
**Decision ("Organize" covers both Extract Pages and Reorder Pages):** The product brief named "Extract Pages" and "Reorder Pages" as separate PDF Tools capabilities. Both are the same underlying transform - rebuild a PDF from a chosen, ordered subset of an existing PDF's pages (`PdfOrganizeService.organize(sourceBytes, orderedPageIndices)`) - so they ship as one tool with one page-thumbnail-grid screen (reorder by drag, remove by tapping delete), not two near-identical page-list screens. This mirrors ADR-033's own reasoning for folding "Image Conversion" into Resize's output-format choice rather than a fourth screen.
**Decision (PDF compression is fixed-tier per preset, not a target-byte search):** `ImageCompressionService` (Phase 5A) binary-searches JPEG quality/downscale to hit an exact target byte size, retrying cheaply since each retry is one pure-Dart re-encode. `PdfCompressionService` does **not** do the same: each retry would mean re-rasterizing every page of the source PDF through the native platform renderer again - a real, expensive, disclosed cost asymmetry, not a corner cut. Each of the five named presets (Resume Upload/Scholarship/Government Exam/University/Email Attachment, plus Custom) instead applies one fixed (DPI, JPEG quality) pair in a single pass - the same fixed-tier convention real tools like SmallPDF's "Recommended"/"Extreme" compression use for the same reason. `PdfCompressPresetSpecs.disclaimer` states this explicitly in the UI, alongside the further disclosed tradeoff that compression works by re-rendering each page as an image - a text-only, born-digital PDF may not shrink (or could even grow), since it has no scanned/photographed content for a lower render DPI to meaningfully reduce; the tool is honestly positioned for the scanned/image-heavy documents (mark sheets, forms, ID cards) this app's own persona list is built around.
**Decision (`toolkit/tmp/` temp-file discipline, extending Phase 5A's "no temp files" pipeline):** Phase 5A's Image Tools pipeline deliberately never writes an intermediate file (ADR-033) - fully in-memory, since a single image's bytes are small. Scanner/PDF Tools cannot make the same choice: a many-page PDF's rasterized pages cannot safely all live in memory at once (this app's own performance requirement). `newToolkitTempFilePath`/`clearToolkitTempFiles` (`lib/core/utils/toolkit_paths.dart`) extend the existing `toolkit/` output-path helper with a `toolkit/tmp/` subfolder; every PDF Tool service wraps its rasterize-then-rebuild work in `try/finally`, deleting every temp file it created whether the operation succeeds or fails - directly applying Phase 4B's leaked-backup-file lesson (ADR-032) to this phase's own, larger temp-file surface. `clearToolkitTempFiles()` is the safety net for the one case `try/finally` can't cover (the process killed mid-operation), mirroring `clearTempTranscodeCache`'s existing precedent.
**Decision (`toolkit_files.page_count`, migration v12 - the only new column, not a speculative metadata blob):** The Phase 5A architecture review (before this phase started) already concluded the schema was future-proof *except* for one soft gap: no field for tool-specific data like a scan's page count. Rather than adding a generic, speculative JSON metadata column, exactly one concrete, currently-needed nullable `INTEGER` column was added - ordinary, additive schema growth (per this project's own migration strategy), not the kind of "existing code refactor" the phase's own instructions prohibited.
**Decision (multi-select gallery import + file-system PDF/image picking - both additive extensions, not new pickers):** `ToolkitImagePickerService` (Phase 5A) gained one new method, `pickMultipleFromGallery()`, for Scanner's "Gallery Import" - reusing the same interface Image Tools already depends on rather than a parallel Scanner-only picker. A new, narrower `ToolkitFilePickerService` wraps `file_picker` for PDF Tools' "pick an existing PDF/image from device storage" need - deliberately not the existing `DocumentImportService` (which is coupled to copying into `Document`-owned storage and creating a `Document` row, a heavier concern than PDF Tools' transient "read bytes, process, discard the source" need).
**Alternatives considered:** Adopting `pdf_manipulator` for its broader out-of-the-box feature set. Rejected outright - AGPL-3.0 is incompatible with a closed-source commercial app without a paid itext7 license, and its Rust native engine is a real Android-build-risk addition this project already has enough of (R-26). Implementing PDF compression as a target-byte search identical to Image Compress. Rejected - the cost-per-retry asymmetry (one native rasterization pass per page vs. one pure-Dart re-encode) makes repeated whole-document retries genuinely expensive, not just more code; a fixed-tier preset is the honest, real-world-precedented alternative. A generic `metadata` JSON column on `toolkit_files` instead of one concrete `page_count` field. Rejected as premature generalization for fields nothing yet needs - normal migration growth handles this the moment a real need appears, per the Phase 5A architecture review's own conclusion.
**Tradeoffs:** Rasterizing every page (even a born-digital, vector-text PDF) means the output's text is no longer selectable/searchable - a real, disclosed fidelity loss inherent to not having a real PDF page-tree editor available under this dependency-and-license constraint; acceptable for this app's own stated personas (scanned forms, mark sheets, certificates - already-flattened content, not text-heavy reports). PDF compression cannot guarantee hitting an exact target size the way Image Compress can, and is disclosed as such rather than silently underperforming its own Phase 5A sibling's stronger guarantee.
**Status:** Accepted. **Date:** 2026-08-14.

### ADR-036 — Phase 6A AI Model Manager: real infrastructure for Chat LLM/Embedding/Whisper, honestly scoped catalog, split download strategy, future-ready `ModelKind`
**Reason:** ADR-035 approved "an AI Model Manager" as a future direction, explicitly deferring every implementation decision to a follow-up ADR. Phase 6A is that follow-up: a production model-download/install/switch/verify/delete surface for the three model kinds this app actually has engines for, built to be extended (not refactored) when OCR/Vision/Translation engines and additional LLM/embedding tiers eventually ship (ADR-035's own condition for profession-based recommendations).
**Decision (catalog is honest, not padded):** `ModelCatalog` (`lib/services/ai/model_catalog.dart`) is static, curated Dart data - the same "specs, not a database table" pattern `PdfCompressPresetSpecs` already established (Phase 5B). It contains exactly one real Chat LLM entry (`Qwen2.5-1.5B-Instruct` Q4_K_M, the same `hf://` source already integration-tested since Phase 0) and exactly one real Embedding entry (`embeddinggemma-300M` Q8_0, integration-tested since Phase 1B/ADR-003) - **no second, invented tier with an unverified download URI was added** for either kind, even though the product brief's "Available Models" browsing experience reads as if multiple tiers should exist per kind. A second tier for either kind is Approved Future Architecture (ADR-035), not fabricated here. Speech-to-text gets all 6 real `WhisperModel` enum values `whisper_flutter_new` supports (`tiny`/`base`/`small`/`medium`/`large-v1`/`large-v2`) - previously only 3 were ever exposed in any screen; this catalog is now the single source of truth, replacing the locally-duplicated lists in `model_setup_screen.dart`/the now-deleted `ai_models_screen.dart`. `ModelKind` (`services/ai/model_lifecycle_manager.dart`) gained `ocr`/`vision`/`translation` values with **zero catalog entries** - the AI Model Manager UI, database schema, and `ModelLifecycleManager` are all already generic over `ModelKind`, so a real engine for one of these three later is an additive change (new engine + new catalog entries), never a refactor of this phase's code.
**Decision (split download strategy, not one uniform downloader):** Direct source inspection of `llamadart` 0.8.17 confirmed its internal `DefaultModelDownloadManager` already does real HTTP-Range resume, retry-with-backoff, and optional SHA-256 verification - reimplementing that for the LLM/embedding kinds would be a pure regression, not an improvement. Instead, `LlamaDartLlmEngine`/`LlamaDartEmbeddingEngine` gained a `modelSourceOverride` constructor parameter (so the AI Model Manager can point them at any catalog entry, not just the one hardcoded `_defaultModelSource`) and an exposed `cancelActiveDownload()`/`isDownloading` pair (so "Pause" can request cancellation of an in-flight `llamadart` download without this app needing its own cancel-token type for that path) - both minimal, additive changes to two already-well-tested files, not a rewrite. Whisper models never had this: `WhisperSpeechToTextEngine`'s own downloader (already a hand-rolled replacement for `whisper_flutter_new`'s own, timeout-less one - see that file's original doc comment) had no resume, no cancellation, and no checksum. Phase 6A adds a new, standalone `ModelDownloadService` (`services/ai/model_download_service.dart`: `HttpModelDownloadService` real implementation + `FakeModelDownloadService` test double, mirroring `PdfPageRenderingService`/`FakePdfPageRenderingService`'s exact convention) that gives Whisper real Range-resume (validated against a stored `ETag`/`Last-Modified`, never blindly trusting a stale `.part` file), real pause/resume, and a local SHA-256 fingerprint computed incrementally during download (`package:crypto` + `package:convert`'s `AccumulatorSink`, both promoted from transitive to direct dependencies) - all without touching `WhisperSpeechToTextEngine` itself (its own hand-rolled downloader stays as a fallback for transcription-triggered downloads that bypass the Model Manager entirely; whichever path runs first simply wins, the other short-circuits on the file already existing).
**Decision ("Verify Model" is a local integrity fingerprint, not publisher-signed verification):** This app has no confirmed, published SHA-256 hash to check a download against for any of these models (neither Hugging Face's Qwen/embeddinggemma repos nor ggerganov/whisper.cpp publish one this app can safely hardcode blind). "Verify" for Whisper therefore re-hashes the on-disk file and compares it to the hash *this app itself* recorded at install time - real corruption/tampering-since-install detection, explicitly **not** a claim of publisher authenticity, and disclosed as such in `InstalledModel.localSha256`'s doc comment. For LLM/embedding, "Verify" re-invokes `ensureModelReady()`, which re-triggers `llamadart`'s own real cache-validation logic (confirmed by source inspection: a cache hit re-checks byte count against stored metadata before trusting it) - genuine, not fabricated, verification, just through the underlying package's own mechanism rather than a hash this app computed itself.
**Decision (honest profession recommendations - Whisper differs, LLM/embedding don't, and the doc comment says so):** `ProfessionRecommendations` (`services/ai/profession_recommendations.dart`) recommends the same single LLM/embedding catalog entry for all 9 professions (there is nothing else to recommend yet) and a genuinely different one of the 6 real Whisper tiers per profession, reasoned from accuracy/RAM/storage/speed trade-offs specific to each profession's real-world recording pattern (e.g. Researcher → Large v2 for citation-accurate interview transcripts; General User → Tiny for minimal footprint). This is a deliberately honest, partial delivery of the "profession-based recommendations" brief, not a differentiated LLM/embedding recommendation dressed up to look real.
**Decision (installed-model tracking is a new table, not a Hive field):** `installed_models` (migration v13) is a new SQLite table - `AppSettings`'s own doc comment already establishes Hive as a poor fit for a growable, queryable list of records (as opposed to a single settings row), the same reasoning that led `toolkit_files` to be a table rather than a Hive list. `AppSettings` gained three new nullable fields instead - `activeLlmModelId`, `activeEmbeddingModelId` (new; `null` resolves to `ModelCatalog.defaultFor(kind)`), and `professionProfile` (persists the Profession Setup screen's last choice) - mirroring `whisperModelName`'s existing role for the third kind, which was left as-is rather than duplicated.
**Decision (Delete Model's honest, disclosed asymmetry):** For Whisper, delete is precise: this app owns the exact `ggml-*.bin` file path and removes it directly. For LLM/embedding, `llamadart`'s cache lives in its own internally-named subdirectory (`ModelSource.cacheDirectoryName`, a private algorithm this app does not reimplement - see Alternatives Considered) with **no public cache-eviction API** - deleting an `InstalledModel` row for these two kinds removes this app's own tracking record and unloads the model from memory if resident, but does not guarantee the on-disk cache file is removed. The Storage Usage screen's "Delete Cache" action covers this honestly instead: a deliberately blunt action that clears `llamadart`'s entire cache root (both the LLM and embedding model together, forcing both to re-download next use) - disclosed in-product, not hidden.
**Decision (Model Safety - no duplicate downloads):** `ModelDownloadController.start(spec)` sets `ModelDownloadInProgress` state **synchronously, before its own first `await`** (not after resolving a destination path or constructing an engine) - closing a real race window a first draft of this code had, where two `start()` calls made back-to-back could both pass the "already downloading?" guard before either had set state, since the state-setting was originally buried behind an async gap. Caught by `model_download_controller_test.dart`'s "second start() call while one is already in flight is a no-op" test before this reached the final implementation.
**Alternatives considered:** Reimplementing `llamadart`'s HTTP-Range/retry/checksum logic from scratch for a uniform downloader across all kinds. Rejected - `llamadart`'s own downloader already does this correctly (confirmed by source inspection); reimplementing it would risk introducing bugs into an already-working path for no capability gain, purely for architectural uniformity. Reverse-engineering `ModelSource.cacheDirectoryName`'s private hashing algorithm to enable precise per-model cache deletion for LLM/embedding. Rejected - it's undocumented internal package behavior that could change across `llamadart` versions without notice; a subtle mismatch would silently delete the wrong directory (or nothing), a worse outcome than the disclosed "Delete Cache clears both together" limitation. Inventing plausible-sounding second-tier LLM/embedding catalog entries (e.g. a fictional "Large" chat model) to make "Available Models" feel richer. Rejected outright - this project's standing no-fabrication discipline (R-35's entire premise) applies exactly as much to a catalog entry with a download URL nobody has verified works as it does to a documentation claim.
**Tradeoffs:** The "Available Models" browsing experience is genuinely rich for Speech-to-text (6 real, distinct choices) but thin for Chat/Embedding (1 choice each, framed honestly as "Standard" rather than implying more exist) - a real, visible gap between what the product brief envisioned and what ships today, explicitly not papered over. LLM/embedding "Delete" not guaranteeing disk space reclamation is a real UX rough edge, mitigated but not eliminated by the Storage Usage screen's blunt cache-clear alternative. `ModelDownloadService`'s real network I/O is untestable under `flutter test` (no device, same standing limitation as R-04/R-18/R-19/R-31/R-32) - its pure resume-decision logic (`buildRangeHeaderValue`/`validatorsCompatible`) is unit-tested in isolation instead, the same "extract the testable logic from the untestable I/O shell" discipline `PdfPageRenderingService` established.
**Status:** Accepted. **Date:** 2026-07-29 (corrected 2026-08-06 — originally logged as 2026-08-20, a typo: later than Phase 6B/ADR-037 which shipped after it. Corrected against the `phase-6a` tag's actual commit timestamp.).

### ADR-037 — Phase 6B Hybrid Retrieval Engine: RRF fusion of chunk-level BM25 + vector search, evidence-based confidence gating a local-vs-general-knowledge LLM fallback, additive-only schema/architecture
**Reason:** The retrieval pipeline had stayed at its Phase 1C baseline (a single `VectorStore.similaritySearch` call, `k=3`, no keyword signal, no ranking beyond cosine order, a hardcoded "couldn't find anything relevant" string when nothing matched) through every subsequent phase. Product direction approved upgrading this into a real hybrid engine - semantic + keyword retrieval, metadata-aware ranking, intelligent context assembly, and, when local knowledge genuinely doesn't cover a question, an explicit, clearly-labeled answer from the local LLM's own general knowledge instead of a fixed refusal string - entirely offline, with no fabricated citations ever attached to a general-knowledge answer.

**Decision (compose `VectorStore` directly, not `RetrievalEngine` - avoid a redundant embed call):** `HybridRetrievalPipeline` (`lib/services/retrieval/hybrid_retrieval_pipeline.dart`) depends on `VectorStore` directly rather than the existing `RetrievalEngine`/`DefaultRetrievalEngine`. `DefaultRetrievalEngine.retrieve()` does nothing but trim the query, call `EmbeddingEngine.embed()` once, and delegate to `VectorStore.similaritySearch()` - composing it from the new pipeline would mean embedding the query a second time (once for confidence-scoring's cosine recompute, which reuses the same embedding, and once inside `RetrievalEngine`), a real, avoidable performance regression on the app's most latency-sensitive native call. `RetrievalEngine`/`DefaultRetrievalEngine`/`BruteForceVectorStore` are left completely untouched and still exported/wired (`retrievalEngineProvider` remains in `app_providers.dart`) - confirmed by research that nothing besides `WorkspaceChatUseCase` (now rewired to the new pipeline) and two performance-benchmark test files (which construct `DefaultRetrievalEngine` directly for their own timing purposes) ever depended on it, so backward compatibility costs nothing here.

**Decision (a second, chunk-granularity FTS5 table, not a redesign of the existing search index):** `content_fts` (migration v4, ADR-009) already gives the Search screen fast full-text search - but at source-item granularity (one row per meeting/document/transcript/summary/note), with no BM25 ranking exposed and no per-chunk id to fuse against a vector match. Rather than redesigning that table or bolting chunk-level concerns onto it, migration v14 adds a new `knowledge_chunks_fts` table at the same granularity as `knowledge_chunks`/`VectorStore` (one row per indexed chunk) - an FTS5 *external content* table (`content='knowledge_chunks', content_rowid='id'`, so `chunk_text` is never duplicated on disk), kept in sync by three triggers (`AFTER INSERT/UPDATE/DELETE` on `knowledge_chunks`) and backfilled once for any pre-existing chunks on upgrade. `content_fts`/`ContentSearchRepository`/`SearchWorkspaceUseCase` are untouched; the only shared code between the two systems is a small, purely extracted `buildFts5MatchQuery()` helper (`lib/core/utils/fts5_query_builder.dart`) - the same tokenization logic `SqfliteContentSearchRepository` already had, pulled out so `KeywordSearchService` doesn't duplicate it, with zero behavior change to the existing Search screen.

**Decision (Reciprocal Rank Fusion, not raw-score blending, for combining vector + keyword results):** Cosine similarity (roughly `[0,1]` for normalized embeddings) and SQLite's `bm25()` (unbounded, corpus-dependent, and "more negative = better" - negated once in `SqfliteKeywordSearchService` so every caller sees "higher = more relevant") are not commensurable numbers; blending them directly would need invented normalization constants this project has no real corpus to validate, the same "don't fabricate an unjustified number" discipline ADR-011 already established for chunk-size estimation. `HybridRanker.fuse()` (`lib/services/retrieval/hybrid_ranker.dart`) instead fuses on *rank position* using RRF (`score += 1/(rrfK + rank + 1)`, `rrfK=60` - the literature-standard constant from Cormack, Clarke & Buettcher 2009, used by production hybrid-search systems including Elasticsearch's and Azure AI Search's own implementations, disclosed here as an unvalidated-for-this-app-but-standard starting point rather than something re-tuned against a real corpus this environment doesn't have). A chunk appearing in both the vector and keyword result lists is fused by id into one entry (`bothMatched`), not double-counted.

**Decision (a real correctness bug in the recency boost, found and fixed by this phase's own test-writing):** A small, capped recency boost is layered on top of the fused RRF score, so a more recently created chunk can win narrow ties without ever letting a genuinely more relevant chunk lose to a barely-relevant-but-fresh one - that invariant is stated directly in `HybridRanker`'s class doc comment. The first implementation applied the boost as a flat percentage (`maxRecencyBoost = 0.10`) of each chunk's *own* score. Writing `hybrid_ranker_test.dart`'s explicit invariant test (`'recency boost never lets an old chunk outrank a more relevant recent one'`) caught that this does **not** actually hold at `rrfK=60`: RRF's score gap between adjacent ranks shrinks as `rrfK` grows (~1.6% relative difference per rank near the top), so a flat 10% boost can leapfrog several ranks of genuine relevance difference - exactly what happened in the failing test (a chunk ranked 4th overtook the 1st-ranked chunk). Fixed by capping the actually-applied boost to strictly less than half the smallest gap between any two distinct RRF scores present in that specific fusion call (`hybrid_ranker.dart`'s `boostBudget` calculation) - a bound that holds for any candidate-set size or composition, not a constant re-tuned to dodge one test case. This means recency can only decide between chunks whose base relevance is equal or near-equal (a genuine tie), never override a real rank-based relevance difference, which is what the class's own documented contract always claimed.

**Decision (evidence-based confidence, recomputed cheaply, not guessed upfront):** `RetrievalConfidenceScorer` (`lib/services/retrieval/retrieval_confidence.dart`) classifies into `RetrievalConfidence { high, medium, low, none }` from a real cosine similarity of the top fused chunk against the query - recomputed once, reusing the query embedding already computed for the vector-search call (so this costs one extra cosine calculation on a handful of already-selected chunks, not a second embedding call), plus whether the keyword path independently agreed. Thresholds (`highThreshold=0.55`, `mediumThreshold=0.35`, `lowThreshold=0.20`, `+0.10` extra margin for "high" without keyword agreement) are disclosed as unvalidated heuristic starting points - no real device or embedding model is available in this environment to tune them against, the same honesty ADR-011's char-per-token estimate and ADR-036/ADR-009's other disclosed-but-unvalidated numeric choices already established for this project.

**Decision (general-knowledge fallback is a distinct new prompt mode, gated by confidence, never fabricating citations):** `LlmEngine.answerGeneralKnowledgeStream(question, {onToken})` is a new method with its own system prompt (`_generalKnowledgeSystemPrompt` in `LlamaDartLlmEngine`, temperature 0.4) that explicitly *permits* the model to answer from its own training knowledge - the existing `answerQuestionStream`'s strict prompt (temperature 0.2) explicitly forbids this and is left unchanged. `HybridRetrievalPipeline` gates the chosen path purely on the recomputed confidence: `high`/`medium` → local-context answer with real citations; `low`/`none` → general-knowledge answer with `sources` always `const []` (never populated, even if some low-confidence chunks happen to exist) and a new, persisted `AnswerProvenance { local, generalKnowledge }` field on `ChatMessage` (migration v14's `chat_messages.answer_provenance` column) - stored explicitly rather than inferred from `sourcesJson` being empty, since those are independent facts about the message. `ChatSourceRef` gained a nullable `confidence` field (the real per-chunk cosine similarity, backward-compatible for old rows lacking the key) so citations shown to the user carry an honest per-source number, not just a source label. `ChatScreen` shows a distinct "From the AI's general knowledge - not your documents" banner whenever `answerProvenance == generalKnowledge`, so the distinction the product decision required is visible, not just logged.

**Decision (token budget selection never truncates a chunk mid-sentence, and now does real work instead of a hidden safety net):** `TokenBudgetSelector` (`charBudget=4000`, matching `LlamaDartLlmEngine._maxTranscriptChars` exactly) greedily includes ranked chunks until the next one would exceed the budget, then stops - always including at least one chunk even if it alone exceeds budget, and never cutting a chunk's text partway through. Because the budget now matches the engine's own hard truncation limit, the engine's blind tail-truncation becomes a rarely-triggered safety net rather than the primary (and cruder) truncation mechanism it effectively was before this phase. `ContextBuilder` formats the budget-selected chunks into the exact same `## <label>\n<text>\n\n` shape `WorkspaceChatUseCase._buildContext` already produced inline - a smarter *selection* of which chunks reach the prompt, not a prompt-format change.

**Decision (Retrieval Statistics stay in-memory, per-query - not a new persisted table):** `RetrievalStats` (vector/keyword/fused/selected candidate counts, truncation flag, elapsed time) is attached to `HybridRetrievalPipeline`'s per-call result for diagnostics, not written to the database - there is no product requirement for historical retrieval statistics, and adding a table for it would be exactly the "unnecessary database redesign" this phase's own brief said to avoid.

**Decision (`AskAboutMeetingsUseCase` and `GeneralChatUseCase` are explicitly out of scope, left untouched):** Research confirmed `AskAboutMeetingsUseCase` is a parallel, independent keyword-overlap-over-summaries path that never used `RetrievalEngine`/`VectorStore` at all (ADR-010's standing no-regression-window still applies to it), and `GeneralChatUseCase`/`ChatScope.general` is unreachable scaffold code (`throw UnimplementedError`, no UI path reaches it). Neither was touched by this phase; the hybrid pipeline only replaces `WorkspaceChatUseCase`'s retrieval path.

**Alternatives considered:** Merging `knowledge_chunks_fts` into the existing `content_fts` table. Rejected - different granularity (source-item vs. chunk) and different consumers (Search screen vs. chat retrieval); forcing one schema to serve both would complicate the simpler, already-working Search path for no benefit to it. Blending cosine similarity and BM25 into one weighted raw score. Rejected - the two scales are not commensurable without invented normalization constants (see RRF decision above). Classifying `QueryType.generalKnowledge` as a pre-retrieval keyword-pattern guess (e.g. treating anything that doesn't look like a workspace question as general-knowledge up front). Rejected - no reliable heuristic can distinguish "unrelated to this workspace" from "genuinely general knowledge" before actually searching; `generalKnowledge` is documented as classifier-unreachable and assigned only as a post-retrieval outcome, reflected via `AnswerProvenance`. Attaching low-confidence chunks as citations on general-knowledge answers "just in case they're relevant." Rejected outright - the explicit product decision was that general-knowledge answers must never carry fabricated/unreliable citations; `sources` is always empty for that path, with no exception.

**Tradeoffs:** The confidence thresholds and the RRF/recency constants (`rrfK=60`, `recencyHalfLifeDays=30`, `maxRecencyBoost=0.10`) are disclosed, unvalidated starting points - no real device, real corpus, or real embedding model is available in this environment to tune them against, matching every prior phase's identical standing disclosure (ADR-011, ADR-036, R-04/R-18/R-19). `FakeEmbeddingEngine`'s bag-of-characters hash produces cosine similarity around 0.45 even for topically unrelated English text (character-frequency distributions across English prose are broadly similar), dangerously close to the 0.35 "medium" threshold - this meant every test asserting "general-knowledge fallback triggered" had to use a genuinely empty corpus (not merely dissimilar content) to be deterministic under test, a real testing constraint worth knowing about if these thresholds are ever retuned against a real embedding model later. `RetrievalStats` being in-memory-only means there is no historical record of retrieval quality over time to analyze if confidence tuning is revisited - an accepted gap given no product requirement asked for one.
**Status:** Accepted. **Date:** 2026-07-30.

### ADR-038 — Product Validation Phase real-device crash: `AppDatabase` switched from sqflite's platform-channel Android backend to `sqflite_common_ffi` + `sqlite3_flutter_libs`, fixing `no such module: fts5`
**Reason:** The first real-device install of the release APK (Product Validation Phase) crashed on first launch with `DatabaseException(no such module: fts5)`, thrown from `migrateV3ToV4`'s `CREATE VIRTUAL TABLE content_fts USING fts5(...)` (migration v4, ADR-009) - a statement `flutter test` has exercised without incident since Phase 0. Root-caused, not guessed: plain `sqflite` (`lib/database/app_database.dart`'s only prior dependency) talks to Android's *own* bundled SQLite on-device via `android.database.sqlite.SQLiteDatabase` (the platform-channel backend), and that OS-level build's FTS5 support is not guaranteed - a well-documented `sqflite`/Android limitation, not an ABI, R8/ProGuard, or Gradle-packaging issue (all confirmed absent by direct inspection of `android/app/build.gradle.kts` - no `abiFilters`/`splits`, no packaging excludes; R8 stripping affects JVM bytecode, never native SQLite grammar). `flutter test` never hit this because it was never exercising that code path in the first place - a fact confirmed directly from source, not inferred: `test/widget_test.dart`'s own `setUpAll` already calls `databaseFactory = databaseFactoryFfi` (from `sqflite_common_ffi`, an FTS5-capable FFI-based SQLite) *before* invoking the real `AppDatabase.open()`, silently overriding the exact same global `sqflite` factory variable the fix below now sets internally. Every other test goes through `test/test_helpers/test_database.dart`'s equivalent FFI setup and never touches `AppDatabase.open()` at all. Production (`main.dart`) had no equivalent override, so it always hit the real platform-channel/OS-SQLite path this codebase's own test suite had never once exercised.

**Decision (switch to `sqflite_common_ffi` + `sqlite3_flutter_libs` in production, not just tests):** `AppDatabase.open()` now calls `sqfliteFfiInit()` and sets `databaseFactory = databaseFactoryFfi` before opening - the identical mechanism already proven correct by this project's own test suite, now applied in production too. `sqlite3_flutter_libs` (new dependency) supplies the bundled, statically-compiled native SQLite library (FTS5 compiled in) for every Android ABI that `package:sqlite3`'s FFI bindings dlopen directly, bypassing the OS's own SQLite entirely. This is a swap of *implementation* behind an already-abstracted interface, not an architecture change: `sqflite_common_ffi`'s `Database`/`Batch`/`OpenDatabaseOptions` types are the same `sqflite_common` interfaces `sqflite`'s own package re-exports, so every repository, migration file (`migrations/v1.dart`-`v14.dart`, all thirteen of them unmodified), and SQL statement in this codebase is untouched - confirmed by `AppDatabase.open()` being the *only* call site for `openDatabase()`/`getDatabasesPath()` anywhere in `lib/` (verified by direct grep, not assumed). No Drift ORM is used anywhere in this codebase (the only "drift" hits in `lib/` are the English word, in doc comments like "silently drift out of sync") - the standing architecture was, and remains, hand-written SQL over `sqflite`'s `Database` interface.

**Decision (resolve the database path via `path_provider`, not `sqflite`'s own `getDatabasesPath()`):** `databaseFactoryFfi`'s own default `getDatabasesPath()` resolves to a `.dart_tool/sqflite_common_ffi/databases` path relative to the working directory (confirmed by reading `sqflite_common_ffi`'s own source, `sqflite_ffi_impl_io.dart`) - correct for desktop tooling, meaningless on a real device. `AppDatabase.open()` instead resolves `getApplicationDocumentsDirectory()` (`path_provider`, already used elsewhere in this app for exactly this reason) and builds the db path from that.

**Decision (defensive legacy-database copy-forward, `migrateLegacyDatabaseFileIfNeeded`):** Because the *old* platform-channel backend's `getDatabasesPath()` (Android's `Context.getDatabasePath()` directory) and the *new* FFI backend's `path_provider`-resolved directory are not the same physical location, a device that had already created a database under the old backend would otherwise appear to "lose" it - a fresh, empty database would simply be created at the new path instead. `AppDatabase.open()` captures the old default path *before* switching `databaseFactory` (the only point at which `sqflite`'s original default factory can still be queried), then a small, independently-unit-tested top-level function copies the file across if one exists at the old path and none yet exists at the new one, never overwriting. In practice this device (and, per the crash log, every prior attempt on it, release or otherwise - the failure is OS-level, not build-type-dependent) never once completed `onCreate`, so there is no real data this migration is rescuing today; it exists for forward-looking correctness, not to paper over known data loss.

**Alternatives considered:** Reimplementing FTS5 support via a different extension or a manually-loaded SQLite extension `.so` on top of the existing platform-channel `sqflite` backend. Rejected - `sqflite`'s Android implementation offers no supported mechanism to load a custom SQLite build or extension into `android.database.sqlite.SQLiteDatabase`; the OS's own SQLite is what it is. Replacing `sqflite`/`sqflite_common_ffi` with a different database package or ORM (e.g. Drift) entirely. Rejected outright per this phase's explicit instruction that the architecture is final, and unnecessary regardless - the actual defect was narrowly which SQLite *binary* executes the SQL, not the API/ORM layer above it, which needed no change. Downgrading to FTS4 (broadly available on Android's system SQLite) instead of fixing FTS5 availability. Rejected - would mean reversing the real, tested Reciprocal-Rank-Fusion/BM25 hybrid retrieval work (Phase 6B, ADR-037) that depends on FTS5's `bm25()` ranking function, a functional regression explicitly out of scope ("do not downgrade the implementation").

**Tradeoffs:** The release APK grows further (native SQLite library bundled per ABI, on top of llamadart/whisper.cpp/ffmpeg's own native libraries already bundled) - not separately measured yet, disclosed as a known cost of the fix, not hidden. The legacy-database copy-forward path is defensive code for a scenario this investigation found no evidence of ever having occurred (every real-device attempt has crashed during `onCreate`, before any database was ever successfully created) - accepted as cheap, standard "don't silently orphan a user's data on a storage-location change" hygiene rather than speculative complexity, and it is independently unit-tested (`migrateLegacyDatabaseFileIfNeeded`) rather than only exercised indirectly.
**Status:** Accepted. **Date:** 2026-07-30.

### ADR-039 — Phase 9.3 (V2.1 Production Hardening): additive `folders` table with no FK, a plain non-`@freezed` `Folder` model, and the confidence chip is a relabel, not a rescoring
**Reason:** Real-device QA on the shipped Phase 9.2 build surfaced eight product-polish issues, two of which were genuine design decisions rather than pure bug fixes: how to add document folders without touching the existing `Document` model or its schema, and how to fix a confidence percentage users read as "answer completeness" when it was always something else.

**Decision (folders as a new table + a nullable, unenforced FK on `documents`, not a redesign of `Document`):** `folders` (`id`, `title`, `created_at`, `updated_at`) ships in migration v15 alongside a new `documents.folder_id INTEGER` column with **no `REFERENCES` constraint** - following the exact precedent `toolkit_files.tool_type` (Phase 5A) and `installed_models.model_id` (Phase 6A) already established for lightweight additive columns: validated at the repository layer (`FolderRepository`/`DocumentRepository`), not the schema layer. `Folder` itself is a plain hand-written class (`copyWith`/`toMap`/`fromMap`), mirroring `Note`, not `@freezed` like `Document` - deliberately avoiding a `build_runner` codegen run for a small, low-risk model. `Document`'s own model and its `@freezed` definition are **untouched** - folder membership is exposed only through dedicated repository methods (`getInFolder`, `moveToFolder`, `getFolderId`), not a new field on `Document` itself, keeping this phase's blast radius to genuinely new files plus narrow, additive repository/provider changes.
**Decision (deleting a folder never deletes its documents):** `FolderRepository.delete()` first sets `folder_id = NULL` on every document currently in that folder, then deletes the folder row - a folder is purely an organizational label, never a container whose deletion cascades to content, matching this app's standing privacy/data-loss posture (no destructive action ever removes user content as a side effect of an unrelated action).
**Decision (the confidence chip was a labeling bug, not a scoring bug):** `ChatSourceRef.confidence` has been a real, per-chunk, per-query retrieval-relevance score since Phase 6B (ADR-037's evidence-based confidence scoring) - the value shown was already correct. The reported "Meeting Transcript: 50% / Transcript: 36%" issue was root-caused to the chip's label reading as if it meant something else (answer completeness/progress) to a user seeing it without that context. Fixed by relabeling the existing value ("N% match") rather than touching `RetrievalConfidenceScorer` or any scoring logic - a one-line UI change, not a retrieval-engine change, and explicitly the smaller of the two possible fixes once the actual root cause was confirmed by reading the code, not guessed at.
**Decision (no second LLM-quality caveat invented):** The brief asked for a "small model quality caveat, only if appropriate, never fabricated." `ModelCatalog` (ADR-036) has exactly one Chat LLM catalog entry - there is no second, lower-quality tier to caveat users about. Declined rather than inventing one, per this phase's own explicit no-fabrication instruction.
**Decision (a shared `friendlyErrorMessage()` utility, not a per-screen fix each time):** Raw exception text (`'$e'`) was reaching users in at least five places (Chat, the AI pipeline fallback widget, the meeting transcript error tab, model download, Profession Setup). Rather than hand-writing a friendlier string at each call site, `lib/core/utils/friendly_error.dart` centralizes pattern-matching on common failure substrings (network/timeout/storage-full/permission/corruption/missing-model/filesystem/OOM) into one `String friendlyErrorMessage(Object error)`, wired into all five sites plus a new dependency-free `hasInternetConnection()` (`dart:io`'s `InternetAddress.lookup`, no new package) for the one place a proactive check (rather than reactive error message) was the better fix - the AI Model Setup download flow.
**Alternatives considered:** Adding `folderId` directly to `Document`'s `@freezed` model. Rejected - forces a `build_runner` regeneration touching a widely-used core model for a feature that doesn't need it there, when dedicated repository methods deliver the same capability with zero risk to existing `Document` call sites. Rescoring or renaming `RetrievalConfidence`'s underlying thresholds to "fix" the percentage. Rejected - the number was never wrong; changing it would have been an unrequested, unjustified scope expansion into Phase 6B's already-tuned (if disclosed-as-unvalidated) retrieval logic. Inventing a second, deliberately-worse LLM catalog entry so a quality caveat would have something real to point at. Rejected outright - fabricating a model to justify a UI string is exactly the discipline ADR-036 already rejected for the same catalog.
**Tradeoffs:** None material - both decisions are minimum-blast-radius fixes to their actual root causes, consistent with this phase's own explicit instructions to prefer the smallest correct fix over a redesign.

### ADR-040 — Productivity Toolkit productization pass: a shared PDF-overlay primitive, not five separate features, and real graphics-state opacity for translucent fills
**Reason:** A 46-capability productization audit (`docs/v2/implementation/13-productivity-toolkit-productization-audit.md`) found that Add Text, Signatures, 5 Annotation types, and Watermark are all the same underlying operation given this app's rasterize-and-rebuild PDF strategy (ADR-034): draw new content on top of an already-rasterized page image before the same rebuild step every PDF Tool already runs. Building each as its own ad hoc implementation would duplicate that mechanism 8 times.

**Decision (one shared overlay primitive, `pdf_overlay.dart`/`pdf_overlay_service.dart`):** `PdfOverlayElement` (`Text`/`Image`/`Rect`/`Line`, normalized 0.0-1.0 page-relative coordinates) plus `buildOverlaidPageContent` (a `pw.Stack`/`pw.Positioned` composition drawn over the base page image) plus `PdfOverlayService.applyOverlays` (mirrors `PdfCompressionService`'s exact rasterize-then-rebuild loop and `try/finally` temp-file discipline, ADR-032). `addImagePageToDocument` (used by every existing PDF Tool) is now a thin wrapper around the new `addOverlaidImagePageToDocument` with an empty overlay list - one page-construction implementation, not two.

**Decision (redaction will NOT reuse this primitive):** A vector shape drawn in the same PDF page as the base image still leaves that image's own pixel data fully intact and separately extractable (any tool reading the embedded image XObject directly recovers the "redacted" content underneath) - the exact "black box over recoverable content" anti-pattern real redaction must avoid. Real redaction requires blacking out pixels of the rasterized image itself, before it's ever embedded - a distinct, `package:image`-level operation, deliberately not built on this overlay mechanism. Documented here so a future redaction implementation doesn't reach for the convenient-but-wrong tool.

**A real bug found and fixed during this feature's own required visual verification, not before:** `pw.BoxDecoration`'s fill goes through `PdfGraphics.setFillColor`, confirmed by reading `graphics.dart`/`decoration.dart` directly to only ever emit the PDF `rg` operator (red/green/blue) - a translucent `PdfColor`'s alpha component is silently ignored by that path. A real generated PDF (`test/manual/generate_pdf_overlay_demo_test.dart`) showed the Highlight rect rendering fully opaque despite an explicit 0x66 (~40%) alpha component, before this was caught. Fixed by wrapping filled/bordered rects in `pw.Opacity` (which correctly emits the PDF graphics-state `/ca` operator via `PdfGraphicState(opacity:)`) using the color's own alpha, with the underlying fill/border color's alpha reset to fully opaque (since the real transparency now comes from the wrapping `Opacity`, not the color itself). Re-verified visually after the fix: an opaque yellow rect partially covered by the translucent highlight now shows a genuine three-region blend (pure yellow / blended / pure highlight-over-background), not two flat opaque colors.

**Alternatives considered:** A separate implementation per feature (Add Text, each of the 5 annotation types, Watermark). Rejected - the productization audit's own explicit finding that this duplicates one mechanism 8 times, and directly contradicts this pass's own "reusable infrastructure layer, not ad hoc" instruction (already applied to Batch Processing's own design in the same audit). A `Canvas`-based freeform drawing API mirroring Flutter's own `CustomPainter` more closely. Rejected as unnecessary complexity - `package:pdf`'s own `pw.CustomPaint`/`PdfGraphics` primitives (already proven in this codebase, `contact_icons.dart`) are sufficient for every element kind this pass's own audit identified as needed (text/image/rect/polyline covers Add Text, Signatures, Highlight, Underline, Strikethrough, Freehand, Shapes, Arrows, and Watermark).

**Tradeoffs:** Inherits the same disclosed rasterize-and-rebuild quality cost every PDF Tool already carries (R-33) - even a page with no overlay at all still passes through one rasterize/JPEG-re-encode cycle, since that's this app's whole PDF-manipulation strategy, not something this feature introduces or can avoid.

**Status:** Accepted, done (P0-2 of the Productivity Toolkit productization pass). 7 new tests (`pdf_overlay_service_test.dart`) plus a manual visual-verification script (`generate_pdf_overlay_demo_test.dart`), all passing. 107/107 passing in `test/services/toolkit/` + `test/features/student_toolkit/` (was 100), `flutter analyze` clean. **Date:** 2026-08-13.

### ADR-041 — PDF Edit screen: user-facing Add Text/Signatures/Annotations/Watermark, built entirely on ADR-040's shared overlay primitive, never a parallel mechanism

**Reason:** P0-2 (ADR-040) built the shared `PdfOverlayElement`/`PdfOverlayService` primitive but no UI reached it yet. P0-3 is that UI - a single "Edit PDF" screen (`pdf_edit_screen.dart`) covering Add Text, Signatures (draw/type/import), 5 Annotation types (Highlight/Underline/Strikethrough/Freehand/Shapes/Arrow), and Watermark, each tool constructing the appropriate `PdfOverlayElement` and routing through `PdfOverlayService.applyOverlays` at save time - no separate rendering/editing path per tool, per this pass's own explicit instruction.

**Decision (editor state, `pdf_edit_providers.dart`):** `PdfEditController extends Notifier<PdfEditState>` mirrors `PdfOrganizeController`'s established "rasterize every page upfront at load time" pattern - `pickPdf()` rasterizes all pages once (at `kPdfOutputDpi`, not the smaller thumbnail DPI, since a full-screen single-page editing surface needs to stay legible for precise placement - a disclosed memory tradeoff, every page held in memory for the session's life). `PdfEditAnnotation` wraps a `PdfOverlayElement` with the two pieces of bookkeeping only the *editor* needs (`id` for select/drag/delete, `pageIndex` since the element itself carries none). A single `addAnnotation`/`updateAnnotation`/`deleteAnnotation` path means undo/history bookkeeping (a full-map snapshot stack, not a diff log - this editor's real scale is a handful of annotations across a few pages, matching this app's own "don't over-engineer for a scale that doesn't exist" discipline) exists in exactly one place regardless of which of the 8 tools produced the mutation. `buildResultBytes()`/`save()` call `PdfOverlayService.applyOverlays` directly - the exact same primitive ADR-040 built, with zero new PDF-writing code.

**Decision (own page type, not `PdfSplitProviders.PdfPageThumbnail`):** `PdfSplitController`/`PdfOrganizeController`'s existing `PdfPageThumbnail` (`{pageIndex, jpegBytes}`) is sufficient for a thumbnail *grid*, where the grid itself lays out every tile. The editor's single-page canvas needs the page's own pixel dimensions to fit one page into its available box and convert screen-space drags to normalized coordinates - `PdfPageThumbnail` never carried them (nothing before this pass needed them). Rather than widen a struct three other controllers already depend on, P0-3 defines its own `PdfEditPage` (`{pageIndex, jpegBytes, width, height}`) - `RasterizedPdfPage` already produces `width`/`height`, so this only keeps values `PdfSplitController.pickPdf()`/`PdfOrganizeController.pickPdf()` already discard, not new rasterization work.

**Decision (canvas coordinate conversion generalizes `ScanPageEditorScreen`'s existing precedent):** `ScanPageEditorScreen`'s `_fitImageToBox` + screen-space drag handles + source-space conversion only at commit time is this codebase's established pattern for screen↔PDF-space conversion. `_PdfEditCanvas` generalizes it: display-space drag positions convert to NORMALIZED (0.0-1.0) coordinates continuously (dividing by the current display size), which is inherently DPI/zoom/page-size-independent - there is no separate "zoom" control in this pass, since the canvas always fits the full page to its available box, so display size *is* the zoom level.

**Decision (real graphics-state text opacity/rotation, additive to `PdfOverlayText`):** Watermark needs semi-transparent, rotated text - `PdfOverlayText` gained `opacity`/`rotationDegrees`/`italic` fields (defaults `1.0`/`0`/`false` reproduce the exact widget tree that existed before, so no P0-2 caller's output changes) rendered via `pw.Opacity(pw.Transform.rotate(pw.Text(...)))`. `opacity` uses the same real graphics-state mechanism ADR-040's own bug fix established for `PdfOverlayRect` (`TextStyle.color`'s own alpha is subject to the identical `setFillColor`-ignores-alpha behavior) - not a second, independently-verified fix, the same one applied to a second element type.

**Decision (Arrow reuses `PdfOverlayLine`, not a new element type):** An arrowhead is one continuous polyline - shaft (start→end) plus two short back-angled barb segments, the pen retracing the tip point imperceptibly for a solid stroke - built from the exact same `PdfOverlayLine` primitive Underline/Strikethrough/Freehand already use. Zero new `PdfOverlayElement` subtypes needed for the full P0-3 tool set.

**Decision (drawn signatures render to transparent PNG via `package:image`, no new dependency):** `signature_pad_dialog.dart` captures finger/stylus strokes and renders them to a `numChannels: 4` fully-transparent-background PNG (never JPEG, which has no alpha) using `package:image`'s own `img.drawLine`/`img.fill` - the same dependency Compress/Resize/Scanner already use for their own image pipelines.

**A real bug found and fixed during this feature's own required visual verification** (`test/manual/generate_pdf_edit_demo_test.dart`, driving `PdfEditController` end to end - distinct from ADR-040's own demo script, which only exercised the shared primitive in isolation, not the editor's tool-specific element construction): the typed-signature demo annotation used `PdfOverlayText`'s default black color on `FakePdfPageRenderingService`'s own pure-black page-0 background - invisible by coincidence, the exact same category of demo-authoring mistake ADR-040 already documented once for its own underline color. Not an app bug; fixed in the demo script by giving the typed signature an explicit white color, then re-verified visually - "Jane Doe" is now clearly visible, confirming the typed-signature path genuinely renders.

**Alternatives considered:** A dedicated redaction tool built on this same overlay mechanism. Rejected per both ADR-040's own explicit prohibition and this pass's own instruction - a vector shape drawn over a page still leaves the underlying rasterized image's own pixels fully intact and separately recoverable, the "black box over live content" anti-pattern real redaction must not be. Real redaction remains a distinct, future, `package:image`-level pixel-blackout operation, deliberately not started here.

**Tradeoffs:** Highlight/Rectangle/Line annotations are drag-to-place-once, not re-editable after commit this pass (`_AnnotationWidget` renders them as `const SizedBox.shrink()` rather than a second draggable widget) - only Text and Image elements support post-placement drag/resize. A disclosed scope boundary, not an oversight: re-editing a committed shape would need hit-testing against an arbitrary rect/polyline, not just a bounding box, and the pass's own priority was full tool coverage over full re-editability of every tool.

**Status:** Accepted, done (P0-3 of the Productivity Toolkit productization pass). 20 new tests (`pdf_edit_controller_test.dart`) plus a manual visual-verification script (`generate_pdf_edit_demo_test.dart`) exercising all 8 tools + Watermark across a 2-page document, visually inspected (both pages) and confirmed genuinely baked into the real output PDF, not merely displayed in the editor's widget tree. 127/127 passing in `test/services/toolkit/` + `test/features/student_toolkit/` (was 107), `flutter analyze lib/` clean. **Date:** 2026-08-17.

### ADR-042 — Permanent PDF Redaction: a pixel-level rewrite, a deliberately separate mechanism from ADR-040/ADR-041's overlay infrastructure

**Reason:** ADR-040 explicitly identified redaction as unsafe to build on the shared overlay mechanism: a `PdfOverlayElement` (e.g. a black `PdfOverlayRect`) is a *second*, separate vector object drawn on top of an unmodified base page image - the original image XObject stays fully embedded and separately extractable underneath, exactly the "black box over recoverable content" anti-pattern real redaction must not be. P0-4 needed a genuinely different mechanism: one where the selected region's original pixel data does not exist anywhere in the produced file, not one where it's merely covered.

**Decision (rasterize → burn pixels → rebuild, never overlay):** `pdf_redaction.dart` defines `RedactionRegion` (normalized 0.0-1.0 coordinates, same convention as `PdfOverlayElement`) and two pure functions: `burnRedactions(image, regions, width, height)` (mutates a decoded `img.Image`, overwriting every pixel inside each region to opaque black via `package:image`'s own `fillRect` - confirmed by reading `fill_rect.dart` directly that a fully-opaque color takes the fast "replace every channel" path, `pixel.set(color)`, not an alpha-blend, so nothing of the original pixel value survives) and `redactJpegBytes` (decode → `burnRedactions` → re-encode). `PdfRedactionService.applyRedactions` structurally mirrors `PdfOverlayService.applyOverlays`'s exact rasterize-then-rebuild loop and `try/finally` temp-file discipline (ADR-032), but calls `redactJpegBytes` (via `compute()`, an isolate, for pages that have a region) instead of `addOverlaidImagePageToDocument` - the redacted page's only representation in the output PDF is this already-sanitized image, embedded via the same `addImagePageToDocument` every other PDF Tool uses for a plain, non-overlaid page. A page with no region rebuilds with its original rasterized bytes unchanged, the same "strict superset of the plain rebuild" property ADR-040 established.

**The actual security argument, stated precisely:** This app's whole PDF strategy (ADR-034) already rasterizes every page to a flat JPEG image with no text or vector layer at all, for every PDF Tool, whether or not redaction is involved - that is what R-33 already discloses (permanent loss of text-selectability, by design). This means, by the time `PdfRedactionService` runs, there is no original PDF text-object graph left in the output *at all*, redacted region or not - only pixels. Redaction's own, additional contribution on top of that inherited property is narrower and more precise: the *specific pixels* inside a selected region are overwritten before that image is ever embedded, so even someone extracting the embedded JPEG XObject directly (bypassing any PDF viewer) gets a file whose redacted-region bytes are genuinely gone, not merely obscured by something drawn in front of them.

**What this does NOT claim:** `Printing.raster()` itself is a native platform channel with no implementation under `flutter test` (R-32) - this pass could not verify on a real device that rasterization behaves identically for every real-world PDF construct (transparency groups, layered/OCG content, unusual embedded fonts). If some exotic real PDF caused `Printing.raster()` to omit or mishandle content in a way that left residual data outside a redacted region, that would be an R-32/R-33-class gap this feature *inherits*, not one redaction's own pixel-burn step could introduce or fail to catch - see R-41 (`04-risk-register.md`) for the explicit, disclosed limitation and the real-device verification this claim still needs before recommending the feature for genuinely sensitive real-world documents (legal/medical/financial PII).

**A concrete, automated proof this pass could run:** `pdf_redaction_test.dart`'s "security regression suite" decodes the actual returned pixel data (not just comparing output byte lengths) and asserts every channel inside a redacted region is exactly black while every pixel outside is untouched - a test that would fail immediately if this feature had instead drawn a vector rectangle over an untouched base image. A second test builds a page with genuinely rendered text ("CONFIDENTIAL: SSN 123-45-6789", via `package:image`'s own bitmap-font drawing) and confirms that string is not present anywhere in the final PDF's raw bytes after redaction - the literal automated version of the P0-4 spec's "attempt text extraction" manual-verification step. (That specific test's result is also true for a page with *no* redaction applied, since no page this pipeline produces ever has an extractable text layer - the property unique to redaction itself, that the selected pixels are gone rather than never-were-text, is what the pixel-decode tests prove.)

**Decision (its own tool type, `ToolkitToolType.pdfRedact`, not folded into `pdfEdit`):** `pdfEdit`'s saved outputs still contain their full original page content underneath any overlay; `pdfRedact`'s outputs have had the selected regions' original pixels permanently overwritten - a materially different security property a saved-file record should not blur by sharing a tool type.

**Decision (destructive-confirmation UX, `showDestructiveConfirmDialog`, ADR-031):** Redact PDF's screen shows a persistent banner ("Redaction permanently removes the selected content from the exported copy") the whole time regions are being drawn, then a Preview step (the exact `buildResultBytes()` output, already redacted - never a fake "here's roughly what it'll look like"), then this app's one existing destructive-confirmation dialog (`confirm_dialog.dart`, Phase 4A) before `save()` ever runs - reusing the established pattern rather than inventing a second one, and giving the final confirm action the same `ColorScheme.error`-styled button treatment as every other "this cannot be undone" action in the app.

**Alternatives considered:** Drawing an opaque `PdfOverlayRect` and calling it redaction. Rejected outright - explicitly the anti-pattern ADR-040 named and this pass exists to avoid; the underlying image XObject would remain fully embedded and extractable. A true PDF page-tree editor that could delete specific text/graphics objects in place. Rejected for the same license/dependency reason ADR-034 already rejected it for the whole app (no permissively-licensed native PDF object-tree editor exists for Flutter; the alternative, `pdf_manipulator`, is AGPL-3.0, unsuitable for a closed-source app). Redacting only the specific region's rasterized sub-image (crop, blacken, re-composite) rather than the whole page. Rejected as unnecessary complexity for no security benefit - every page already gets rasterized+re-encoded regardless (ADR-034's inherited cost), so operating on the full page image is no more expensive and is simpler to reason about correctness for (one image, one set of regions, no separate crop/composite step that could itself introduce a boundary bug).

**Tradeoffs:** Inherits the same disclosed rasterize-and-rebuild costs every PDF Tool already carries (R-33) - even an unaffected page still passes through one rasterize/JPEG-re-encode cycle, and every affected page loses any residual print/zoom quality a true vector redaction could have preserved (moot here, since ADR-034 means no page in this app's output ever has vector content regardless). Highlight/Rectangle-style re-editing after a region is drawn (drag to move, corner-handle to resize) is supported, but there is no "undo a mistaken redaction after saving" - by design, matching the feature's own stated purpose (once saved, the content really is gone), disclosed explicitly in the confirm dialog's own copy.

**Status:** Accepted, done (P0-4 of the Productivity Toolkit productization pass). 26 new tests (12 in `pdf_redaction_test.dart` covering the pixel-burn primitive/service including the text-extraction and security regression proofs, 14 in `pdf_redact_controller_test.dart`) plus a manual visual-verification script (`generate_pdf_redaction_demo_test.dart`) producing before/after PDFs from a page with genuinely rendered text and an image-like block, visually inspected and confirmed both target regions are fully and exclusively blacked out while unrelated content survives untouched. 153/153 passing in `test/services/toolkit/` + `test/features/student_toolkit/` (was 127), `flutter analyze lib/` clean. Real-device verification against born-digital PDFs with genuine text/vector content remains outstanding (R-41) - the claim this pass can make is that the pixel-burn mechanism itself is correct against whatever image the rasterization step hands it, not that `Printing.raster()`'s own real-world behavior has been independently verified on-device. **Date:** 2026-08-17.

### ADR-043 — Page Management: a real PDF `/Rotate` attribute for rotation, one shared page-composer primitive for Rotate/Delete/Extract/Insert/Duplicate/Replace/Reorder

**Reason:** P0-5's audit of the existing Merge/Split/Organize services confirmed all three already operate exclusively on rasterized pages (ADR-034) - `PdfOrganizeService.organize()` already supported arbitrary reordering *and* duplicate page indices in one call, meaning Reorder/Extract/Duplicate/Delete were already, structurally, the same primitive under a narrow single-source API. The one genuinely new capability this phase needed was rotation, and the one genuinely new *kind* of operation was pulling pages from a second source (Insert/Replace) - everything else was a matter of generalizing what already existed, not inventing a new mechanism.

**Decision (rotation is a real PDF page attribute, not a pixel transform):** `package:pdf`'s low-level `PdfPage.rotate` field (`PdfPageRotation` enum: `none`/`rotate90`/`rotate180`/`rotate270`, exported from `package:pdf/pdf.dart`) sets the actual `/Rotate` entry in the PDF page dictionary - confirmed by reading `pdf/obj/page.dart` directly (`params['/Rotate'] = PdfNum(rotate.index * 90)`). This is a standard, first-class PDF feature every viewer honors on display; setting it is zero-recompute and zero-quality-loss, since the underlying JPEG pixel data is never touched, only the page's own presentation. `pw.Document`'s widget-layer `Page` constructor doesn't expose this directly, but the underlying `PdfDocument` (`doc.document`, a public field) does via `pdfPageList.pages` (also public) - `PdfPageComposerService` sets `doc.document.pdfPageList.pages.last.rotate` immediately after adding each page, before `doc.save()`. Verified in `pdf_page_composer_test.dart` by a raw byte/string search of the output PDF for the literal `/Rotate 90`/`/Rotate 180`/`/Rotate 270` tokens (these are plaintext in the page dictionary, not inside compressed stream data) - a real, conclusive proof, not an assumption about `package:pdf`'s internals.

**Decision (`PdfPageComposerService`, one shared "rasterized pages -> PDF" builder):** `pdf_page_composer.dart` defines `PdfPageInput` (jpeg bytes + dimensions + rotation) and `PdfPageComposerService.compose(List<PdfPageInput>)` - deliberately does no rasterization itself, just builds a document from pages the caller already has in hand. `PdfOrganizeService.organize()` (existing, public, tested) now delegates its own page-building step to this composer internally - its own signature/behavior/tests are completely unchanged, so "Organize Pages"' prior guarantees hold exactly as before. The richer `PdfOrganizeController` (P0-5's actual UI-facing capability) calls the composer directly, since Rotate/Insert/Replace need capabilities (per-page rotation, multi-source pages) `PdfOrganizeService`'s narrow single-source API was never meant to express.

**Decision (self-contained `PdfPageSlot`, no lazy source-index indirection, no repeat rasterization):** Every page in a Page Management session (`PdfOrganizeController`) is rasterized once, at pick/insert/replace time, and held directly as `{jpegBytes, width, height, rotation}` - not a reference back into a source file re-rasterized later. This eliminates a real, previously-accepted inefficiency: the pre-P0-5 "Organize Pages" screen rasterized once at `kPdfThumbnailDpi` for its grid *and again* at `kPdfOutputDpi` inside `PdfOrganizeService.organize()` when the user applied changes. Every mutation (reorder/rotate/delete/duplicate) is now pure list/metadata manipulation with zero further rasterization until the one, final `compose()` call - Rotate/Delete/Extract/Duplicate/Reorder all reduce to "which `PdfPageInput`s, in which order, with which rotation," and Insert/Replace additionally splice in pages rasterized from a second source (reusing `PdfMergeInput`'s existing `.pdf`/`.image` distinction for what that second source can be).

**Tradeoff (accepted, disclosed):** Every page is held in memory at `kPdfOutputDpi` (150, not 72) for the session's life - the same tradeoff `pdf_edit_providers.dart`/`pdf_redact_providers.dart` already accepted for the identical reason (P0-3/P0-4), now extended to Page Management. A large-page-count document held in a Page Management session uses more memory than the old thumbnail-only design did; in exchange, the double-rasterization cost at Apply-Changes time is gone entirely.

**Decision (Replace's 1:1 vs 1:many mapping):** Replacing multiple selected pages accepts either a replacement source with exactly as many pages as selected (1:1, in slot order) or exactly one replacement page/image (applied to every selected page) - anything else (e.g. a 3-page replacement PDF against 2 selected pages) is refused with a specific, actionable error naming the expected count, rather than silently guessing an ambiguous mapping.

**Alternatives considered:** Rotating the rasterized bitmap itself (`img.copyRotate`) before re-embedding. Rejected - real recompute/re-encode cost and generation loss for zero benefit over the real PDF attribute, which every viewer already honors natively; the only reason to rotate pixels would be if `/Rotate` weren't respected somewhere in this app's own pipeline, which isn't the case (this app's own `Printing.raster()`-based rasterization, used by every other PDF Tool, is a standard PDF renderer and honors `/Rotate` like any other). A parallel, separate "Page Manager" screen distinct from "Organize Pages." Rejected - Organize's existing reorder/extract-via-delete capability is a strict subset of Page Management's, so extending it in place (same route, same tool tile, same `ToolkitToolType.pdfOrganize`) avoids exactly the "duplicate PDF rendering mechanism" anti-pattern this productization pass exists to prevent.

**Status:** Accepted, done (P0-5 of the Productivity Toolkit productization pass). 44 new tests (8 `pdf_page_composer_test.dart`, 36 `pdf_organize_controller_test.dart` covering all 27 P0-5 spec scenarios) plus the 5 pre-existing `pdf_organize_service_test.dart` tests re-verified passing unchanged after the internal refactor, plus a manual visual-verification script (`generate_pdf_page_management_demo_test.dart`) driving a combined rotate+delete+duplicate+insert+replace+reorder sequence against a synthetic 6-page mixed-content document, visually inspected page-by-page (rotation genuinely sideways in the viewer, duplicate/inserted/replaced pages each visually distinct, deleted page absent, reorder moved the correct page) plus a separate Extract output confirmed to contain exactly the selected two pages in working order. 198/198 passing in `test/services/toolkit/` + `test/features/student_toolkit/` (was 153), `flutter analyze lib/ test/` clean. Real-device rasterization of genuinely varied real-world PDFs (different page sizes/orientations, actual embedded vector/text content) remains unverified, the same standing limitation as R-32/R-41. **Date:** 2026-08-17.

### ADR-044 — Images ↔ PDF + PDF Search foundation: reuse over reinvention, JPEG-only image export, page-indexed offline search via an already-pinned dependency, no OCR

**Reason:** P0-6's audit of Scanner/Merge/Organize/PdfPageRenderingService found that "combine images into a PDF" and "read a PDF's pages as images" already existed as *internal* mechanisms inside other tools (Scanner's own image→PDF path, `PdfPageRenderingService.rasterizePages`) but had never been exposed as their own standalone, general-purpose tools; separately, `read_pdf_text` (already a pinned dependency, used by Documents' `PdfParser` for whole-document extraction) turned out to expose a page-indexed extraction method (`getPDFtextPaginated`) neither this app nor the earlier audit had previously used - making real, offline, page-level PDF search achievable with zero new dependencies. This ADR covers three sub-features built on those findings.

**Decision (Images → PDF: `PdfPageComposerService` directly, no new PDF-writing code):** `ImagesToPdfController` decodes each picked image (`decodeToolkitImageOrThrow`, already used by every other image-consuming tool), holds it as a self-contained `ImageToPdfSlot` (bytes+dims+rotation, mirroring `PdfPageSlot`'s P0-5 precedent), and calls `PdfPageComposerService.compose()` directly - the exact same primitive Organize/Redact/Edit already share. Page sizing reuses Scanner's own already-shipped, already-correct convention (`ScannerPdfService`/`addImagePageToDocument`): each page's size is derived from *that image's own* pixel dimensions at `kPdfOutputDpi` (the same "virtual DPI" Scanner already uses, not a new constant) - a portrait photo produces a portrait page, a landscape photo produces a landscape page, never a forced A4/Letter shape. Rotation reuses P0-5's real `/Rotate` PDF attribute mechanism verbatim. Images can be added from the gallery (`ToolkitImagePickerService.pickMultipleFromGallery`) or the file/document picker (`ToolkitFilePickerService.pickMultiplePdfsOrImages`, already jpg/jpeg/png-scoped) - both funnel through the same decode-and-append path, so there is exactly one "how a new image slot gets created" implementation regardless of source.

**Decision (PDF → Images: `PdfPageRenderingService.rasterizePages` directly, JPEG-only export, no new dependency):** `PdfToImagesController` calls the exact same rasterization primitive Compress/Merge/Split/Organize already use - no new rasterization mechanism. **Format decision, explicitly scoped down from the spec's own "choose output format if supported":** JPEG only, no PNG option. `PdfPageRenderingService` always JPEG-encodes internally, before the temp file this class reads is ever written - there is no hook in its public interface to intercept pre-JPEG raw pixel data. Offering "PNG" would mean either widening the shared rendering interface every other PDF Tool depends on (real risk to code this pass doesn't otherwise touch), or silently re-encoding an already-JPEG-compressed image as PNG (a lossy-then-lossless round trip that isn't genuinely lossless, misleading to present as a real format choice). Per the spec's own "do not add format options current dependencies cannot reliably support" instruction, this is the honest choice. **DPI decision (deliberately two-tier, not P0-5's "rasterize once" pattern):** the page-selection grid uses `kPdfThumbnailDpi` (matching every other page-picker grid, Organize/Split); the actual export re-rasterizes only the *selected* pages at `kPdfOutputDpi`. Unlike P0-5 (where the same bytes served both display and final output), a PDF→Images grid and export serve genuinely different resolutions for potentially very different page subsets - rasterizing every page at full export quality just to populate a selection grid would waste memory on pages the user may never export. **Output decision:** one `ToolkitFile` row per exported page (mirroring `PdfSplitController.saveOutput`/`saveAll`'s own established multi-output pattern) rather than a ZIP archive - `archive` is a pinned dependency but Split's own precedent (already proven, already tested) is the better architectural fit; each exported image is independently viewable/shareable in Recent Files exactly like every other toolkit image output (`imageCompress`/`imageResize`) already is, with zero extra Recent Files handling needed. **Progress/cancellation:** genuinely new, small, and scoped to this one controller - `rasterizePages`'s stream is consumed with a progress callback per page and a cooperative cancel flag checked between pages; cancelling stops consuming further pages immediately, though a page whose native rasterization was already in flight still completes in the background before the next check - a disclosed, honest limitation of cooperating with a native platform-channel call this app doesn't control, not a fake "instant" cancel.

**Decision (PDF Search: page-indexed extraction via an already-pinned dependency, a dedicated viewer, no OCR):** `read_pdf_text`'s `getPDFtextPaginated(path)` (confirmed, by reading the plugin's own Android Java source directly, to be a real natively-implemented method, not a Dart-only stub) returns one string per page - genuine page-indexed text, distinct from Documents' `PdfParser`, which only ever calls the *other* method (`getPDFtext`, one flat whole-document string) since RAG/embedding has no need for page boundaries. `PdfTextSearchService` (new, Toolkit-scoped) wraps `getPDFtextPaginated` the same way `PdfParser` already wraps `getPDFtext` - same exception-handling shape, deliberately not the same interface (Documents' `DocumentTextExtractionService` is coupled to `Document`-owned DB storage, a different, heavier concern this pass's transient "read this file's text, don't persist anything about it" need doesn't have, mirroring `ToolkitFilePickerService`'s own established reasoning for not reusing `DocumentImportService`). Matching is pure, synchronous, and testable independent of extraction (`searchPdfPagesText`, `pdf_search_matcher.dart`) - case-insensitive substring counting per page, returning one `PdfSearchMatch` (page index + occurrence count) per page that has at least one hit. **Navigation granularity is honest, not invented:** `read_pdf_text` exposes no in-page character/coordinate positions, so "next/previous result" moves page to page, not occurrence to occurrence within a page - a genuinely different, coarser granularity than a text editor's "find next," disclosed rather than faked finer. **Viewer architecture:** a new dedicated single-page-at-a-time "View PDF" screen (`ViewPdfScreen`), not `printing`'s `PdfPreview` widget - confirmed by reading `PdfPreview`'s own constructor and its `PdfPreviewController`/`PdfPreviewCustomState` internals that no safe external "jump to page N" API exists, and no text-search capability exists at all. Reuses the exact rasterize-and-display-one-page pattern P0-3/P0-4/P0-5 already established for Edit/Redact/Organize, rather than depending on an undocumented internal widget API. **No OCR, explicitly:** for a PDF whose every page's extracted text is empty/whitespace (`hasNoSearchableText`), the UI shows "No searchable text found in this PDF" plus a disabled "Run OCR" affordance with an explanatory tooltip - never a false claim of searchability, and never an attempt to actually run OCR (ADR-015 remains in force; OCR stays its own, future, dedicated phase).

**Offline guarantee:** verified by direct code audit (not just asserted) - every new production file's import list was read directly; the only new external dependency touched is `read_pdf_text`, a native local PDFBox-Android/PDFKit wrapper with no network capability, already audited once for Documents' own use. No `http`/`dio`/socket/`Uri.parse`-for-network/WebSocket import appears anywhere in the seven new files this ADR covers.

**Alternatives considered:** A PNG export option for PDF→Images. Rejected (see above - not genuinely losslessly supportable without touching shared infrastructure). A ZIP archive output for PDF→Images. Rejected in favor of Split's own already-proven per-output-row pattern. Wrapping `printing`'s `PdfPreview` for the View PDF screen. Rejected after directly confirming it exposes no safe page-jump or search API. Reusing Documents' `DocumentTextExtractionService`/`PdfParser` directly for PDF Search. Rejected - wrong granularity (flat, not page-indexed) and wrong coupling (Document-owned persistence this transient toolkit flow doesn't need).

**Status:** Accepted, done (P0-6 of the Productivity Toolkit productization pass). 53 new tests (17 `images_to_pdf_controller_test.dart`, 14 `pdf_to_images_controller_test.dart`, 10 `pdf_search_matcher_test.dart`, 12 `view_pdf_controller_test.dart`) covering all 34 P0-6 spec scenarios, plus three manual visual-verification scripts producing real output: a 5-image (3 portrait, 2 landscape, one rotated) combined PDF, a 5-page mixed-content PDF exported to real JPEG images (all-pages and selected-subset), and a 4-page PDF searched for the spec's own exact example terms ("Azure Kubernetes Service"/"Kubernetes"/"Terraform"/"GitHub Actions") with correct per-page match counts and next/previous navigation confirmed - all visually inspected in the browser. 251/251 passing in `test/services/toolkit/` + `test/features/student_toolkit/` (was 198), `flutter analyze lib/ test/` clean. A direct offline-code audit confirmed zero network-related imports across all seven new production files. Real-device verification of `Printing.raster()`/`read_pdf_text` against genuinely varied real-world PDFs remains unverified, the same standing limitation as R-32/R-41/R-42. **Date:** 2026-08-18.

### ADR-045 — Offline OCR + Searchable PDF: `flutter_tesseract_ocr` for real per-word hOCR alignment, OCR folded into the existing Model Manager, no fabricated language support

**Reason:** P0-7's audit confirmed OCR was completely absent (`ocr_parser.dart` an explicit `UnimplementedError` stub since ADR-015) but the seam to build it on was already there: `ModelKind.ocr` existed in the model-lifecycle enum, rejected everywhere with "not available yet," and `ModelDownloadService`/`HttpModelDownloadService` (real HTTP-range-resume, `.part` files, ETag/Last-Modified validators, SHA-256 integrity - built for Whisper) was already generic enough to download any single file, not just Whisper's `.bin` models.

**Decision (engine: `flutter_tesseract_ocr`, not Google ML Kit):** ML Kit's on-device models download invisibly through Google Play Services with no size/progress/resume control this app could ever surface in its own Model Manager - violating this phase's own Phase 6 requirement outright, and excluding non-GMS Android devices entirely. `flutter_tesseract_ocr` (BSD-3-Clause, actively maintained - published within the 2 months before this audit, unlike the ~14-month-stale `tesseract_ocr` alternative) instead loads plain `.traineddata` files from an arbitrary on-disk path (`FlutterTesseractOcr.getTessdataPath()`), which drops straight into the existing `ModelDownloadService` with zero new download mechanism - the English model (`tessdata_fast/eng.traineddata`, 3.92 MB, size confirmed by directly inspecting the file's real GitHub blob page, not estimated) is `ModelCatalog.ocrEnglish`, a real `AiModelSpec` with `kind: ModelKind.ocr`.

**Decision (real per-word bounding-box alignment via hOCR, not a coarser fallback):** initial research (pub.dev's own published docs) suggested Android word/line bounding boxes weren't available from this plugin - directly reading its Android platform-channel source (`FlutterTesseractOcrPlugin.java`) overturned that: `extractHocr()` calls `TessBaseAPI.getHOCRText(0)`, Tesseract's real hOCR output with genuine per-word pixel bounding boxes, a materially better foundation than assumed. `hocr_parser.dart` (`parseHocrWords`, pure, zero native dependency, fully unit-testable) extracts each `ocrx_word` span's text and `bbox`; `ocr_page_text_layout.dart`'s `buildInvisibleWordOverlay` converts each word's pixel box into a normalized position and a font size derived from the word's own pixel height, placed as an invisible PDF text object at that position - real per-word alignment, not a page-level blob or an even-line-spacing guess. **Honestly disclosed limitation:** the invisible text's own font metrics (character widths, baseline) don't reproduce Tesseract's source glyph shapes exactly, so a hand-drawn selection rectangle in a real PDF viewer won't trace the visual word outline pixel-for-pixel the way a true PDF-native OCR pipeline (`tesseract --pdf`, which this Flutter plugin does not expose) would - see R-44.

**Decision (invisible text via `package:pdf`'s real `PdfTextRenderingMode.invisible`, reusing P0-3's overlay pipeline):** `PdfOverlayText` (`pdf_overlay.dart`, P0-3's Add Text/Signatures/Watermark primitive) gained one additive field, `invisible` (default `false`, every existing caller unaffected), which sets `pw.TextStyle.renderingMode` - confirmed by reading `package:pdf`'s own `graphics.dart`/`widgets/text.dart` that this maps straight through to the real PDF `Tr` (text-rendering-mode) operator, mode 3. The OCR text layer is drawn on top of the same rasterized page image via `addOverlaidImagePageToDocument` - the exact primitive every other "add content to a page" tool already shares - so the page's visual appearance is provably unchanged; only a real, searchable, copyable, invisible text layer is added underneath it.

**Decision (`SearchablePdfBuilderService`, one shared pipeline for every entry point):** `OcrSourcePage` (jpeg bytes + dims + optional rotation + optional `existingText`) is the unified input every entry point (Scanner's "Save Searchable PDF", Images to PDF's "Generate Searchable PDF", View PDF's "Run OCR") converts its own source into, mirroring `PdfPageInput`'s identical P0-5 role. For a page whose `existingText` is already known (extracted via `PdfTextSearchService`, P0-6, before this document was rasterized), OCR is never called for that page (scenario 26) - its real text is reused verbatim, spread evenly down the page (`buildEvenlySpacedLineOverlay`, since no bounding boxes exist for text that was never OCR'd), strictly more accurate than a redundant OCR pass would be. `doc.save()` is only called once, after every page has succeeded - a cancellation or per-page OCR failure partway through can never produce a truncated or corrupt output PDF, since nothing is written until the whole document is ready.

**Decision (model missing is a clean, proactive state, never a native crash):** `FlutterTesseractOcrPlugin.java`'s `TessBaseAPI.init()` call is never checked for success before use - a missing `.traineddata` file could crash natively rather than surfacing a catchable Dart exception. `OcrSessionController._run()` checks `InstalledModelRepository.getActiveForKind(ModelKind.ocr)` *before* ever reaching the native plugin, surfacing `OcrSessionState.modelMissing` as a clean, retriable UI state instead.

**Decision (OCR is optional in offline readiness, never blocking):** `OfflineReadinessCheck` gained a `required` field (default `true` for every pre-P0-7 check); `OfflineReadinessReport.isReady`/`.failingChecks` now only consider `required` checks. OCR's own check (`required: false`) is real and visible - not downloading the model never makes the app "not offline ready" the way skipping the LLM/embedding/speech-to-text models does, mirroring the Enhanced (second-tier) LLM model's own "never required" precedent.

**Decision (English only, architecture already language-ready):** this session could not independently confirm other `tessdata_fast` languages' real file existence/size (a GitHub tree-listing fetch for Telugu/Tamil came back inconclusive, and the spec's own "never show a fake option" instruction rules out shipping an unverified entry). `ModelCatalog`/`AiModelSpec`/`InstalledModel` are already fully generic on `kind`/`id`/`version` - a second language is one more real, verified catalog entry, zero architecture change.

**Alternatives considered:** Google ML Kit (rejected - no download/progress/resume control, GMS-only). The stale `tesseract_ocr` package (rejected - ~14 months without a release, bundled-assets-only traineddata loading incompatible with this app's "download after install" convention). A page-level or evenly-spaced-line invisible text layer for every page (rejected as the primary mechanism once `extractHocr`'s real per-word boxes were discovered - kept only as the fallback for pages whose text is known but was never OCR'd, where no box data could exist). Hand-writing a native Android MethodChannel around `TessBaseAPI` directly for pixel-perfect PDF-native OCR output (rejected - genuinely new native platform code, well outside this phase's scope, and against this app's own established "reuse an existing rendering mechanism, never invent a second one" discipline, ADR-034).

**Status:** Accepted, done (P0-7 of the Productivity Toolkit productization pass). 71 new tests across `hocr_parser_test.dart` (8), `ocr_page_text_layout_test.dart` (9), `searchable_pdf_builder_service_test.dart` (12), `ocr_model_download_test.dart` (6), `ocr_session_controller_test.dart` (8), plus one added scenario each to `view_pdf_controller_test.dart` and `model_download_controller_test.dart` (updated for OCR no longer being a rejected kind), plus 6 manual visual-verification scripts (`generate_ocr_searchable_pdf_demo_test.dart`) producing real PDFs (clean scan, 3-page multi-page, mixed born-digital+scanned, rotated, low-quality/blurred, blank) - each visually inspected in the browser (correct visual appearance, correct page count, `/Rotate` genuinely honored by a real PDF viewer) and, going one step further than prior phases' manual scripts, each PDF's own content streams were zlib-decompressed (`dart:io`'s `zlib`, matching `package:pdf`'s own default VM deflate implementation exactly) and the OCR'd word text confirmed literally present as real, extractable PDF content - not merely asserted from the code that adds it. `flutter analyze lib/ test/` clean; full toolkit+AI-models+OCR suite (308 tests) passing. `flutter_tesseract_ocr`'s own native OCR call has no implementation under `flutter test` (the same standing limitation as `Printing.raster`/`read_pdf_text`/Whisper - R-32 and successors) - every test above runs against `FakeOcrTextExtractionService`/`FakeModelDownloadService`; real-device OCR accuracy against genuine handwriting/print, and interactive text-layer selection/search in a real PDF viewer, remain unverified (R-44). **Date:** 2026-08-18.

### ADR-046 — PDF Security (password protect/unlock): `pdf_cos`/`pdf_document` for genuine Standard Security Handler encryption, own write-side key-derivation on top of the library's own verified primitives, full-scope open/unlock for any third-party encrypted PDF (explicit user decision)

**Reason:** P0-8's audit confirmed `package:pdf` (this app's sole existing PDF writer, ADR-034, every other Toolkit feature) has zero concrete encryption capability: `lib/src/pdf/obj/encryption.dart` defines only an abstract `PdfEncryption` with no subclass anywhere in the package, and `PdfDocument.encryption` is honored by the writer if set but nothing ever sets it. The package's usual companion, `pdf_crypto`, was investigated and found effectively dead - absent from the current `DavBfr/dart_pdf` GitHub monorepo, distributed only via the author's own private pub host, with a real, unresolved "can't import it" issue. A genuine password-protection feature therefore could not be built on this app's existing PDF infrastructure at all - the first P0 phase where that was true.

**Decision (scope: real open/unlock for ANY third-party encrypted PDF, not just this app's own output - an explicit user decision):** the spec's Workflow B/C ("Open protected PDF" / "Unlock PDF") has a real fork: supporting only PDFs this app itself protected needs no general-purpose parser (this app already knows the exact bytes it wrote), while genuinely opening an arbitrary encrypted PDF a user picks from anywhere requires a real PDF object-graph reader. This was surfaced to the user directly (not decided unilaterally) as a three-option tradeoff; **the user explicitly chose "Add a real PDF parser dependency"** - the full-scope, most capable option. Every design decision below (choice of `pdf_cos`/`pdf_document`, the `CosDocument.open`-based `inspect`/`checkPassword`/`removePassword` API) follows directly from that choice: this app can open, validate the password against, and losslessly unlock a copy of any Standard-Security-Handler-encrypted PDF, not merely its own.

**Decision (dependency: `pdf_cos` + `pdf_document`, not Syncfusion Flutter PDF):** Syncfusion has real RC4/AES-256 encryption but requires a Community License (revenue/team-size caps, register-and-agree-to-terms) or a commercial license - inconsistent with this app's no-accounts-anywhere stance, and its own PDF writer would duplicate the `package:pdf` architecture this app has consistently avoided doing (ADR-034's own discipline never to run two independent PDF-generation stacks side by side). `pdf_cos`/`pdf_document` (Apache-2.0, verified publisher `benmilanko.com`, from the `ben-milanko/dart-pdf` project) were instead verified by directly reading their crypto/document/object-model source, not trusted from pub.dev metrics (which looked thin - "0 likes, published 3 days ago" - a legitimate reason for skepticism that direct source reading resolved): `crypto/standard_security_handler.dart`'s `StandardSecurityHandler` implements the real ISO 32000-1 §7.6.3.3 Standard Security Handler (V1/V2/V4/V5, RC4 and AES), confirmed against the spec's own Algorithm 2/3/4/5/7 constants and structure (the exact 32-byte password-padding string; Algorithm 2's truncated-per-round 50-round MD5 loop versus Algorithm 3's differently-shaped full-digest-per-round loop for `/O` - two genuinely different loop shapes a naive reimplementation could easily conflate, both present and correct here) - `crypto/rc4.dart` and `crypto/aes.dart` are equally verified-correct, textbook KSA/PRGA RC4 and FIPS-197 AES respectively.

**Decision (this app's own write-side key-derivation, `pdf_encryption_algorithms.dart`, reusing only the library's own already-verified ciphers):** `StandardSecurityHandler` has exactly one public constructor, `fromEncrypt()` - it *authenticates against* an existing `/Encrypt` dictionary; nothing in the public API *computes* a new one for a chosen password. Rather than reimplementing RC4/AES/MD5 (real cryptographic-correctness risk this app has no business taking on), `pdf_encryption_algorithms.dart` implements only the PDF-spec-specific key-derivation glue (Algorithms 2/3/4 - computing `/O`, `/U`, and the file encryption key from a chosen password, `/ID`, and permission bits), calling the library's own already-verified `rc4()`/`Aes` functions for every actual cipher operation. Correctness was proven with an unusually strong technique, not merely self-consistency: `pdf_encryption_algorithms_test.dart` builds a synthetic `/Encrypt` dictionary from this app's own computed `/O`/`/U`, then feeds it to the library's own independent read-side `StandardSecurityHandler.fromEncrypt()` and confirms it authenticates the right password, rejects the wrong one, and rejects a mismatched `/ID` - an independent verifier, not this app's own code checking its own work.

**Decision (full, non-incremental rewrite for both protect and unlock, never an incremental update):** `PdfSecurityService.protect()`/`.removePassword()` both read every object from the source document and re-serialize the *entire* file fresh (`_writeFullRewrite`, built directly on `pdf_cos`'s public `CosSerializer`/`CosXrefTableWriter` primitives, since neither existing high-level writer fit: `CosDocumentBuilder` renumbers every object from 1, breaking existing internal references, and computes `/ID` only after writing all bytes - incompatible with needing the `/ID` to derive the encryption key *before* encrypting any object). This is a real security property, not just a correctness one: an incremental update that merely appended a new `/Encrypt` dictionary to an existing file would leave the original plaintext object bytes still physically present earlier in the same file, trivially recoverable with any PDF repair tool. A full rewrite never writes a plaintext byte of page content anywhere in `protect()`'s output.

**Decision (encryption standard shipped: Revision 4, AES-128, `/V 4`/`/AESV2`):** `computeEncryptionKeys()` hardcodes 128-bit keys; `protect()`'s `/Encrypt` dictionary sets `CF/StdCF/CFM = AESV2`, `StmF`/`StrF = StdCF` - real AES-128-CBC content-stream and string encryption, ISO 32000-1 Revision 4, not R2/R3's older, weaker RC4-only handler, and not R6/AES-256 (R5/R6 was available in `StandardSecurityHandler` but not selected - AES-128/R4 has materially broader legacy-reader compatibility, and this phase's spec did not ask for R6 specifically). Permission bits (`pdf_permissions.dart`, `toPBits()`/`fromPBits()`) cover exactly the four capabilities the underlying Standard Security Handler's `/P` bit field genuinely enforces per ISO 32000-1 Table 22 (print, modify, copy/extract, annotate) - per the spec's own "do not expose security options the underlying library cannot actually enforce" instruction, no UI checkbox exists for a permission this handler doesn't real-encode.

**Decision (owner vs. user password):** `protect()` accepts an optional, separate `ownerPassword`, defaulting to empty - per the PDF spec's own convention, an empty owner password still produces a real, distinct owner key (not "no protection"), and `checkPassword`/`removePassword`/`CosDocument.open` all try the supplied password as user first, then owner, matching `StandardSecurityHandler`'s own built-in Algorithm 7 fallback. The Protect PDF screen (`pdf_protect_screen.dart`) only exposes the user password field, matching the spec's own minimal-UI mockup - the owner-password parameter exists in the service layer for completeness/testability, not surfaced in this pass's UI.

**Decision (error handling - no silent failures, every path user-visible):** `PdfSecurityException` (`{message, isWrongPassword}`) is thrown, never swallowed, for: empty password, an already-encrypted source (`protect()` refuses to double-encrypt), a corrupted/unreadable source, a wrong existing password on unlock (`isWrongPassword: true`, so the UI can show "Incorrect password." specifically rather than a generic failure and allow immediate retry), and an unsupported encryption method (`UnsupportedEncryptionException`, re-wrapped with a specific message rather than crashing). View PDF's `pickPdf()` calls the real, unfaked `PdfSecurityService.inspect()` before ever attempting rasterization - encrypted PDFs route to a password prompt (`needsPassword`) instead of a confusing generic rasterization failure; anything else unreadable (corrupted bytes, truly broken PDFs) deliberately falls through to the exact same rasterization/error path every other unreadable PDF has always used, rather than a second, parallel "is this corrupted" opinion that could disagree with the established one (a real regression this pass found and fixed in its own test suite - see the P0-8 group in `view_pdf_controller_test.dart`).

**Offline guarantee:** verified by direct code audit - `pdf_cos`/`pdf_document` are pure-Dart, no native code, no plugin, no network capability of any kind (confirmed by reading every file under both packages' `lib/`); no `http`/`dio`/socket/`Uri.parse`-for-network import appears anywhere in `pdf_security_service.dart`, `pdf_encryption_algorithms.dart`, `pdf_permissions.dart`, or either new controller/screen file. Password protect/unlock never leaves the device.

**Alternatives considered:** Syncfusion Flutter PDF (rejected - licensing friction incompatible with this app's no-accounts stance, and a second independent PDF-writer stack this app has consistently avoided). `pdf_crypto` (rejected - effectively dead, unreliable custom pub host, unresolved import-failure issue). Reimplementing RC4/AES/MD5 directly rather than depending on `pdf_cos`'s own primitives (rejected - real cryptographic-correctness risk this app has no need to take on when a verified implementation already exists). Scoping Workflow B/C to this app's own protected files only (rejected per the user's own explicit choice of the broader, real-parser option).

**Status:** Accepted, done (P0-8 of the Productivity Toolkit productization pass). 47 new automated tests: `pdf_encryption_algorithms_test.dart` (8, including the cross-validation-against-the-library's-own-independent-reader tests), `pdf_security_service_test.dart` (28), a new P0-8 group in `view_pdf_controller_test.dart` (5, including the regression fix described above), `pdf_protect_controller_test.dart` (5, new this pass - `ProtectPdfController`'s password/confirm validation, real protect()+independent-reopen, permission round-trip, save-to-`ToolkitFile`, reset). Plus 6 manual real-output verification scenarios (`generate_pdf_security_demo_test.dart`): 1-page, 6-page multi-page (page count independently re-verified via `pdf_document`'s own `PdfDocument.open(...).pageCount`), a permissions round-trip read directly off the real `/P` entry (not the service's own claim), an OCR-generated searchable PDF where a naive zlib-scan of the protected file's content streams finds **zero** occurrences of the known marker text (proof of genuine ciphertext, not a relabeled/hidden plaintext stream) and the unlocked copy restores it exactly, original-bytes-never-mutated, and offline corrupted-PDF/wrong-password error handling. The four most illustrative output PDFs (1-page protected/unlocked, OCR protected/unlocked) were delivered directly to the user for their own visual/interactive confirmation in a real PDF viewer, since this session's sandboxed browser preview pane did not composite frames for local file review (a session-specific tooling limitation, not a gap in the underlying verification - the cryptographic claims above were all independently proven in code, via `pdf_cos`'s own separate `CosDocument.open` read path and `pdf_document`'s own separate page-tree reader, not merely asserted by `PdfSecurityService`). `flutter analyze lib/ test/` clean. `flutter_tesseract_ocr`, `Printing.raster()`, and `read_pdf_text` remain the standing native-plugin real-device-verification gaps (R-32 and successors) unrelated to this ADR; `pdf_cos`/`pdf_document` are pure-Dart and have no such gap, but are newly-adopted dependencies with correspondingly less real-world mileage than `package:pdf` itself - see R-45. **Date:** 2026-08-18.

### ADR-047 — File-Manager Parity (P0-9): a separate `toolkit_folders` table reusing Documents' own proven logical-folder pattern, search/sort as pure client-side logic over the already-fetched list, multi-select as UI-only state, bulk delete/share as thin loops over already-existing single-item operations

**Reason:** P0-9's own audit (mandatory Phase 0, per the spec's explicit "inspect before assuming anything is missing" instruction) found the Recent Files screen (V2 Phase 5A onward) already implemented rename, favorite/star, duplicate, delete (with swipe + destructive confirmation), share (`share_plus`, real OS share sheet), and preview-before-delete - a materially more complete starting point than "a collection of tools with no file management" implied. What was genuinely absent: folders/folder navigation, move-to-folder, search, an explicit sort control, a dedicated Favorites view, multi-select, bulk delete/share, and graceful missing/corrupt-file handling in the list itself (only the PDF preview path had an `onError`).

**Decision (folders: a new `toolkit_folders` table, not Documents' shared `folders` table):** Documents already solved "logical folders in a database" for exactly this shape of problem (migration v15, V2.2 Production Hardening) - a generic `Folder` model (id/title/timestamps, no content-type coupling), a `FolderRepository` interface, and a nullable `documents.folder_id` column with **no real foreign key, validated at the repository layer** (an explicitly documented, already-established convention this schema uses repeatedly, e.g. `toolkit_files.tool_type`). Reusing the exact same `folders` table for toolkit files too was considered and rejected: Documents (imported source material for RAG/chat) and toolkit files (generated tool outputs) are unrelated content types this pass never audited together, and sharing one folder table would mean deleting or renaming a folder from either screen silently affects the other - real, unaudited cross-feature coupling for no actual benefit. Instead, migration v21 adds a new, separate `toolkit_folders` table (identical shape to `folders`) plus a nullable `toolkit_files.folder_id` column (same no-FK convention), and a new `SqfliteToolkitFolderRepository` implements the exact same `FolderRepository` interface `SqfliteFolderRepository` (Documents) does, reusing the `Folder` model class as-is - genuine architecture reuse (proven schema shape, proven repository contract, proven model), without the coupling risk of a shared table.

**Decision (search/sort: pure, stateless functions over the already-fetched list, not new queries):** `toolkitFileListProvider` already fetches every file on every load (Recent Files' own pre-existing behavior); `toolkit_file_query.dart`'s `filterToolkitFilesByQuery`/`sortToolkitFiles` (case-insensitive substring match; six sort orders: date newest/oldest, name A-Z/Z-A, size largest/smallest) are pure Dart functions run client-side against that already-in-memory list - no new SQL, no new repository methods beyond the folder-scoped `getInFolder`/`moveToFolder` migration v21 itself required. Kept deliberately separate from the widget layer (mirrring `pdf_search_matcher.dart`'s own "logic separable from I/O, directly unit-testable" precedent) rather than inlined into the screen's `build()`.

**Decision (the Recent tab keeps its exact pre-P0-9 behavior, unaffected by search/sort):** The Files screen is a `TabBar` (All Files / Recent / Favorites / Folders), not a single flat list, specifically so the one tab users already relied on (`Today`/`This Week`/`Older` grouping, always newest-first) stays byte-for-byte identical to what shipped in V2 Phase 5A - search and sort controls apply only to All Files/Favorites (the two genuinely new, general-purpose views), hidden entirely on Recent/Folders rather than shown-but-inert. All five pre-existing Recent Files widget-test scenarios were ported onto this new structure with zero behavior change (only the test harness needed updating for the new tab navigation - a mechanical port, not a rewrite).

**Decision (multi-select/bulk actions: thin orchestration over `ToolkitFileActions`, never a second file-operation pipeline):** `toolkitSelectionModeProvider`/`toolkitSelectedFileIdsProvider` are UI-only `StateProvider`s (never persisted, mirroring `selectedFolderProvider`'s own established convention). `ToolkitFileActions.deleteMany()` loops over the exact same `delete()` every single-file swipe-to-delete already calls (same on-disk-then-row order, same "missing file is not an error" tolerance) - bulk delete is provably not a second deletion implementation. Bulk share reuses `share_plus`'s own multi-file `ShareParams(files: [...])` directly - a real OS-level share-sheet capability already supported by the same dependency this app's existing single-file share already used, not a new cloud/upload mechanism of any kind.

**Decision (missing/corrupt-file handling: a cheap `File.existsSync()` check per row, `errorBuilder` on `Image.file`):** A file whose on-disk output was moved/deleted outside the app now renders a "Missing" status chip instead of the normal size/reduction label, and tapping it shows a snackbar instead of attempting `File.readAsBytes()` (which would previously have surfaced a raw, unhandled `FileSystemException`/broken-image render). `Image.file`'s `errorBuilder` (previously absent - only `PdfPreview`'s own `onError`, added in P0-1, existed) now covers the image-preview path the same way.

**Decision (duplicate names: explicitly not an error, matching Documents' and this app's own established convention):** Neither file titles nor folder titles carry a uniqueness constraint - two files or two folders may legitimately share a display name (a real, common scenario: "Scan.pdf" scanned twice), exactly as Documents' own folders already allow. This is proven with a dedicated test in both `toolkit_folder_repository_test.dart` and `toolkit_files_screen_test.dart` rather than assumed.

**Offline guarantee:** verified by direct code audit - every new file (`toolkit_folder_repository.dart`, `toolkit_folder_providers.dart`, `toolkit_file_query.dart`, `toolkit_files_screen.dart`, migration v21) contains no network-related import; `share_plus`'s OS share sheet is the only external-facing surface touched, and it was already audited/in use before this pass.

**Alternatives considered:** A shared `folders` table across Documents and toolkit files (rejected - unaudited cross-feature coupling). Filesystem-based real folders (rejected - fights this app's existing app-private-storage path scheme, `toolkit_paths.dart`, for no benefit over a logical DB folder). A single flat "Files" list with no tabs (rejected - would have required changing Recent's own established grouped-by-day behavior to accommodate search/sort, a real regression risk for zero benefit, versus scoping the new controls to the tabs that actually need them). Per-row leading checkboxes baked into `KnowledgeSourceCard` itself (rejected - the shared widget stays unmodified; selection mode instead wraps it in a `Row([Checkbox, Expanded(card)])` at the call site, avoiding a shared-widget behavior change for a feature only one screen needs).
